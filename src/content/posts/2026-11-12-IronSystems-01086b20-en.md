> [!WARNING]
> **Verdict: Malicious** · Family **IronSystems** (uncertain) · Confidence **Low**
> 
> Aliases: IronSystems Go Loader
> 
> The sample is an x64 Go program compressed with a modified UPX packer. In real dynamic analysis, about 3 seconds after the process starts it unpacks itself in memory and additionally maps a PE implant not registered in the module list (base 0x144e10000, MEM_PRIVATE, 5 sections); the same process keeps sending multipart /gate check-in packets (hwid, build_id, format=json) to 195[.]15[.]201[.]249 and to specific paths on telegram[.]me and steamcommunity[.]com, reconnecting every 2–5 seconds until observation ended. The implant embeds dozens of security-software process/module names and anti-debug calls such as NtQueryInformationProcess and NtSetInformationThread, and has AES-GCM encryption and browser UA masquerading. Overall it is assessed as an evasion-capable RAT check-in/loader.

## Behavior Analysis

**10** behaviors in total, each backed by evidence; **6** are statically obtainable and **4** were obtained through dynamic analysis.

### 1. Two-layer UPX unpacking in memory

`T1027.002` · Confidence **High** · Static

The file section table is UPX0/UPX1/UPX2, with the entry point in the high-entropy (8.0) UPX1; after execution the main image is unpacked in memory, and memory scanning finds 4,903 code patches relative to the on-disk image, consistent with compressed sections being expanded in memory.

> **Evidence**: sections UPX0/UPX1/UPX2, UPX1 entropy 8.0, entry RVA 0x402df0 in UPX1; memory scan code_scan patches=4903
> 
> **Source**: `ev-000004` · `ev-000008` · `ref:10293806e7` · `ref:71ff0d96cf`

### 2. Manual-mapped implant in memory

`T1620` · Confidence **High** · Dynamic

A PE module that belongs to no on-disk file and is not registered in the module list appears inside the sample process: base 0x144e10000, size 0xE9000, protection PAGE_EXECUTE_READWRITE(0x40), mapping type MEM_PRIVATE, 5 sections, a 64-bit executable image — a typical manually mapped/reflectively loaded payload.

> **Evidence**: working-set scan module=144e10000 size=e9000 protection=40 mapping_type=MEM_PRIVATE is_listed_module=0 sections_count=5
> 
> **Source**: `ref:71ff0d96cf` · `ref:16e1c227e3`

### 3. POST host fingerprint to /gate

`T1071.001` · Confidence **High** · Dynamic

The process sends an HTTPS POST /gate to the C2 address with multipart form fields hwid, build_id, format=json, where build_id is fixed as e7a89f53fafc99939d3104696d2ebe64 and hwid is the local machine fingerprint string, Content-Length 401, used for victim registration and task delivery.

> **Evidence**: dynamic network record: POST /gate HTTP/1.1, body contains name="hwid"/"build_id"/"format", Host: 195.15.201[.]249
> 
> **Source**: `ref:b1b28d3d3f` · `ref:42eeeac115`

### 4. Telegram/Steam fallback gateways

`T1102` · Confidence **High** · Dynamic

Besides the direct IP connection, the sample also visits telegram[.]me/d33ttt and steamcommunity[.]com/profiles/76561198610252751, first GETs the path and then appends /gate to the same path to send the same check-in form, using social-platform paths as fallback C2 gateways/dead drops.

> **Evidence**: DNS queries for telegram.me, steamcommunity[.]com; GET /d33ttt followed by POST /d33ttt/gate; GET /profiles/76561198610252751 followed by POST /profiles/76561198610252751/gate
> 
> **Source**: `ref:42eeeac115` · `ref:7bbed09904`

### 5. Embedded security-software allowlist

`T1518.001` · Confidence **High** · Static

The implant embeds a UTF-16 plaintext list of security-software processes, covering Defender (MsMpEng.exe, MpCmdRun.exe), Avast/AVG, ESET (ekrn.exe, egui.exe, eamsi), Kaspersky (avp.exe, avpui.exe, kavfs.exe), Bitdefender, Norton, Malwarebytes, Dr.Web, Trend Micro and more, and checks the runtime environment against it.

> **Evidence**: implant UTF-16 strings: AvastSvc.exe, aswEngSrv.exe, ekrn.exe, avp.exe, bdagent.exe, NortonSvc.exe, MBAMService.exe, SpIDerAgent.exe, MsMpEng.exe etc.
> 
> **Source**: `ref:49662e2749`

### 6. Evade security modules and sandboxes

`T1497.001` · Confidence **Medium** · Static

The implant embeds a list of security modules and virtualization components to avoid (eamsi, klhk, klfp, aswh, aswA, atcuf, symam, symef, tmmon, vboxdisp.dll), indicating that it adapts its behavior to the security/virtualization modules loaded into the process.

> **Evidence**: implant strings: eamsi, klhk, klfp, aswh, aswA, atcuf, symam, symef, tmmon, vboxdisp.dll
> 
> **Source**: `ref:49662e2749`

### 7. Dynamically resolve anti-debug APIs

`T1622` · Confidence **Medium** · Static

The implant statically imports only a few APIs such as GetProcAddress/LoadLibraryA/GetModuleHandleA/HeapAlloc, and at runtime dynamically resolves NtQueryInformationProcess, NtSetInformationThread, NtQuerySystemInformation and NtQueryInformationToken from ntdll for anti-debugging and process/token probing.

> **Evidence**: implant import table has only 9 thunks (kernel32/user32); strings include NtQueryInformationProcess, NtSetInformationThread, NtQuerySystemInformation
> 
> **Source**: `ref:c5c02fcb9d` · `ref:49662e2749`

### 8. AES-GCM encrypted communication

`T1573.001` · Confidence **Medium** · Static

The implant imports bcrypt's BCryptOpenAlgorithmProvider/BCryptGenerateSymmetricKey/BCryptEncrypt/BCryptDecrypt/BCryptGenRandom and embeds the ChainingModeGCM string, giving it the ability to AES-GCM encrypt/decrypt returned data or delivered payloads.

> **Evidence**: implant IAT: bcrypt.BCryptEncrypt/BCryptDecrypt; UTF-16 string ChainingModeGCM
> 
> **Source**: `ref:c5c02fcb9d` · `ref:49662e2749`

### 9. Browser-impersonating requests

`T1036.005` · Confidence **High** · Dynamic

All HTTP requests carry a browser User-Agent and Accept/Accept-Language headers, switched per target: a macOS Firefox UA for the direct-IP C2 and a Windows Firefox UA for telegram[.]me / steamcommunity[.]com, reducing traffic-side detectability.

> **Evidence**: dynamic request headers User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10.15; rv:140.0) and Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:161.0)

> **Source**: `ref:42eeeac115` · `ref:b1b28d3d3f`

### 10. Go symbol and build-info obfuscation

`T1027` · Confidence **High** · Static

The main program is built with go1.21.1, links only the standard library, and has main-package function and type names replaced with random strings (e.g., main.jcNPLTZ, main.xLdZIrCcd0Ye0); the build path exposes only IronSystems/main.go, raising the difficulty of static attribution.

> **Evidence**: Go buildinf: path IronSystems, mod IronSystems (devel), go1.21.1; symbols main.eUMzNKUs, main.n0AWlKqBKB etc.
> 
> **Source**: `ref:4112393784` · `ref:c23bde4f28`

## Must Not Be Misinterpreted

:::important
The following conclusions are **easy to misjudge**; keep them in mind when citing this report.

- Do not assume it is original UPX just from the UPX0/UPX1 section names and high entropy: the entry jump and unpacking flow were modified, emulation cannot locate the OEP, and actual unpacking can only rely on a memory dump.
- This observation found no persistence traces such as Run registry keys, services or scheduled tasks, and no files dropped to disk, so it cannot be said to have residency or dropping capability.
- No credential, browser-data or file-exfiltration traffic was captured, only check-in registration packets, so it cannot be asserted to be a stealer.
- telegram[.]me and steamcommunity[.]com are only fallback gateway paths in the configuration; no real business session was seen, so the sample cannot be inferred to be related to the Telegram/Steam platforms or to use their official APIs.
:::

## Analysis Method & Limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | Yes (stage2 `f02ba21aa3a11231fc18ddd8c329b4f35f36e33bbb8142125ea2e4faa3bc3472`) |

**Limitations and pending verification**

1. The main program is a Go binary with a modified UPX packer + garble obfuscation; static analysis recovered only the section table, import surface and build info, and emulation did not reach the OEP within the 500k-instruction budget, so the plaintext code could not be statically recovered.
2. Network monitoring recorded only the request side (including the full POST form) and did not obtain the C2 response body, so tasks, configuration or follow-up payloads delivered after /gate cannot be confirmed.
3. The security-software list, module list and Nt* anti-debug function names exist as strings/dynamic resolution; no actual call sequence was observed, and the corresponding evasion effect is an inference of capability.
4. hwid is a one-time fingerprint of this controlled host, while build_id is the sample-level constant; if other C2s rotate, they should be correlated by build_id.
5. The meaning of the mangle-obfuscated configuration keys inside the implant (such as taret_gateway, mutex80feld) could not be fully recovered, and there may be further untriggered configuration items.
6. No persistence, lateral movement or data theft was observed; the conclusions cover only this run window of about 3.5 minutes.
