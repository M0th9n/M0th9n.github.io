> [!WARNING]
> **Verdict: Malicious** · Family **Unattributed custom DLL loader** (uncertain) · Confidence **low**
> 
> Aliases: Custom DLL shellcode loader, Staged reflective PE loader
> 
> Decompilation and disassembly confirm: in DllMain this DLL hot-patches code at fixed offset 0x10BA in the host EXE (after VirtualProtect it rewrites 85 C0 0F 84 to E9 rel32) and jumps to 0x100054E2; there, a rolling key decrypts 0x2327B bytes (143995 bytes) of high-entropy .rdata data into VirtualAlloc-allocated read-write-execute memory, then calls it directly for execution. The decrypted result is a position-independent reflective PE loader that resolves LoadLibraryA/GetProcAddress/VirtualAlloc/Sleep through PEB traversal and API hashing (0x7C35D9A3) and loads an embedded image. The above is self-evident from byte-by-byte recomputation and disassembly, not speculation.

## Behavior analysis

**6** behaviors in total, each backed by evidence, all statically recoverable.

### 1. Hot-patch host code

`T1055` · Confidence **high** · static

On DLL_PROCESS_ATTACH it calls GetModuleHandleA(NULL) to get the host EXE base, verifies the bytes at base+0x10BA are 85 C0 0F 84, and on a match rewrites them to E9 rel32 after VirtualProtect, jumping to 0x100054E2.

> **Evidence**: 0x100055CA: call GetModuleHandleA; lea esi,[eax+0x10BA]; 0x10005564: VirtualProtect and write E9
> 
> **Source**: `ref:57d9cd73f7` · `ref:7652c7a743` · `ref:c0731314b8`

### 2. Decrypt encrypted payload

`T1027` · Confidence **high** · static

0x100054E2 uses 0xE6CF8C23 at .rdata RVA 0x7808 as the seed and XORs each of the 0x2327B bytes starting at RVA 0x780C, updating the key per byte with ((k<<16)+(k>>16))*0x77+0x13, writing the result to a newly allocated buffer.

> **Evidence**: 0x1000550F: push 0x2327F; call VirtualAlloc; 0x1000553D: xor al,bl loop; .rdata entropy 7.948
> 
> **Source**: `ref:97988d53d0` · `ev-000016` · `ev-000005`

### 3. Execute payload from RWX memory

`T1055` · Confidence **high** · static

It allocates memory with VirtualAlloc(NULL, 0x2327F, MEM_COMMIT, PAGE_EXECUTE_READWRITE), writes the decrypted data, then pushes 0 and calls the buffer entry, executing the payload without touching disk.

> **Evidence**: 0x10005503 push 0x40/0x1000/0x2327F/0; 0x1000557A push 0; call [ebp-8]
> 
> **Source**: `ref:97988d53d0`

### 4. Reflectively load embedded image

`T1620` · Confidence **medium** · static

The stub at 0x22C56 of the decrypted data walks the PEB's InLoadOrderModuleList, locates kernel32.dll by hash 0xFD5B1261, then resolves LoadLibraryA/GetProcAddress/VirtualAlloc/Sleep; it then uses a custom descriptor at 0x18 (magic 0x7C35D9A3, PE magic 0x010B) to allocate the image, copy sections, relocate, and fix imports, finally calling the entry point.

> **Evidence**: PEB traversal via fs:[0x30] from 0x22C56; hash comparisons 0xFD5B1261/0xBDA26FE6/0xA16DC157/0x24A6650A/0x27BE7673
> 
> **Source**: `ev-000016` · `ref:97988d53d0`

### 5. Fake exports, minimal imports

`T1036` · Confidence **high** · static

The DLL export directory keeps only the random module name hpqhvsei.dll with 0 exported functions; the import table has only KERNEL32 CRT functions and USER32.GetForegroundWindow, exposing no network/process/file capabilities.

> **Evidence**: export directory RVA 0x2B230, DLL name hpqhvsei.dll, count=0; imports only 2 DLLs with 59 symbols total
> 
> **Source**: `ref:d39cc919fc` · `ref:1cf19b5670` · `ref:94a32265bc`

### 6. Junk jumps to hinder analysis

`T1027` · Confidence **medium** · static

The decrypted loader inserts 5-byte junk sequences into the instruction stream (e.g., 78 03 79 01 E9, where both conditional jumps land at +5), misaligning linear disassembly; the decryption loop calls GetForegroundWindow once per byte to create noisy calls.

> **Evidence**: junk jumps at 0x22C6E/0x22C8E etc.; 0x100054E2 mov esi,[0x100060EC]; call esi inside the loop
> 
> **Source**: `ev-000016` · `ref:97988d53d0`

## Must not claim

:::important
The following conclusions are **prone to misjudgment**; take care when citing this report.

- It cannot be judged a stealer/ransomware/miner sample: the final PE payload has not been fully unpacked, and there is no evidence of file traversal, encryption, or mining logic.
- It cannot be claimed to have remote C2 or domain/IP indicators: there are no network strings statically, and dynamic observation showed no sample-related egress.
- It cannot be judged benign just because the sandbox produced no new process/alerts: the sample is a DLL and requires a specific host to load it before the +0x10BA hot-patch condition is met.
- It cannot be simply attributed to a known family: it has only generic loader characteristics, and family attribution evidence is insufficient.
:::

**Limitations and pending verification**

1. The custom PE wrapper inside the second stage (descriptor magic 0x7C35D9A3 at 0x18) was not fully unpacked, so the final PE's functionality and C2 are unknown.
2. The target host EXE was not obtained, so the base+0x10BA patch precondition could not be met; real dynamic execution observed no malicious behavior, reproduced=false.
3. Empty c2 and host_iocs mean only that none were observed, not that the sample lacks network or persistence capability.
4. The .rdata high entropy (7.948) comes from an encrypted payload rather than a compression packer, so standard packer-detection scores of 0 do not apply to this sample.
