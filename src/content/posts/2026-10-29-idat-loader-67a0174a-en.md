> [!WARNING]
> **Verdict: malicious** · Family **DIDAT / IDAT-style multi-stage PE loader (HijackLoader-like)** (uncertain) · Confidence **medium**
> 
> Aliases: HijackLoader, IDAT Loader, DIDAT Loader
> 
> Static analysis fully recovered a self-implemented multi-stage packer: layer 1 uses an xorshift stream to decrypt the tables/API names in .data, then extracts a 0x25a00-byte stage2 DLL from .text (RVA 0x2010) by chunk shuffling, maps it reflectively and calls its export RunStage2; stage2 then decrypts the 0x9e00-byte overlay at the tail with key 0x6f0fecc8 and reflectively loads the stage3 payload; stage3 contains Windows Defender exclusions (WMI root\Microsoft\Windows\Defender / MSFT_MpPreference / ExclusionPath), amsi.dll and NtRemoveProcessDebug/DbgUiSetThreadDebugObject, LdrLoadDll code scanning (unhooking), debugger/VM checks and target paths of system processes. This combination has no legitimate software use.

## Behaviour analysis

**10** behaviours were recovered, each with supporting evidence, and all are static.

### 1. Decrypt the embedded strings and tables

`T1140` · confidence **high** · static

Starting from the .data tables (RVA 0x41010/0x41c20/0x428c0/0x430f0), it recovers the API names and the length/offset tables with an xorshift32 stream plus multiplication constant 0x5f356495 (seed 0xefdf8662).

> **Evidence**: FUN_140001b70 @0x140001b70; FUN_140001c60 @0x140001c60; seed 0xefdf8662
> 
> **Source**: `ref:19c2f91efb` · `ref:1858e3ae5b` · `ref:89c2ced317`

### 2. Extract the embedded payload

`T1027` · confidence **high** · static

From the 0x39dd4 bytes of shuffled data at RVA 0x2010 it sequentially extracts 0x25a00 bytes in 32 segments of random length, yielding the stage2 DLL.

> **Evidence**: FUN_14003beb0 @0x14003beb0 arguments (0x39dd4,0x25a00,0xefdf8662,0x26,1,2)
> 
> **Source**: `ref:8ce4fe535d` · `ref:8d626874ee`

### 3. Reflectively map stage2

`T1620` · confidence **high** · static

It heap-allocates an image, copies the 0x400 header and 6 sections, patches 772 relocation entries, fills the IAT with LoadLibraryA/GetProcAddress from the recovered KERNEL32 name table, changes page protections with VirtualProtect and then calls entry 0x1010.

> **Evidence**: FUN_14003ca40 @0x14003ca40; relocation tables 0x140041010/0x140041c20; import name table 0x1400428c0
> 
> **Source**: `ref:ba906b5ade` · `ref:95df3a67d5` · `ref:cd5b14b2bf`

### 4. Map the image as an executable section

`T1055` · confidence **high** · static

NtCreateSection (size 0x21000, SEC_COMMIT) + NtMapViewOfSection map it into the current process with PAGE_EXECUTE_READWRITE, providing the target memory for reflective loading.

> **Evidence**: FUN_14003d400 @0x14003d400 calls NtCreateSection(0xf001f)/NtMapViewOfSection(prot=0x40)
> 
> **Source**: `ref:9e67ec9d9b` · `ref:688a4c80d8`

### 5. Second decryption and load of the dropped payload

`T1620` · confidence **high** · static

stage2 applies the same stream decryption to the accompanying 0x9e00-byte overlay with key 0x6f0fecc8, validates MZ/PE, then reflectively loads it with NtCreateSection/NtMapViewOfSection and jumps to the entry point.

> **Evidence**: FUN_1800010b0 @0x1800010b0; FUN_180001150 key=0x6f0fecc8; FUN_180001240 MZ+PE validation
> 
> **Source**: `ref:a329b314f8` · `ref:629b762960` · `ref:d979f94f01`

### 6. Add Defender exclusions

`T1562.001` · confidence **medium** · static

Through COM/WMI it connects to root\Microsoft\Windows\Defender and calls MSFT_MpPreference to set ExclusionPath (with ChainingMode/ObjectLength/Force parameters).

> **Evidence**: strings root\Microsoft\Windows\Defender / MSFT_MpPreference / ExclusionPath; imports ole32 CoCreateInstance/CoSetProxyBlanket/CoInitializeSecurity
> 
> **Source**: `ref:cb8c7a65bb` · `ref:018012a7ee`

### 7. Evade AMSI and debugging

`T1562.001` · confidence **medium** · static

It references amsi.dll, enumerates the LdrLoadDll machine code to find overwritable locations (unhooking), and uses undocumented APIs such as DbgUiSetThreadDebugObject and NtRemoveProcessDebug to evade debugging/scanning.

> **Evidence**: FUN_140003054 @0x140003054 parses the LdrLoadDll instruction stream; strings amsi.dll / DbgUiSetThreadDebugObject / NtRemoveProcessDebug
> 
> **Source**: `ref:3b8574ec07` · `ref:cb8c7a65bb`

### 8. Detect virtualisation and debuggers

`T1497.001` · confidence **high** · static

It uses cpuid/rdtsc/int 2Dh plus IsDebuggerPresent and NtQueryInformationProcess to probe for debuggers/VMs, and exits silently on anomalies.

> **Evidence**: anti-debug static identification hits rva 253494 (rdtsc)/22061 (int 2Dh)/28060 (cpuid); string NtQueryInformationProcess
> 
> **Source**: `ref:637a6a8d80` · `ref:cb8c7a65bb`

### 9. Masquerade as a system cleanup tool

`T1036.005` · confidence **high** · static

The stage3 resource version information is disguised as CleanMgr / cleanmgr.exe / Disk Management; the outer version information is disguised as Silver-Systems' Sensor Authenticator System.

> **Evidence**: VS_VERSION_INFO OriginalFilename=cleanmgr.exe; outer CompanyName=Silver-Systems

> **Source**: `ref:cb8c7a65bb` · `ref:f32a3195ca`

### 10. Select system processes as targets

`T1218` · confidence **medium** · static

It bundles the C:\Windows\System32\ComputerDefaults.exe, winver.exe and \System32\RuntimeBroker.exe paths for use in the privilege-escalation/proxy execution chain.

## Don't misread this

:::important
The following conclusions are **easy to get wrong**; keep them in mind when citing this report.

- No file encryption/destruction behaviour was observed, so it must not be judged ransomware or a wiper.
- The final payload's import table contains no evidence of browser-credential or wallet APIs, so it must not be asserted to be a stealer.
- In this real sandbox the sample process started but no injection, child process or outbound connection was observed, so it must not be claimed that C2 communication or a second-stage download was observed.
- No persistence evidence (service/scheduled task/Run key) was found, so it must not be claimed that the sample starts itself automatically.
- The outer Silver-Systems / Sensor Authenticator and the inner CleanMgr metadata are both masquerades and must not be taken as real vendor attribution.
:::

**Limitations and open questions**

1. The real sandbox run observed no malicious behaviour: memory scanning found no injected/replaced modules, and network monitoring saw no outbound traffic from the sample process, so reproduced=false and all dynamic conclusions are pending_dynamic_verify.
2. The C2/download addresses were not recovered; the final payload may fetch configuration or the next stage remotely at runtime, which requires dynamic analysis or external network access to confirm.
3. The static recovery was reproduced by a custom script implementing the packer algorithm, so it is self-reported evidence; a few functions remain unexpanded (e.g. the details of WMI argument construction).
4. The Defender exclusion and AMSI unhooking are static capability identifications; neither was seen taking effect in the sandbox.
5. The sample contains cpuid/rdtsc/int 2Dh anti-virtualisation checks, so the sandbox environment may cause it to abort and mask its true behaviour.
6. Family attribution is based on the .didat/DIDATSIG markers and the loader structure, without vendor YARA or multi-engine corroboration, hence marked uncertain.
