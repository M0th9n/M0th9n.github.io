> [!WARNING]
> **Verdict: malicious** · Family **Unattributed (suspected RAT/screen-capture component)** (doubtful) · Confidence **low**
> 
> The PE32 DLL has an empty export table and its entry is DllMainCRTStartup; decompilation and instruction-level emulation confirm that its normal load path only performs CRT initialization, executes Sleep(0x153), and returns. The binary contains two blobs of high-entropy data with no recognizable header (69,920 bytes in .data and 75,187 bytes in the overlay), bracketed by 77-entry and 158-entry code-pointer dispatch tables; the code is control-flow flattened throughout and actually references VirtualAlloc/VirtualProtect/LoadLibraryA/GetProcAddress as well as window, icon, cursor, clipboard, and token-impersonation APIs. This combination matches an encrypted-payload carrier/RAT component, but the payload could not be decrypted and executed in the analysis environment.

## Behavior analysis

**8** behaviors in total, each backed by evidence; **7** are obtainable statically and **1** was obtained through dynamic analysis.

### 1. Embed two high-entropy payload blobs

`T1027.009` · Confidence **High** · Static

The 69,920-byte blob in .data and the 75,187-byte overlay have entropy of about 7.996/7.998, with clear boundaries and no MZ/PE, zlib, LZMA, or bzip2 headers; both blobs are immediately adjacent to code-pointer tables.

> **Evidence**: .data starting at RVA 0x6144, 0x11120 bytes; file offset 0x16C00, 0x125B3 bytes
> 
> **Source**: `ev-000005` · `ev-000017`

### 2. Control-flow flattening

`T1027` · Confidence **High** · Static

Many basic blocks end with jmp dword ptr [table entry], backed by the 77-entry code-pointer table at .data 0x6010-0x6144 and the 158-entry table at 0x17264-0x174D8; the decompiler cannot recover the full call graph.

> **Evidence**: rva 0x35FA jmp [0x100172FC]; rva 0x2242 jmp [0x10006020]; rva 0x3606 jmp [0x10017350]
> 
> **Source**: `ev-000017` · `ev-000014` · `ev-000016`

### 3. 339 ms delay on load

`T1497.003` · Confidence **High** · Dynamic

After CRT initialization DllMain(DLL_PROCESS_ATTACH) calls Sleep(0x153) and then returns 1 directly, with no other business action.

> **Evidence**: KERNEL32.Sleep(0x153), call site in the 0x100047E* path
> 
> **Source**: `ev-000018`

### 4. Read hostname and seed RNG

`T1082` · Confidence **Medium** · Static

Internal function 0x10001000 calls GetComputerNameA to read the hostname and uses 0x5FB00000 as the srand seed, serving host fingerprinting/randomization.

> **Evidence**: 0x10001000 call [0x10005070]=GetComputerNameA; followed by call srand
> 
> **Source**: `ev-000008` · `ev-000018`

### 5. Enumerate windows and clipboard

`T1113; T1115` · Confidence **Medium** · Static

Imports and references in code include GetTopWindow/GetWindow/GetWindowTextA/GetWindowThreadProcessId/GetGUIThreadInfo/IsWindowUnicode/IsIconic/IsZoomed/GetWindowRgn/GetWindowDC/GetIconInfo/DuplicateIcon/GetCursor/IsClipboardFormatAvailable, etc.; emulation calling 0x10001834 directly observed IsClipboardFormatAvailable(3).

> **Evidence**: call [0x100050xx]=IsClipboardFormatAvailable inside 0x10001834; USER32/GDI32 import surface
> 
> **Source**: `ref:5df3f89e84` · `ev-000013` · `ev-000018`

### 6. Reserve and change memory protection

`T1055` · Confidence **Medium** · Static

The code contains VirtualAlloc (rva 0x29B3, 0x4444) and VirtualProtect (rva 0x183A) call sites and also references VirtualQuery; emulation calling 0x10001834 directly hit VirtualProtect.

> **Evidence**: 0x100029B3 call [0x10005038]=VirtualAlloc; 0x1000183A call [0x10005074]=VirtualProtect
> 
> **Source**: `ref:5df3f89e84` · `ev-000013` · `ev-000018`

### 7. Dynamically resolve imports

`T1027.007` · Confidence **Medium** · Static

Imports and calls LoadLibraryA (rva 0x387A) and GetProcAddress to resolve at runtime APIs not listed in the import table, a common precursor to later payload execution.

> **Evidence**: 0x1000387A call [0x10005054]=LoadLibraryA; import table contains GetProcAddress@0x10005030
> 
> **Source**: `ref:5df3f89e84` · `ev-000015`

### 8. Can revert to caller token

`T1134.001` · Confidence **Medium** · Static

Imports InitializeSecurityDescriptor, RevertToSelf, and GetUserNameA; RevertToSelf is called twice in the code, indicating impersonation of the logged-on user in a service/high-privilege context.

> **Evidence**: ADVAPI32!RevertToSelf@0x10005008, 2 call sites; InitializeSecurityDescriptor@0x10005000

> **Source**: `ref:5df3f89e84` · `ev-000016`

## Do not misjudge

:::important
The following conclusions are **easy to misjudge**; keep this in mind when citing this report.

- Do not claim actual execution of C2 outbound traffic, screen capture, keylogging, or clipboard theft was observed — the dynamic stage did not show these behaviors.
- Do not judge it as ransomware or a file encryptor because of GDI/USER32 imports; no file encryption, ransom note, or bulk file rewriting was found.
- Do not claim the DLL can be run directly with rundll32 or regsvr32: its export table is empty and DllMain has no business logic.
- Do not directly assert that the two high-entropy blobs are AES/RC4 ciphertext or the output of a known packer; neither the algorithm nor the packer identity is confirmed.
:::

**Limitations and open questions**

1. The DLL has no exports, and DllMain's normal path only performs CRT initialization and Sleep(0x153), providing no triggerable business entry; invoking it by internal RVA from a specific host cannot be ruled out.
2. The two embedded blobs have entropy near 8.0 and all zlib/bzip2/raw LZMA decompression attempts fail; the key and algorithm were not recovered, so the payload type, C2, and full configuration cannot be confirmed.
3. Control-flow flattening (77/158-entry dispatch tables and many indirect jumps) leaves the static call chain incomplete; function semantics come from local decompilation and targeted emulation.
4. Real sandbox delivery observed no child processes, file/registry changes, or sample-related network traffic; the network monitoring log contained only system-update noise.
5. Family attribution lacks YARA, plaintext configuration, or multi-engine corroboration; only a candidate category is given with low confidence.
