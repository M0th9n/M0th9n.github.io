> **Verdict: Malicious** · Family **XMRig** · Confidence **High**
> 
> Aliases: CoinMiner, XMRig Miner, Riskware.Miner
> 
> The sample is a UPX-packed x86-64 static ELF; after unpacking it is an 8.78 MB XMRig 6.26.0 miner. Real execution in an isolated Linux instance confirmed: with no configuration file it does not exit but enters the mining main loop directly, creates a TCP socket and connects to 85.11.167[.]190:443, retrying continuously after failure; it also reads host information such as /proc/meminfo, DMI/SMBIOS, /dev/mem and /proc/sys/vm/nr_hugepages for mining parameter tuning. The sample carries no dropper, persistence, ransomware or stealer components and is classified as a mining trojan (CoinMiner).

## Behavior Analysis

**7** behaviors in total, each with evidence attached; **3** are statically available and **4** were obtained by dynamic analysis.

### 1. Delivered UPX-packed

`T1027.002` · Confidence **High** · Static

The sample appears as a UPX-packed x86-64 static ELF, with a 'UPX!' marker at file header offset 0xEA; after unpacking, its size grows from 2,484,928 bytes to 8,784,920 bytes (compression ratio 28.27%), yielding a parseable statically linked miner.

> **Evidence**: 'UPX!' at packed offset 0xEA (ev-000002); upx -d succeeded, recovered file sha256=afaba21a… (ev-000073)
> 
> **Source**: `ev-000002` · `ev-000073`

### 2. Starts Mining Without Config

`T1496` · Confidence **High** · Dynamic

When run without arguments, the sample tries in turn to open <exe_dir>/config.json, $HOME/.xmrig.json and $HOME/.config/xmrig.json; after all three are absent it does not exit but continues to initialize the mining engine and keeps running; the process stays alive throughout the 20-second observation window (terminated by timeout, exit=137).

> **Evidence**: three 'unable to open ...' lines on stdout; dyn.exec exit=137 timed_out (ev-000010); open(config.json/.xmrig.json/.config/xmrig.json) all ENOENT (ev-000044, ev-000046, ev-000047)
> 
> **Source**: `ev-000010` · `ev-000044` · `ev-000046` · `ev-000047`

### 3. Direct Connection to Pool Port 443

`T1095` · Confidence **High** · Dynamic

After startup it creates an AF_INET stream socket (with TCP_NODELAY and SO_KEEPALIVE) and connects directly to 85.11.167[.]190:443; the connection returns ENETUNREACH due to network isolation, after which the process retries at roughly 1-second intervals and stays resident.

> **Evidence**: socket(AF_INET, SOCK_STREAM) = 13 (ev-000070); connect(13, {443, 85.11.167[.]190}) = -1 ENETUNREACH (ev-000071)
> 
> **Source**: `ev-000070` · `ev-000071`

### 4. Built-in Default Pool Address

`T1573.002` · Confidence **High** · Static

The binary embeds the string 'stratum+ssl://randomx[.]xmrig[.]com:443', referenced by the lea instruction at 0xe2d5c as the default pool endpoint when no config is present; the same region also retains algorithm identifiers such as cryptonight-monerov8.

> **Evidence**: 0xe2d5c: lea rcx,[rip+0x5738ed] → 0x656650 'stratum+ssl://randomx[.]xmrig[.]com:443' (ev-000075); 0x63e21b 'cryptonight-monerov8' (ev-000074)
> 
> **Source**: `ev-000074` · `ev-000075`

### 5. Collects Host Hardware Fingerprint

`T1082` · Confidence **High** · Dynamic

During execution it reads /proc/meminfo, /proc/sys/vm/nr_hugepages, /sys/firmware/dmi/tables/smbios_entry_point, /sys/firmware/efi/systab and /proc/efi/systab, and tries to open /dev/mem for physical memory information, using them to select the RandomX dataset mode and thread count.

> **Evidence**: open('/proc/meminfo')=11 and 1503 bytes read (ev-000060); open('/dev/mem') = -1 EACCES (ev-000067); DMI/SMBIOS probing (ev-000064); hugepages probing (ev-000059)
> 
> **Source**: `ev-000059` · `ev-000060` · `ev-000064` · `ev-000067`

### 6. Huge Pages and MSR Performance Tuning

`T1496` · Confidence **Medium** · Static

The code contains the /dev/cpu/<n>/msr path and the command string '/sbin/modprobe msr allow_writes=on > /dev/null 2>&1', used to write MSR and request huge pages under root privileges to boost RandomX hashrate; this run used uid=1000, so that path was not triggered.

> **Evidence**: 0x296383: lea rsi,[rip+0x3aadc6] → 0x641150 '/dev/cpu/'; 0x65ad10 '/sbin/modprobe msr allow_writes=on' (ev-000074, ev-000075); getuid=1000 at runtime (trace from ev-000042)
> 
> **Source**: `ev-000074` · `ev-000075`

### 7. Multithreaded Resident CPU Usage

`T1496` · Confidence **Medium** · Dynamic

While running, the process forks a child process and creates multiple 'libuv-worker' threads; when run with explicit pool parameters it keeps consuming CPU for 12 seconds (terminated by timeout, exit=124), consistent with background mining load.

> **Evidence**: trace: fork followed by clone of libuv-worker threads; dyn.exec 12s timeout exit=124 (ev-000040); 20s run exit=137 (ev-000010)
> 
> **Source**: `ev-000010` · `ev-000040`

## Do Not Misjudge

:::important
The following conclusions are **easy to misjudge**; take note when citing this report.

- The sample contains no ransomware, stealing or lateral movement code and should not be reported as ransomware, stealer or worm.
- No persistence writes via cron/systemd/rc.local/ssh were observed, nor any download or secondary drop behavior, so it should not be reported as a dropper/downloader.
- The built-in default pool domain randomx[.]xmrig[.]com is XMRig's official donation pool and cannot be used to attribute attacker infrastructure; the runtime-observed 85.11.167[.]190:443 did not establish a stratum session, so wallet ownership and revenue flow cannot be confirmed.
- No embedded Monero wallet address was found, so it cannot be asserted that this binary is a custom exclusive miner bound to a single wallet.
:::

## Analysis Method and Limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis (Linux sample) + static decompilation |
| Unpacking | Yes (stage2 `afaba21a3fe0eda9ff4263900b9bb81a3c335daa16cc1490f8345daa38c1b624`) |

**Limitations and Pending Verification**

1. The analysis network namespace has no external network access; only connect returning ENETUNREACH was observed and no stratum session was established, so both pool endpoints are recorded as static and marked pending_dynamic_verify.
2. Static analysis found no embedded Monero wallet address; the actual operator wallet must be provided by runtime parameters or an external config.json, which was not available here, so attribution of mining revenue cannot be determined.
3. The dynamic connection target 85.11.167[.]190 does not appear in the binary as ASCII or as big-/little-endian 4-byte values, and the trace contains no DNS or /etc/hosts resolution calls, so its mapping to the built-in domain randomx[.]xmrig[.]com cannot be confirmed.
4. The sample ran as uid=1000, so performance optimization paths requiring root, such as MSR writes and huge page requests, were not triggered; the related behavior is supported only by static strings and code references.
5. The sample is a standalone mining component with no dropper/loader, so the initial intrusion vector and delivery source cannot be reconstructed.
