> 
> Aliases: Linux.XORDDoS, XorDdos, Linux/XOR.DDoS

> The decompiled main function and the real run in the isolated environment agree: at startup the program checks the /tmp/log_de.log marker, then resolves and connects to the hardcoded address 38.46.15[.]202:9633, sends the l64 handshake, receives remote data encoded with XOR 0x99 and writes it to an anonymous memory file, and finally executes it with fexecve and disguises the process name as [kworker/0:2]. It has a clear C2 channel and remote payload execution capability, and is judged malicious.

## Behavior Analysis

**8** behaviors in total, each backed by evidence; **5** are statically obtainable and **3** were obtained through dynamic analysis.

### 1. Check marker to prevent rerun

`T1480` · Confidence **high** · Dynamic

At startup, uses access("/tmp/log_de.log", F_OK) to check the drop marker; if the file exists, directly exit(0), to avoid repeated execution.

> **Evidence**: main @0x400950; 0x400967 call access, 0x400977 jne exit branch
> 
> **Source**: `ev-000002` · `ev-000008`

### 2. Hardcoded C2 address

`T1095` · Confidence **high** · Dynamic

Fills the hardcoded 38.46.15[.]202 and port 9633 into sockaddr_in; the address comes directly from .rodata, with no configurable items.

> **Evidence**: .rodata 0x400d00 "38.46.15[.]202"; 0x4009d6 mov word ptr [rsp+0x1e],0xa125 (network order 0x25a1=9633)
> 
> **Source**: `ev-000001` · `ev-000002` · `ev-000014`

### 3. Reconnect every 10s when offline

`T1095` · Confidence **high** · Dynamic

After connect fails, calls sleep(10) and retries indefinitely; in the isolated offline environment, two consecutive connect attempts both returned ENETUNREACH, and the program kept residing and reconnecting.

> **Evidence**: 0x400a37 call sleep(10); 0x400a0f jmp back to connect; dynamic event connect(38.46.15[.]202:9633) = -1 ENETUNREACH
> 
> **Source**: `ev-000002` · `ev-000014` · `ev-000015`

### 4. Send l64 handshake

`T1071` · Confidence **high** · Static

After a successful connection, sequentially sends the 6-byte "l64 " identifier, the 2-byte network-order port, and the 32-byte C2 address string.

> **Evidence**: 0x400a48 send(sock,"l64 ",6,0); 0x400a5f/0x400a72 send port and IP string
> 
> **Source**: `ev-000002` · `ref:4b04210496`

### 5. XOR-decrypt command stream

`T1140` · Confidence **high** · Static

XORs each byte of the data received by each recv with 0x99, then writes it to the drop file, as remotely delivered commands or payload.

> **Evidence**: 0x400abd xor byte ptr [rax],0x99 (loops for the length of this recv)
> 
> **Source**: `ev-000002` · `ref:4b04210496`

### 6. memfd anonymous delivery

`T1620` · Confidence **high** · Static

Calls memfd_create via syscall(0x13f,"a",0) to create an anonymous memory file, writing the decrypted remote data into it without touching disk.

> **Evidence**: 0x400a8a mov edi,0x13f; 0x400a95 call syscall; .rodata 0x400ceb name "a"
> 
> **Source**: `ev-000002` · `ref:4b04210496` · `ref:5b63fba855`

### 7. Fileless payload execution

`T1620` · Confidence **high** · Static

After the C2 connection closes, directly executes the remote payload in the memory file with fexecve(memfd_fd, argv, environ), achieving fileless loading.

> **Evidence**: 0x400b33 call fexecve; arguments fd=r12d, argv={"[kworker/0:2]",NULL}, envp=environ
> 
> **Source**: `ev-000002` · `ref:bc78d7556c`

### 8. Masquerade as kernel thread

`T1036.005` · Confidence **high** · Static

Sets argv[0] to "[kworker/0:2]", and writes its own absolute path via realpath into the CWD environment variable passed to the next stage, masquerading as a kernel worker thread.

> **Evidence**: .rodata 0x400cf1 "[kworker/0:2]"; 0x400b16 realpath; 0x400b22 setenv("CWD")
> 
> **Source**: `ev-000002` · `ref:bc78d7556c` · `ref:5b63fba855`

## Analysis Method and Limitations

| Item | Content |
|:--|:--|

| Unpacking | No |

**Limitations and pending verification**

1. C2 was only observed attempting connect during real execution, returning ENETUNREACH, with no successful session or request/response; therefore the C2 and related configuration are all recorded as static and marked pending_dynamic_verify.
2. The second-stage payload could not be obtained; its functionality, persistence method, and ultimate purpose cannot be confirmed; the remote payload execution path at this stage is proven only by static decompilation.
3. /tmp/log_de.log is only checked, not created, at this stage; the actual writer may be a later stage, and its write timing cannot be confirmed.
4. Family attribution is inferred from strings, the XOR key, the fileless execution technique, and the residual source filename, lacking independent vendor engine or YARA review, and should be cited with caution.
5. The isolated environment has no network; no real C2 response was observed, so subsequent protocol fields and command semantics cannot be verified.
