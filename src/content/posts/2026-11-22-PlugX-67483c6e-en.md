## Behavior Analysis

**12** behaviors in total, each backed by evidence; **10** are static and **2** were obtained dynamically.

### 1. UPX Self-Decompression

`T1027.002` · Confidence **High** · Dynamic

The outer layer is UPX (UPX0 entropy 0, UPX1 entropy 7.783). After launch it decompresses and fills the ~25MB UPX0 section and jumps into the inner loader; that region has been written in the memory dump.

> **Evidence**: Memory dump Minidump range 0x401000 length 0x181c000 filled; on-disk UPX1 entropy 7.783; entry RVA 0x1C56150
> 
> **Source**: `ref:f386b0fd32` · `ref:0bb47ad3e4` · `ref:2450c7992f` · `ref:fe4daf07be`

### 2. Read Key and Decrypt Payload

`T1027` · Confidence **High** · Static

The second-stage loader opens C:\Windows\mshlpda32.dll and reads the first byte of C:\Windows\temp\setup_gitlog.txt, then combines it with a CPUID-derived key stream to XOR/add-decrypt .text; emulation observed the corresponding CreateFileA/ReadFile calls.

> **Evidence**: 0x1C560B0 CreateFileA(C:\Windows\mshlpda32.dll) / 0x1C564BE CreateFileA(setup_gitlog.txt) + ReadFile 1 byte; after CPUID, loop writes bytes starting at 0x401000; in-memory .text differs from disk by 10,650 bytes
> 
> **Source**: `ref:d7c97717d4` · `ref:768d3bb1a8` · `ref:1c590e66e0`

### 3. Impersonate Microsoft Service Host

`T1036.005` · Confidence **High** · Static

## Common Misinterpretations

:::important
The following conclusions are **easy to misinterpret**; keep them in mind when citing this report.

- Do not judge it as ransomware or a file encryptor merely because the sample contains SHA-256 constants; those constants serve the hash-verification/loading flow, and no file encryption or ransomware behavior was observed in the dynamic window.
- Do not assume self-replication or worm-like spreading just because systeminfo/ping/taskkill appear; no SMB scanning, self-copying or lateral dropping was observed in this run.
- Do not claim a successful connection to 200.111.174[.]22 or completion of the UPlugPlay service installation in the dynamic sandbox; the dynamic window only confirmed reconnaissance commands, and neither network nor persistence landing points produced a real session.
- Do not treat Microsoft Corporation/sqhost.exe in the version resource as a legitimate signature or trusted vendor information; that field is impersonated.
:::

## Analysis Method and Limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacked | Yes (stage2 `b2cc539152e17bfd9153f5c4a3560927454b87dc917831e6f7b5698c8af5436e`) |

**Limitations and pending verification**

1. Only reconnaissance child processes were observed in the dynamic window; no actual network session with 200.111.174[.]22 was obtained. C2 and peer_chain are static extractions, recoverability=static and pending_dynamic_verify=true.
2. The inner .text requires C:\Windows\mshlpda32.dll, the first byte of the marker file and a CPUID-derived key to decrypt fully; static decompilation mainly covers the outer loader and plaintext strings, and the full RAT command-handling logic was not recovered.
3. UPlugPlay service creation, Run-key writing and mshlpda32.dll dropping were not observed in the dynamic sandbox; the corresponding behaviors are static code/string capability assessments and were not upgraded to dynamic conclusions.
4. The family naming is based on service names and installation-flow fingerprints such as UPlugPlay, mshlpda32.dll and Dcomsvc/watchdog, without cross-validation from a decrypted configuration or vendor naming, so confidence is medium and uncertain=true.
5. Domains in the network-monitoring log are all OS/browser update and certificate-validation traffic; no sample-originated outbound traffic was seen, so they cannot be used to identify C2 domains.
