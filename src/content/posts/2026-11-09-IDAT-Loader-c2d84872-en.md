## Behavior analysis

**9** behaviors in total, each backed by evidence; **8** are statically available and **1** was obtained through dynamic analysis.

### 1. Decrypts embedded PE payload

`T1140` · Confidence **high** · static

The main function reads 36 chunks from rva 0x855600, calls a self-implemented ChaCha20 variant (FUN_140011d90) to decrypt each chunk, and concatenates them into a complete MZ/PE image.

> **Evidence**: FUN_1400170c0 @0x1400170c0 calls FUN_140011d90(rva 0x11d90); chunk loop over local_598[i*2]/[i*2+1]; decrypted first bytes are 0x4d5a
> 
> **Source**: `ev-000034` · `ev-000037` · `ev-000051`

### 2. Resolves system APIs by hash

`T1027` · Confidence **high** · static

Without relying on the import table, it walks the PEB module list and matches export names using a djb2 variant hash (h=c+h*0x407f), resolving function addresses in ntdll/kernel32 and other modules.

> **Evidence**: FUN_140002160 @0x140002160 parses the export directory; FUN_1400033a0 @0x1400033a0 computes the hash; the main function hard-codes hash constants such as 0x564dc701
> 
> **Source**: `ev-000017` · `ev-000021` · `ev-000031`

### 3. Section-mapping injection into target process

`T1055` · Confidence **high** · static

It resolves and calls NtCreateSection, NtMapViewOfSection, NtQueryInformationProcess, NtWriteVirtualMemory, NtReadVirtualMemory, NtCreateThreadEx and NtResumeThread, working alongside CreateProcessW/GetThreadContext/SetThreadContext — a section-based process-injection/hollowing chain.

> **Evidence**: hashes 0x564dc701=NtCreateSection, 0x47d35655=NtMapViewOfSection, 0xa597a281=NtCreateThreadEx, 0x2f0f37bf=NtResumeThread; main function @0x14004ef40
> 
> **Source**: `ev-000031` · `ev-000017` · `ev-000051`

### 4. Uses Taskmgr as injection host

`T1055.012` · Confidence **medium** · static

After decryption, the encrypted strings in .data contain both System32 and SysWOW64 Taskmgr.exe paths, used to select the host process to inject into/launch according to the target architecture.

> **Evidence**: FUN_14001f770 @0x14001f770 chain-XOR decrypts rva 0x59000/0x59080; plaintext C:\Windows\System32\Taskmgr.exe and the SysWOW64 version
> 
> **Source**: `ev-000052` · `ev-000032`

### 5. Loads mshtml module stomping

`T1055.001` · Confidence **medium** · static

The decrypted strings also contain System32/SysWOW64 mshtml.dll paths, consistent with mapping a large legitimate module into the host process and overwriting its image (module stomping) to carry the payload.

> **Evidence**: decrypted by the same FUN_14001f770 @0x14001f770; rva 0x59040/0x590c0 plaintext mshtml.dll paths; used together with NtCreateSection/NtMapViewOfSection
> 
> **Source**: `ev-000052` · `ev-000031`

### 6. Quick exit after anti-analysis

`T1497.001` · Confidence **medium** · dynamic

It contains anti-analysis checks such as rdtsc/cpuid timing detection and loaded-module-name hash comparison; in the dynamic sandbox the process exited on its own within about 2 seconds of starting, producing no network, dropped files or child processes.

> **Evidence**: FUN_140001550 @0x140001550 uses rdtsc+cpuid; FUN_14002d620 @0x14002d620 enumerates module-name hashes; watch_timeline records pid 3872 as gone after start with no dump/network
> 
> **Source**: `ev-000015` · `ev-000050` · `call:a06467582e2f4e6086812c91`

### 7. Dynamically loads winhttp for outbound

`T1071.001` · Confidence **medium** · static

The second-stage entry reconstructs the UTF-16 string "winhttp.dll" on the stack, resolves LoadLibraryExW by hash, and loads WinHTTP from System32 with the 0x800 flag, preparing for subsequent HTTP communication, though no actual request was observed in this run.

> **Evidence**: stage2 entry @0x140002100: stack XOR reconstructs winhttp.dll, FUN_140031620 resolves hash 0xa1e54897=LoadLibraryExW, then calls ("winhttp.dll",0,0x800)
> 
> **Source**: `ev-000045` · `ev-000051`

### 8. Screen capture and desktop collection

`T1113` · Confidence **high** · static

The second stage imports BitBlt/GetDIBits/CreateCompatibleBitmap/GetDC/GetWindowDC/GetForegroundWindow/GetSystemMetrics/EnumDisplaySettingsW and CreateDesktopW/OpenDesktopW, giving it full-screen capture and desktop/foreground-window information collection capability.

> **Evidence**: stage2 import table: GDI32.BitBlt/GetDIBits, USER32.GetForegroundWindow/GetWindowDC/CreateDesktopW
> 
> **Source**: `call:85099b97efcc4ad48107caaf` · `ev-000039` · `ev-000044`

### 9. Collects host user information

`T1033` · Confidence **high** · static

The second stage imports GetComputerNameA/GetComputerNameExA/GetUserNameA/GetKeyboardLayout/LookupPrivilegeValueW, used to collect the host name, user name and keyboard layout and to adjust token privileges.

> **Evidence**: stage2 import table: KERNEL32.GetComputerNameA/GetComputerNameExA, ADVAPI32.GetUserNameA/LookupPrivilegeValueW
> 
> **Source**: `call:85099b97efcc4ad48107caaf` · `ev-000045`

## Must not be misjudged

:::important
The following conclusions are **easy to misjudge**; keep them in mind when citing this report.

- Do not call it ransomware: the sample imports/resolves no file-encryption or cryptocurrency-related APIs, scan_crypto found no encryption-algorithm constants, and there are no ransomware extensions or ransom strings.
- Do not claim that a C2 has been confirmed or that outbound communication occurred: the dynamic sandbox captured no DNS/HTTP/TCP request from the sample, the second stage only shows static WinHTTP load preparation, and the C2 endpoint remains unrecovered.
- Do not treat the family as a firm conclusion: Taskmgr/mshtml and chunked ChaCha20 are only candidate family traits, lacking family-specific configuration, signatures or public fingerprint comparison.
- Do not claim that the sample completed injection or persistence in the sandbox: the process exited soon after starting, the monitoring component found no injection/hollowing traces, and there is no evidence of registry/service/scheduled-task changes.
:::

**Limitations and pending verification**

1. The dynamic sandbox captured no network request or file write, and c2_hosts/c2_port/campaign_id were all unobtained and treated as dynamic + pending.
2. The second stage's WinHTTP/screenshot/information-collection capabilities come from the import table and entry decompilation and were not observed in a real run; argument parsing, command protocol and endpoints still need later dynamic verification.
3. The family is a low-confidence candidate (IDAT/Hijack Loader), with no family-specific strings or public fingerprint comparison obtained.
4. The second stage's own module-name hash comparison, rdtsc timing and other anti-analysis checks may cause it to exit early in the sandbox, limiting the completeness of the statically derived executable path.
5. The sample's .rdata contains about 8.4 MB of zero padding, making the file abnormally large, but no packed section or high-entropy executable region was found (packing.score=0).
