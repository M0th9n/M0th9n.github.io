> [!WARNING]
> **Verdict: Malicious** · Family **cmutil.dll proxy sideload loader (unattributed family)** (uncertain) · Confidence **medium**
> 
> Aliases: CMUTIL proxy sideload loader, two-stage PE loader
> 
> The sample is a UPX-packed DLL disguised as cmutil.dll; it exports all 57 legitimate cmutil export names and forwards them to the original DLL in System32, while embedding an x64 PE encrypted with a custom transform; the loader decrypts that PE in a TLS callback/export call path, writes it to a temporary file, and completes process-hollowing injection through NtCreateSection/NtMapViewOfSection/NtUnmapViewOfSection, CreateProcessW and SetThreadContext; it also installs a WH_KEYBOARD hook and a fake error dialog as anti-analysis measures. All of the above logic is directly confirmed by decompilation and decoded string tables, and constitutes malicious loader behavior.

## Behavior analysis

**10** behaviors in total, each backed by evidence, and all are statically available.

### 1. Masquerade as cmutil proxy exports

`T1574.002` · Confidence **high** · static

Under the name cmutil.dll the sample exports all 57 same-named functions; at startup it loads the real cmutil.dll from System32 and calls GetProcAddress for each one, forwarding legitimate calls so that the host program does not crash from the replaced DLL.

> **Evidence**: export table 57 entries (CmAtolA..WzToSzWithAlloc); FUN_2783f1c50 concatenates %SystemDir%\cmutil.dll then LoadLibraryW + 57 GetProcAddress calls
> 
> **Source**: `ref:f8ea2ea3ae` · `ref:09410c38b5` · `ref:93154af3a7`

### 2. Decrypts embedded encrypted payload

`T1027` · Confidence **high** · static

It stores 958,682 bytes of ciphertext in .rdata (pointers at RVA 0xF3B80/0xF3B90), and FUN_2783f2200's variable-step addition, whole-buffer reversal and adjacent-byte swap transform restores an x64 PE beginning with MZ/PE.

> **Evidence**: FUN_2783f4960 copies [0x97D0,0xF38AA) then calls FUN_2783f2200(ptr,size,-2,-0x5A,-0x12); the recovered PE is 912,384 bytes
> 
> **Source**: `ref:33230f43f3` · `ref:87d51e205b` · `ref:4735b761ef`

### 3. Drops temp file and executes it

`T1106` · Confidence **high** · static

The decrypted PE is written to a random file name under %TEMP%, after which CreateProcessW (with a PROC_THREAD_ATTRIBUTE_LIST) creates a suspended process executing that file path.

> **Evidence**: FUN_2783f32c0: GetTempPathW → GetTempFileNameW (plaintext key string) → CreateFileW(0xC0010000) → WriteFile → CreateProcessW + InitializeProcThreadAttributeList
> 
> **Source**: `ref:e86da9e6ad` · `ref:260816ffed`

### 4. Hollow and inject new process

`T1055.012` · Confidence **high** · static

It maps memory with NtCreateSection + NtMapViewOfSection, writes the payload into the target process, unmaps the original image with NtUnmapViewOfSection, and uses GetThreadContext/SetThreadContext to modify the thread context and launch the payload.

> **Evidence**: string table @RVA 0x96A0-0x96E0 decodes NtCreateSection/NtMapViewOfSection/NtUnmapViewOfSection/NtWriteVirtualMemory/NtQueryInformationProcess; FUN_2783f32c0 calls these APIs and SetThreadContext
> 
> **Source**: `ref:c36a81f54e` · `ref:3b7af87d1a` · `ref:e86da9e6ad`

### 5. Enumerates processes and opens handles

`T1057` · Confidence **high** · static

It traverses processes with CreateToolhelp32Snapshot/Process32FirstW/Process32NextW and obtains handles with OpenProcess, preparing to select an injection target.

> **Evidence**: string table @RVA 0x9400-0x9430 decodes CreateToolhelp32Snapshot/Process32FirstW/Process32NextW/OpenProcess, resolved by FUN_2783f2df0
> 
> **Source**: `ref:3b7af87d1a` · `ref:6f6ef4e13d`

### 6. Installs keyboard hook callback

`T1056.001` · Confidence **medium** · static

It calls SetWindowsHookExW(WH_KEYBOARD) with GetCurrentThreadId as the thread argument, pointing the callback at internal function FUN_2783f2440 and calling CallNextHookEx in the callback chain.

> **Evidence**: FUN_2783f2550: GetProcAddress(user32,SetWindowsHookExW) then SetWindowsHookExW(5, FUN_2783f2440, 0, GetCurrentThreadId)
> 
> **Source**: `ref:c7bf225862` · `ref:3b7af87d1a`

### 7. Executes early via TLS callbacks

`T1622` · Confidence **high** · static

The PE's TLS directory registers two callbacks (tls_callback_0/tls_callback_1) that enter internal initialization logic before DllMain, used to complete environment checks/preparation ahead of the normal loading flow.

> **Evidence**: tls_callback_0 @RVA 0x6490 calls FUN_2783f7041; tls_callback_1 @RVA 0x6550; the TLS data directory is non-empty
> 
> **Source**: `ref:ba365a4d48` · `ref:4632fd2ce4`

### 8. Fake error dialog as cover

`T1497` · Confidence **medium** · static

It imports and resolves MessageBoxW/MessageBoxIndirectW/SoftModalMessageBox/DialogBoxParamW plus GetShellWindow and window class "#32770", giving it the ability to pop fake error dialogs or probe analysis windows in abnormal scenarios.

> **Evidence**: string table @RVA 0x9450-0x9570 decodes the above APIs; FUN_2783f2740/FUN_2783f2df0 resolve user32 exports
> 
> **Source**: `ref:3b7af87d1a` · `ref:18e3141f2e`

### 9. Dynamically resolves system APIs

`T1027` · Confidence **high** · static

The first stage statically imports only 10 symbols and leaves the rest absent; the second stage has 0 imports and relies on GetProcAddress/LoadLibraryA/GetModuleHandleA and PEB parsing for the APIs it needs, evading import-table detection.

> **Evidence**: pe.imports: the original sample has 10 imports; the decrypted second stage has 0 imports, with only plaintext names such as GetProcAddress/LoadLibraryA/GetModuleHandleA/GetProcessHeap/HeapAlloc at the end of .rdata
> 
> **Source**: `ref:10d5042e3a` · `ref:da98f210d2` · `ref:0da033370e`

### 10. UPX-packed high-entropy sections

`T1027.002` · Confidence **high** · static

The outer DLL is UPX-packed, with UPX0 an empty virtual section, UPX1 at entropy 7.999, and the entry section writable and executable, used to hide the loader code.

> **Evidence**: sections UPX0/UPX1, UPX1 entropy 7.999, UPX0/UPX1 both RWX; packer identification upx confidence 0.9
> 
> **Source**: `ref:111a7a3893` · `ref:ab351ad916`

## Must not be misjudged

:::important
The following conclusions are **easy to misjudge**; keep them in mind when citing this report.

- Do not report it as ransomware/wipers: no file encryption, shadow-copy deletion or boot-area destruction was found.
- Do not treat the sample as a normal cmutil.dll: the legitimate export names and version information are only a disguise, and the code is a custom loader.
- Do not give specific C2 domains/IPs/URIs: no configuration was statically recovered, and no outbound communication was observed when detonated in the isolated environment.
- Do not assert the keyboard hook is a keylogger: it is a thread-local WH_KEYBOARD hook, possibly for execution scheduling/anti-analysis, and was not dynamically confirmed.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | Static decompilation (dynamic execution yielded no runtime behavior) |
| Unpacking | Yes (stage2 `6e8e30f07d7b320f716ca446d6121e90d0d5e77f3bb2da77de0f2a9c404fd9e7`) |

**Limitations and pending verification**

1. The sample is a DLL without directly executable exports such as DllRegisterServer/ServiceMain, and no host was launched after detonation (the dynamic timeline shows no new process or network record), so runtime behavior could not be verified by replay.
2. The C2, configuration and installation paths were not statically recovered; the second stage's strings/configuration are decrypted at runtime, requiring execution in an environment with a host process or a memory dump for confirmation.
3. About 27 KB of high-entropy data at second-stage .data offset 0x42900 has not been decrypted, so the presence of configuration or a third-stage payload cannot be excluded.
4. The exact purpose of the keyboard hook, the process-enumeration filtering conditions and the injection target process name were not dynamically observed and are inferred only from decompilation.
