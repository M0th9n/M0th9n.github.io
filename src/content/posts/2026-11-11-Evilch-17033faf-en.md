> [!WARNING]
> **Verdict: malicious** · Family **Evilch** · Confidence **medium**
> 
> Aliases: Trojan.Win32.Evilch, Win32/GenKryptik, Evilch Loader
> 
> At the static level this is confirmed to be a Delphi resource loader: FormCreate reads the custom resource RTIRTWERQQ/TJERTIER6, and after de-interleaving and offset-varying XOR decryption obtains 202240 bytes of plaintext, in which a complete PE (stage2, sha256 1bec4642…) sits at offset 0x729. At runtime it dynamically resolves VirtualAlloc to allocate executable memory and jumps into the decrypted payload; in the dynamic sandbox this payload was implanted into svchost.exe(1304), after which svchost issued a complete HTTP GET to a Google Drive download address. Multiple independent evidence items jointly support the malicious loader/downloader chain verdict.

## Behavior Analysis

**7** behaviors in total, each with attached evidence; **5** are statically available and **2** were obtained through dynamic analysis.

### 1. Decrypt embedded resource

`T1027.009` · Confidence **high** · Static

FormCreate reads the 203508-byte resource of type RTIRTWERQQ and name TJERTIER6 from its own PE; it de-interleaves by skipping 2 bytes out of every 0x140 bytes, then applies (value + offset) XOR (0x8a726 + offset) to each double word, yielding 202240 bytes of plaintext with a complete PE at offset 0x729.

> **Evidence**: FormCreate VA 0x4c93ec; TResourceStream/FindResourceA helper VA 0x41dcac; decrypted stage2.exe sha256 1bec4642…
> 
> **Source**: `ref:60853d38ea` · `ref:12e7abc1c3` · `ref:52cb7475fa` · `ref:d327800c85`

### 2. Memory-load second stage

`T1620` · Confidence **high** · Static

Dynamically resolves VirtualAlloc through GetModuleHandleA/GetProcAddress, allocates memory with PAGE_EXECUTE_READWRITE, writes the decrypted content into it, and jumps to execute; the payload never touches disk, which makes this reflective/memory loading.

> **Evidence**: inside FormCreate VA 0x4c93ec, GetProcAddress("VirtualAlloc"), call arguments include 0x40, and at the end parameters are pushed and ret enters the code in the buffer
> 
> **Source**: `ref:60853d38ea` · `ref:52cb7475fa`

### 3. Implant into svchost process

`T1055.012` · Confidence **high** · Dynamic

After the dynamic run, a 0x33000-byte PE image with MEM_PRIVATE and protection 0x40 (PAGE_EXECUTE_READWRITE) appeared at 0x2e70000 in svchost.exe (PID 1304); memory forensics judged that the original image had been replaced and an implanted PE was present, and the dump and the decrypted stage2 agree on about 90% of double words per section (differences come from relocations).

> **Evidence**: memory record: pid 1304 module 0x2e70000 size 0x33000, mapping MEM_PRIVATE, protection 0x40, replaced=1, implanted_pe=1; dump and stage2 .text agree on 29256/32423 double words
> 
> **Source**: `ref:6a866ea67e` · `ref:fc319d58f3`

### 4. Outbound to Google Drive

`T1105` · Confidence **high** · Dynamic

The implanted svchost.exe (1304) resolves drive[.]usercontent[.]google[.]com and issues a complete HTTP GET /download?id=1YBVID…; the request carries a browser-style Accept header and Accept-Language: ru-RU,ru;q=0.9,en;q=0.8.

> **Evidence**: network simulation log: DNS for drive[.]usercontent[.]google[.]com, followed by GET /download?id=1YBVID…, Host: drive[.]usercontent[.]google[.]com; second-stage decompilation 0x401975 uses InternetOpenA/InternetConnectA/HttpSendRequestA
> 
> **Source**: `ref:9d45b8c02e` · `ref:d0c4146648` · `ref:b7e314ded8`

### 5. Masquerade as update service

`T1036` · Confidence **medium** · Static

The payload hardcodes strings such as updateSW, /service, and SUB=, and initiates downloads with common browser request headers, appearing externally as software update/service component traffic to reduce detectability.

> **Evidence**: stage2 string offsets 0x2919c "updateSW", 0x29218 "/service", 0x29224 "SUB="; network request headers match those of a browser
> 
> **Source**: `ref:6479e72f30` · `ref:9d45b8c02e`

### 6. Delay to evade the sandbox

`T1497.003` · Confidence **high** · Static

FormCreate first calls Sleep(0x1479≈5.2 seconds), then runs a loop of 0x1ef6154 no-op DeleteDC(0) calls to stall execution before starting decryption and the jump; at the beginning it also calls GetMessageExtraInfo to probe the message environment.

> **Evidence**: FormCreate VA 0x4c93ec: push 0x1479; call Sleep(0x40d670); mov esi,0x1ef6154 loop call DeleteDC(0x406db8); 0x407110 GetMessageExtraInfo
> 
> **Source**: `ref:251822b015` · `ref:0ffe1ac024` · `ref:60853d38ea`

### 7. Manual PE mapping capability

`T1620` · Confidence **medium** · Static

The second stage contains manual PE mapping error strings such as "DOS header is not valid!", "Signature != IMAGE_NT_SIGNATURE!", "Section alignment invalid!", and "Error protecting memory page", and imports VirtualAlloc/VirtualProtect, giving it the ability to reflectively map downloaded content as a PE.

> **Evidence**: stage2 strings and imports: VirtualAlloc/VirtualProtect, PE mapping error messages
> 
> **Source**: `ref:2bb854e99a` · `ref:2fc3e62132`

## Do Not Misjudge

:::important
The following conclusions are **easy to misjudge**; keep them in mind when citing this report.

- Do not judge it as ransomware because of VT's "cryp" tag: the sample does not encrypt user files; it is actually a resource decryption loading and download chain.
- Do not treat the Google Drive download address as an interactive C2 panel: only one payload download request was dynamically observed, with no task delivery or back-channel seen.
- Do not judge it as legitimate software merely because the file carries a 360 code-signing certificate: the Authenticode digest and certificate chain validity were not verified this time.
- No file drops, registry persistence, service creation, or scheduled task creation were observed this time; do not fabricate corresponding host IOCs on that basis.
:::

## Analysis Method and Limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | Yes (stage2 `1bec46428cbd7887a6e17b51610876330daccdcb62c367520078ae965a9c2825`) |

**Limitations and pending verification**

1. The outer file carries a 360 code signature and a Symantec timestamp; this time only their presence was recorded, without verifying the digest or certificate chain validity.
2. The decrypted second stage was obtained and compared, but the third-stage content it downloaded was not successfully retrieved (the network simulation returned a fake response), so the nature of the third stage is unconfirmed.
3. No file drops, registry writes, service creation, or scheduled task creation were observed, so host_iocs is empty.
4. APIs such as CryptAcquireContextW/CryptDecrypt appear only as imports, and their specific use was not confirmed in the call chain or dynamic events.
5. The dynamic sandbox was a single run, and network sessions were captured through simulation in an isolated environment, which does not represent real server responses; the C2 port is recorded as 443 per observation.
