> The sample is a 32-bit ARM ELF packed with UPX 3.96 (LZMA) on the outside; static unpacking yields an approximately 560KB statically linked image. The image contains a complete IoT botnet implementation: hardcoded C2 77.239.124[.]167 with HTTP/HTTP2 masquerading, telnet weak-password brute force with self-copy download-and-execute, multi-layer DDoS attacks (udp/ack/stomp/hold/tcpkill, raw-socket IP_HDRINCL, SSDP reflection), multi-path boot persistence, watchdog and firewall takeover, sensitive-file scanning and upload, and framebuffer/lock-screen scareware modules. All of the above capabilities are directly evidenced by decompilation and string cross-references; assessed as malicious.

## Behavior Analysis

**12** behaviors in total, each backed by evidence, and all obtained statically.

### 1. Self-extract UPX payload

`T1027.002` · Confidence **High** · Static

The entry point is a self-extracting stub: it opens /proc/self/exe, mmaps and decompresses the embedded image with LZMA, mprotects it executable and jumps to the original entry (UPX 3.96).

> **Evidence**: "$Info: This file is packed with the UPX executable packer" @0x346ee, "$Id: UPX 3.96" @0x3473d, "/proc/self/exe" @0x34868, mmap2/mprotect svc sequence in the entry stub at 0x43cf4
> 
> **Source**: `ref:6e5ee58286` · `ref:8defb3a1b2` · `ref:9049663e2a`

### 2. Callback to hardcoded C2

`T1071.001` · Confidence **Medium** · Static

Resolves the hardcoded address 77.239.124[.]167 with inet_addr, builds sockaddr_in via htons(80) and calls connect, serving as the default command/drop host; it can be overridden by environment variables such as SUPERIOR_DROP_IP/PORT.

> **Evidence**: String 77.239.124[.]167 @0x6a185; 0x3e484 mov r0,#0x50 → bl htons → strh sin_port; 0x3e498 inet_addr(IP) → connect(0x51b94)
> 
> **Source**: `ref:7d19c43be9` · `ref:05c7977d01` · `ref:13d4263eb2`

### 3. Browser-like HTTP2 traffic

`T1071.001` · Confidence **High** · Static

Masquerades as a normal browser with hxxps://%s/, GET %s HTTP/1.1, Upgrade: websocket, PRI * HTTP/2.0, multiple Chrome/Edge/Firefox UA versions, sec-ch-ua and sec-fetch-* headers, and exchanges commands/results through random paths /l/%08x and /o/%08x.

> **Evidence**: "GET %s HTTP/1.1" @0x69e6a, "PRI * HTTP/2.0" @0x697f0, "/l/%08x" @0x69e16, "/o/%08x" @0x69e1e, UA table from 0x66562
> 
> **Source**: `ref:57bdce6184` · `ref:7d19c43be9` · `ref:f91c75896e`

### 4. Telnet brute-force self-replication

> **Evidence**: Password table @0x6b0f7-0x6b1cb; SELFREP download commands @0x6adb8, @0x6ae57, @0x6aede, @0x6af44, @0x6afb2, @0x6b01c

## What Not to Assume

:::important
The following conclusions are **easy to misjudge**; keep this in mind when citing the report.

- Do not assess it as ransomware: its framebuffer/lock screen is only a scareware display; the binary contains no file-encryption or key-exchange logic.
- Do not treat the UPX shell as the only characteristic: the unpacked native code includes DDoS, telnet self-replication and persistence, making it a full botnet rather than an ordinary packed program.
- Do not claim a real C2 session was confirmed: 77.239.124[.]167:80 was recovered only from static constants and connect construction code, with no request/response obtained.
- Do not claim the sample was successfully detonated: the 32-bit ARM sample failed to start in the dynamic environment, and no process, file or network event was observed.
- Do not apply Windows-side IOCs: the sample targets Linux/Android/embedded devices and has no registry, Windows services or mutex objects.
:::

## Analysis Method and Limitations

| Item | Content |
|:--|:--|
| Analysis method | Static decompilation (no runtime behavior obtained) |
| Unpacking | Yes (stage2 `4b3b22242f23c618910f80382bc4a963aa435d5eb9814f5d6de13bbf3c569ac7`) |

**Limitations and items to verify**

1. The sample is 32-bit ARM; both the hardened dynamic instance and cross-architecture emulation returned detonator failures, so no runtime network/file/process events were obtained and the runtime behavior has not been validated by execution.
2. The C2 host, port and URI are all statically recovered: 77.239.124[.]167 also serves as the default drop host, and which path carries the command channel is inferred from constants and call order, marked pending_dynamic_verify.
3. Unpacking is a static byte-level recovery (UPX 3.96 LZMA) without executing the original entry; consistency between the unpacked image and running the original sample was not dynamically confirmed.
4. Many 1.2.3[.]4, mirai-c2[.]example[.]com, 127.0.0[.]1 and similar strings in the image are only help/sample text and should not be treated as real IOCs.
5. The family name "Superior" comes from the sample's self-identification strings and Mirai-style code characteristics; it lacks independent naming corroboration from vendor engines/YARA and is marked uncertain.
