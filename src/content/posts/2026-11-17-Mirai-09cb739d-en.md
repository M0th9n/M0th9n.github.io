> [!WARNING]
> **Verdict: malicious** · family **Mirai** · confidence **high**
> 
> Aliases: Aesky, Mirai botnet, ELF Mirai
> 
> The sample is a statically linked, symbol-stripped 32-bit ARM ELF; the main function (VA 0x9900) implements C2 callback, binary command parsing and attack dispatch, and retains the full Mirai-family code set: string-table obfuscation, a 256-connection-table Telnet scanner, /bin/busybox competitor cleanup, raw-socket SYN flood and HTTP flood. After actual execution in an isolated instance, the sample printed the Aesky banner, changed its process name with prctl(PR_SET_NAME), repeatedly connected to 5.39.10[.]241:9931 (returning ENETUNREACH without network) and probed multiple watchdog devices, demonstrating clear DDoS botnet functionality.

## Behavior analysis

There are **9** behaviors in total, each backed by evidence; **6** are statically obtainable and **3** were obtained through dynamic analysis.

### 1. Print banner and spoof process name

`T1036` · confidence **high** · dynamic

After startup it writes the Aesky banner to standard output (write(1,"Aesky\n",6) and write(1,"\n",1)) and calls prctl(PR_SET_NAME,"aaaa") to change the process name to a meaningless short string, concealing the bot's identity.

> **Evidence**: main @ VA 0x9900 calls write/prctl; dynamic write(1,"Aesky\n",6) ret=6, prctl(PR_SET_NAME,"aaaa") ret=0
> 
> **Source**: `ev-000004` · `ev-000015` · `ev-000056`

### 2. Call back to hardcoded C2

`T1095` · confidence **high** · dynamic

It first uses a UDP connect to 8.8.8[.]8:53 together with getsockname to obtain the local egress IP (without sending a DNS query), then loops establishing TCP connections to 5.39.10[.]241:9931; failed connections are retried with 1-second/10-second backoff.

> **Evidence**: connect loop in main @ VA 0x9900; FUN_00009678 writes the sockaddr as inet_addr("5.39.10[.]241") and the table entry port before each connection; strace connect(0, {sin_port=htons(9931), sin_addr=5.39.10[.]241}) = ENETUNREACH
> 
> **Source**: `ev-000004` · `ev-000009` · `ev-000056`

### 3. Parse commands and dispatch attacks

`T1095` · confidence **high** · static

After receiving C2 data it parses it in a private binary format: the first 4 bytes are the target IPv4, followed by duration, target count, 5 bytes per target (4-byte address + mask) and option TLVs, then hands off to the attack dispatch function to start the corresponding flood threads.

> **Evidence**: FUN_000083cc parses *param_1 / param_1[1] / the count at offset 5 and 5-byte target records, then calls FUN_00008268 at the end to dispatch
> 
> **Source**: `ev-000007`

### 4. Raw-socket SYN flood

`T1498.001` · confidence **high** · static

Creates an AF_INET/SOCK_RAW/IPPROTO_TCP socket and sets IP_HDRINCL, manually fills a 0x28-byte TCP header with random source addresses/ports, and sends SYN packets to targets in bulk to carry out reflection/spoofed-source flooding.

> **Evidence**: FUN_00008dfc: socket(2,3,6), setsockopt(3), build a 0x28-byte header and sendto in a loop; random numbers come from the xorshift in FUN_0000a254
> 
> **Source**: `ev-000002` · `ev-000003`

### 5. HTTP flood masquerading as a browser

`T1498.001` · confidence **high** · static

A built-in HTTP flood template sends GET / HTTP/1.1, Host: %s and Chrome/120 User-Agent, Accept and other headers, and parses Content-Length/Transfer-Encoding/Set-Cookie/Location fields in responses to maintain the connection and subsequent requests.

> **Evidence**: FUN_00008c9c calls FUN_0000820c(…, DAT_00008df0=HTTP template) and FUN_0000dbcc; the template string is at VA 0x18AA0
> 
> **Source**: `ev-000005` · `ev-000001`

### 6. Telnet weak-credential brute force

`T1110.001` · confidence **high** · static

Maintains a 0x100-entry connection table and uses raw sockets to scan 23/tcp; on a hit it tries the built-in usernames/passwords (root, anko, hunt5759, telnet, default, password, admin, vizxv, support, ko0admin, 12345, user) to log in, and recognizes shell/enable/system prompts.

> **Evidence**: FUN_0000ab4c allocates a 0x100*0x120 connection table, raw socket(2,3,6), destination port 0x1700 and table-entry credentials; the string table contains root/vizxv/ko0admin and shell/enable/system
> 
> **Source**: `ev-000010` · `ev-000001`

### 7. Kill competing malicious processes

`T1489` · confidence **high** · static

Initializes a table of about 40 competing malicious process names/ports, and at runtime calls /bin/busybox ps to enumerate processes and /bin/busybox kill -9 to terminate competing bots holding the same port or bearing the same name, monopolizing the device.

> **Evidence**: FUN_0000c360 fills the {ptr,len} process-name table entry by entry (including /bin/busybox ps, /bin/busybox kill -9), registered in main as a cleanup callback
> 
> **Source**: `ev-000008` · `ev-000001`

### 8. Disable the hardware watchdog

`T1562.001` · confidence **high** · dynamic

Enumerates /dev/watchdog, /dev/misc/watchdog, /dev/watchdog0, /dev/FTWDT101_watchdog, /sbin/watchdog, /etc/watchdog and other devices/files, opens them with open(O_RDWR) and then loops ioctl(WDIOC_GETTIMEOUT/SETTIMEOUT, 0x80045704/0x80045705) to prevent the device from rebooting on watchdog timeout, keeping the bot resident.

> **Evidence**: FUN_000096c0 opens table entries 0x26-0x2e and calls FUN_0000d3dc(fd,0x80045704/0x80045705) on the fd; strace observed openat("/dev/FTWDT101_watchdog", O_RDWR) and others
> 
> **Source**: `ev-000013` · `ev-000056` · `ev-000001`

### 9. Read /proc to probe the environment

`T1082` · confidence **medium** · static

Reads /proc/stat, /proc/cpuinfo, /sys/devices/system/cpu, /proc/net/route, /proc/net/tcp, /etc/resolv.conf to obtain CPU/memory, routing and established-connection information, used to choose the number of attack threads and avoid reinfection.

> **Evidence**: the string table contains /proc/stat, /proc/cpuinfo, /sys/devices/system/cpu, /proc/net/route, /proc/net/tcp, /etc/resolv.conf, referenced by the scanner/watchdog logic
> 
> **Source**: `ev-000001` · `ev-000010`

## Do not misjudge

:::important
The following conclusions are **easy to misjudge**; please note them when citing this report.

- Do not report it as ransomware or an infostealer: the sample has no file encryption, browser credential or user-data exfiltration code.
- Do not claim the C2 is confirmed online or that a session was successfully established: the isolated instance has no external network, and only connect attempts returning ENETUNREACH were observed.
- Do not claim systemd/rc boot autostart or service installation exists: only watchdog device operations were seen, with no persistence file writes.
- Do not claim it can download follow-up payloads: no wget/tftp/curl download commands appear in the string table.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis (Linux sample) + static decompilation |
| Unpacking | No |

**Limitations and pending verification**

1. The isolated instance is an unshare -n network-less environment; the C2 only shows connect attempts (ENETUNREACH), so c2/config are recorded as static throughout and pending_dynamic_verify is retained.
2. The ARM32 sample was run under qemu-user in user mode; system call behavior is observable, but there are differences from real IoT device kernels/drivers (e.g. the watchdog and FTWDT101 devices do not exist).
3. The string table uses multi-byte XOR that changes by key position; some long strings (download/control commands) could not be fully recovered, and capability judgments rely on the recovered code paths.
4. Actual DDoS traffic and Telnet brute-force traffic were not observed: this requires the C2 to deliver attack commands or an externally reachable target, which the current environment does not provide.
