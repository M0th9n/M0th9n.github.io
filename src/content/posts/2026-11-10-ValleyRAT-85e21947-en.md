## Behavior analysis

**10** behaviors in total, each backed by evidence; **4** are statically available and **6** were obtained through dynamic analysis.

### 1. Self-extracting dropped payload

`T1027.009` · Confidence **high** · static

The sample is a 7-Zip self-extracting archive (the valid PE is only 187904 bytes; the rest is SFX configuration and the 7z stream); per the configuration InstallPath="%TEMP%" it drops En_Bu.exe, krpt.dll, eventlib.map, proxy_server.pdb, and the VC runtime libraries, and launches %TEMP%\En_Bu.exe via RunProgram.

> **Evidence**: offset 187907: ;!@Install@!UTF-8! InstallPath="%TEMP%" RunProgram="\"%%T\\En_Bu.exe\""; from offset 188228 is the 7z stream; dropped files confirmed by system telemetry
> 
> **Source**: `ev-000019` · `ref:1f16ffc385` · `ref:7973dcf12d`

### 2. White-plus-black sideloading of krpt.dll

`T1574.002` · Confidence **high** · static

En_Bu.exe is a legitimate WPS PDF file (wpspdf.exe, 12.9.0.21549) with a valid Zhuhai Kingsoft signature, and its import table statically references krpt.dll!?_force_link_krpt in the same directory; the krpt.dll in that directory is unsigned yet exports same-named _krpt_* functions, so malicious logic executes on load.

> **Evidence**: En_Bu.exe import table dll=krpt.dll, symbol=?_force_link_krpt@@YGXXZ; signer subject CN=Zhuhai Kingsoft Office Software Co., Ltd.; krpt.dll exports 7 _krpt_* functions and has no security directory
> 
> **Source**: `ref:b78768e0b4` · `ref:56a49a22d5` · `ref:c4fc6f8eb8` · `ref:8c7ff304fa`

### 3. Copy to ProgramData and restart

`T1036.005` · Confidence **high** · dynamic

En_Bu.exe under %TEMP% copies itself along with krpt.dll, msvcp140.dll, ucrtbase.dll, and vcruntime140.dll to C:\ProgramData\logadapter\, then restarts the process from that directory copy, forming a stable foothold.

> **Evidence**: system telemetry: Image=C:\Users\analyst\AppData\Local\Temp\En_Bu.exe (pid 800) creates C:\ProgramData\logadapter\En_Bu.exe / krpt.dll / msvcp140.dll / ucrtbase.dll / vcruntime140.dll; subsequently pid 2480 Image=C:\ProgramData\logadapter\En_Bu.exe
> 
> **Source**: `ref:7973dcf12d` · `ref:31c6887c0a`

### 4. Create a scheduled task for persistence

`T1053.005` · Confidence **high** · dynamic

The ProgramData copy (pid 2480) writes C:\Windows\Tasks\sys_webhook_net20_rc.job, and the Task Scheduler service then creates C:\Windows\System32\Tasks\sys_webhook_net20_rc, achieving boot-time persistence via a scheduled task.

> **Evidence**: system telemetry T1053: pid 2480 creates C:\Windows\Tasks\sys_webhook_net20_rc.job; svchost.exe(1260) creates C:\Windows\System32\Tasks\sys_webhook_net20_rc
> 
> **Source**: `ref:7973dcf12d`

### 5. Drop the EZ-Play stage-two host

`T1036.005` · Confidence **high** · dynamic

The ProgramData copy drops C:\Users\<user>\AppData\Local\PicoInterf.exe (a vendor-signed legitimate file, described as EZ-Play maintenance tool, 8.0.1[.]2) and launches it immediately as the host process for the next-stage malicious code.

> **Evidence**: system telemetry Process Create pid 8044 Image=C:\Users\analyst\AppData\Local\PicoInterf.exe, Company=VSO Software SARL, Description=EZ-Play maintenance tool, FileVersion 8.0.1[.]2; parent process is C:\ProgramData\logadapter\En_Bu.exe
> 
> **Source**: `ref:31c6887c0a` · `ref:7973dcf12d`

### 6. Replace the in-process PE module

`T1055.012` · Confidence **high** · dynamic

Inside the PicoInterf.exe process at 0xd00000 there is a PE module of size 0xF0000 whose DOS/NT headers, section table, and entry point have all been rewritten (is_pe_replaced=1), inconsistent with the original file; meanwhile ntdll shows 3 code patches and the main module 1346 patches, indicating in-process module replacement/injection.

> **Evidence**: memory scan: module=0xd00000 size=f0000 is_pe_replaced=1 dos_hdr_modified=1 nt_hdr_modified=1 ep_modified=1 sec_hdr_modified=1; ntdll patches=3; 400000 patches=1346
> 
> **Source**: `ref:3e668c9581` · `ref:5b310e40dc` · `ref:f11d321c52`

### 7. Send back a host reconnaissance beacon

`T1082` · Confidence **high** · dynamic

A plaintext JSON beacon appears in process memory, collecting the computer name, username, Windows version, memory, CPU core count, UAC status, antivirus status (Windows Defender(OFF)), and monitor resolution and refresh rate, along with version 0.1.32, buildId main, sid VUSURWIV, and connection ports cp=3333/dp=3334.

> **Evidence**: plaintext in memory: {"computer":"DESKTOP-7QK4M2P","user":"analyst","av":"Windows Defender(OFF)","ver":"0.1.32","cp":3333,"dp":3334,"sid":"VUSURWIV","monitors":[{"name":"\\.\DISPLAY1","width":1371,"height":853,"rate":64}]}
> 
> **Source**: `ref:960a514dea` · `ref:d2ecc1659d`

### 8. Periodically reconnect to C2 with encryption

`T1573.001` · Confidence **high** · dynamic

After resolving new-label[.]club, PicoInterf.exe periodically connects to 3333/TCP and sends encrypted binary data (about once every 30-45 seconds, observed 4 times); no server response was seen.

> **Evidence**: network monitoring: Dns query new-label[.]club (pid 8044) → 192.0.2[.]123; TCP 3333 at 04:25:56 / 04:26:39 / 04:26:44 / 04:27:24, raw TCP hex payloads recorded
> 
> **Source**: `ref:7d133558de` · `ref:7973dcf12d` · `ref:cdb2eb0aef`

### 9. Built-in backup C2 domain table

`T1008` · Confidence **medium** · static

Four backup domains exist in process memory — ew-label[.]club, ew-zone[.]club, ew-craft[.]ink, ew-works[.]cc — used on the same port as the primary domain, forming backup channels.

> **Evidence**: contiguous strings from 0x40d33c in memory: ew-label[.]club / ew-zone[.]club / ew-craft[.]ink / ew-works[.]cc
> 
> **Source**: `ref:741ecae710` · `ref:d2ecc1659d`

### 10. Encrypted containers disguised as debug files

`T1027.013` · Confidence **medium** · static

The package's eventlib.map (6570502 bytes, entropy 7.94) and proxy_server.pdb (121905 bytes, entropy 6.63) are both high-entropy encrypted/compressed containers whose filenames masquerade as a linker map and a debug symbol file; krpt.dll's .data section embeds these two filenames.

> **Evidence**: eventlib.map entropy 7.941, proxy_server.pdb entropy 6.628; krpt.dll file offset 61679 (rva 0x112EF) 'eventlib.map', offset 60930 (rva 0x11002) UTF-16 'proxy_server.pdb'
> 
> **Source**: `ev-000019` · `ref:adf64dd640` · `ref:0b2e3aa362`

## What not to claim

:::important
The following conclusions are **easy to misinterpret**; please note them when citing this report.

- Do not treat En_Bu.exe / PicoInterf.exe as malicious in-house programs: the former is a legitimate WPS PDF file with a valid Kingsoft signature, the latter an EZ-Play maintenance tool signed by VSO Software; both are merely abused as loading hosts.
- Do not call it ransomware or a miner: no file encryption or ransom prompts (count 0) were seen in the sandbox, nor any mining pool/mining components.
- Do not claim browser credentials were stolen or keystrokes logged: the memory beacon reflects only host information collection, with no evidence of browser databases, keyboard hooks, or credential dumping.
- Do not write the C2 up as a fully established control channel: only DNS resolution and TCP outbound/uplink data were observed; no server response or complete request-response session was captured.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | Yes (stage2 `f8e409319baa062bbba8bb4114889d7e3dfc5774780aefc57a46f19ff407c18b`) |

**Limitations and open questions**

1. No C2 server response was captured, so the complete session and command set cannot be verified; all C2 entries are recorded as static + pending_dynamic_verify.
2. The encryption algorithm and plaintext contents of eventlib.map / proxy_server.pdb were not recovered, and their correspondence with the replaced module at 0xd00000 is unproven.
3. Family attribution is only a candidate (delivery chain and protocol features are consistent), without corroboration from YARA or multi-engine family labels.
4. No registry Run keys, service installation, or mutexes were observed; persistence evidence is the scheduled task sys_webhook_net20_rc and a randomly named environment variable pointing to C:\ProgramData\logadapter\En_Bu.exe.
5. No plaintext strings were found in the 0xd00000 module dumped from memory (likely encrypted/reflectively loaded), and no instruction-level recovery was performed; the beacon and domains come from other regions of the same process's memory.
6. Some system telemetry event timestamps in the sandbox deviate from the run time, so event order rather than absolute time was used as the criterion.
