> **Verdict: malicious** · family **Mikey** (uncertain) · confidence **medium**
> 
> Aliases: Zillber, ZillberReleyHost, Trojan.Mikey, Gen:Variant.Mikey
> 
> The sample was detonated for real in an isolated Windows sandbox and the full delivery chain was reproduced: the main process writes a copy of itself, ZillberReleyHost.exe, and launch.hta into C:\ProgramData\Package Cache\a42a0607dfa5684f\, opens a decoy document under %TEMP%, and the copy is then launched by mshta.exe; the copy process loads the .NET runtime, its memory shows forensic traces of amsi.dll!AmsiScanBuffer being rewritten and clr.dll patched in multiple places, and it carries complete browser-credential/cryptocurrency-wallet/Telegram data theft strings and injection primitives (VirtualAllocEx, WriteProcessMemory). Network monitoring recorded the process repeatedly initiating TCP connections to 45[.]192[.]211[.]63:56001 (also 56002/56003). On the static side there are further anti-analysis features: about 8.85 MB of high-entropy payload appended after the signature, only 41 kernel32 imports, and 15000+ obfuscation stub functions. The three corroborate each other, and both behavior and capability are backed by first-hand observation.

## Behavior analysis

**12** behaviors in total, each backed by evidence; **5** are statically obtainable and **7** were obtained through dynamic analysis.

### 1. Drop a copy of itself into ProgramData

`T1036.005` · confidence **high** · dynamic

The main process writes a copy of itself, ZillberReleyHost.exe, into the C:\ProgramData\Package Cache\a42a0607dfa5684f\ directory (in the process-creation audit record, the process that wrote this file is the analyzed sample).

> **Evidence**: file-creation audit event TargetFilename=C:\ProgramData\Package Cache\a42a0607dfa5684f\ZillberReleyHost.exe, Image=sample path, time 19:20:07
> 
> **Source**: `ref:5d490c05f3` · `ref:a2ff64564d`

### 2. Write an HTA and launch it with mshta

`T1218.005` · confidence **high** · dynamic

The sample writes launch.hta; mshta.exe then starts with that HTA as its argument and spawns the dropped ZillberReleyHost.exe (parent process mshta.exe), forming a system-binary proxy execution chain.

> **Evidence**: process-creation audit: mshta.exe "C:\ProgramData\Package Cache\a42a0607dfa5684f\launch.hta" (pid 7368), followed by ZillberReleyHost.exe (pid 7184, parent mshta.exe)
> 
> **Source**: `ref:5d490c05f3` · `ref:653e164355`

### 3. Open a decoy document as a diversion

`T1204.002` · confidence **medium** · dynamic

Executes cmd /c start "" %TEMP%\7ad2bd3a1687244f.docx, after which the WordPad process opens the document, presenting a normal document to the user while credentials are stolen.

> **Evidence**: process-creation audit: "C:\Windows\System32\cmd.exe" /c start "" "C:\Users\analyst\AppData\Local\Temp\7ad2bd3a1687244f.docx"; afterwards WORDPAD.EXE starts with that file as its argument
> 
> **Source**: `ref:5d490c05f3`

### 4. Load the .NET payload in memory

`T1620` · confidence **high** · dynamic

The copy process loads the CLR (mscorlib.ni.dll, clrjit.dll, clr.dll, etc.); a complete .NET string heap and metadata appear in the process memory, indicating the encrypted payload is decrypted in memory and handed to the .NET runtime for execution, with no original payload written to disk.

> **Evidence**: memory-forensics scan record lists runtime modules such as clr.dll/clrjit.dll/mscorlib.ni.dll; BSJB metadata signatures and .NET string heaps exist at multiple offsets in the same process memory
> 
> **Source**: `ref:246c08fcf4` · `ref:a2ff64564d`

### 5. Rewrite AmsiScanBuffer to bypass detection

`T1562.001` · confidence **high** · dynamic

In the copy process the body of the AmsiScanBuffer function in amsi.dll is rewritten (single-point patch), disabling script/assembly scanning, which is a typical AMSI bypass.

> **Evidence**: memory-forensics patch list: amsi.dll offset 0x5960 hits AmsiScanBuffer and its content was modified
> 
> **Source**: `ref:076676036d`

### 6. Patch clr.dll to weaken runtime monitoring

`T1562.001` · confidence **high** · dynamic

The same process applies 10 patches to the clr.dll code section (range 0x100e4-0x10cd8) to suppress detection/telemetry paths on the .NET runtime side.

> **Evidence**: memory-forensics patch list: 10 patch points in clr.dll, offsets 0x100e4/0x100f4/0x10108/0x10120/0x10150/0x10180/0x101b0/0x101e0/0x10210/0x10cd8
> 
> **Source**: `ref:076676036d`

### 7. Steal browser credentials and cookies

`T1555.003` · confidence **high** · static

The payload carries User Data paths for more than 40 Chromium/Gecko browsers plus targets such as Cookies, leveldb and Login Data, covering Chrome, Edge, Brave, Vivaldi, 360, QQBrowser, CocCoc, Torch and others, giving it the ability to export browser credentials in bulk.

> **Source**: `ref:a2ff64564d`

### 9. Enumerate antivirus and host fingerprint via WMI

`T1518.001` · confidence **high** · static

The payload queries SELECT * FROM AntiVirusProduct and Win32_Processor/Win32_DiskDrive/Win32_PhysicalMemory/Win32_OperatingSystem via WMI to collect host fingerprints such as antivirus names, CPU, disk serial numbers, memory and camera devices.

> **Evidence**: memory string heap: root\SecurityCenter2, SELECT * FROM AntiVirusProduct, Win32_Processor, ProcessorId, SerialNumber, SELECT Caption FROM Win32_OperatingSystem

### 10. Inject code by writing to memory

`T1055` · confidence **medium** · static

The payload retains primitives such as VirtualAllocEx / WriteProcessMemory / VirtualProtect / OpenProcess / GetDelegateForFunctionPointer (the strings are split into "Virtual "+"Alloc", "Write "+"Process "+"Memory"), giving it the ability to write code into other processes and execute it.

> **Evidence**: memory string heap: "Virtual " "Alloc", "Write " "Process " "Memory", "Protect", "Open " "Process", GetDelegateForFunctionPointer, kernel 32.dll
> 
> **Source**: `ref:a2ff64564d`

### 11. Beacon out to relay ports 56001-56003

`T1095` · confidence **high** · dynamic

After startup the dropped process repeatedly initiates TCP connections to 45[.]192[.]211[.]63:56001 and to local 127.0.0[.]1:56001/56002/56003, retrying at a fixed interval, consistent with a relay/callback channel; this observation captured no application-layer request or response.

> **Evidence**: network monitoring log: ZillberReleyHost.exe (7184) requested TCP 45.192.211[.]63:56001 and 127.0.0[.]1:56001/56002/56003 (one round about every 11 seconds from 19:20:57)
> 
> **Source**: `ref:d6e1a60078` · `ref:a2ff64564d`

### 12. Embedded scheduled-task persistence template

`T1053.005` · confidence **medium** · static

The payload contains a Register-ScheduledTask template: it registers a scheduled task as the current user with highest privileges, triggered repeatedly every 5 minutes, together with an encoded powershell -NoProfile -ExecutionPolicy Bypass -Enc command; this sandbox run did not observe the template actually landing (no corresponding registry/scheduled-task change events).

> **Evidence**: memory string heap: Register-ScheduledTask -TaskName '…' -Action (New-ScheduledTaskAction -Execute '…') -Trigger (New-ScheduledTaskTrigger -Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Minutes 5)) -RunLevel Highest

## What not to misjudge

:::important
The following conclusions are **easy to misjudge**; keep them in mind when citing this report.

- It must not be judged as ransomware: although the sample uses AES and hash derivation, both are used entirely for local encryption of payloads/configuration, and during the observation period there was no bulk file encryption, extension rewriting or ransom-note generation.
- It must not be claimed that a session with the C2 was established or data exfiltration completed: network monitoring recorded only TCP connection attempts, with no application-layer request/response or evidence of a completed upload; the relevant C2 fields remain pending dynamic re-verification.
- It must not be claimed that a scheduled task or registry autostart was written: runtime auditing found no scheduled-task creation or Run key change triggered by the sample, and the scheduled task exists only as a template in memory strings.
- The compilation activity of csc.exe / cvtres.exe must not be attributed to the sample: its timeline overlaps with the sandbox-side compilation of auxiliary components, and there is no parent-child process evidence, so it is activity of the analysis environment itself.
- It must not be asserted from the embedded Take-Two/Rockstar signature alone that the sample was published by that vendor: the certificate expired in 2013, and the signature data is immediately followed by about 8.85 MB of high-entropy appended data, structural features of signature theft/forgery.
:::

**Limitations and pending verification**

1. The C2 configuration (host 45[.]192[.]211[.]63, ports 56001-56003) comes from the process memory dump after the real detonation and matches the connection attempts observed on the network side, but this run captured no application-layer request/response, so per the standard it is still recorded as static with pending_dynamic_verify=true.
2. The appended region of about 8.85 MB has entropy close to 8.0, so the plaintext cannot be recovered statically; this run produced no decrypted payload hash for direct comparison, recovered.unpacked is recorded as false, and the second stage is registered only by the hash of the dropped copy.
3. Capabilities such as persistence, clipboard and injection come from strings and API combinations in the payload memory; these are capability assessments rather than actual execution evidence, and runtime auditing did not observe a scheduled task or autostart entry landing.
4. The memory forensics targeted the running copy process, and some .NET strings may come from shared libraries within the same runtime, so call-chain analysis is needed to further confirm attribution.
5. The loader itself is heavily obfuscated (15000+ stub functions, string encryption, only 41 kernel32 imports), and the decryption algorithm and control flow could not be recovered function by function; family attribution relies on external multi-engine naming, as there is no family-specific local marker.
6. The embedded code-signing certificate chain was not checked for validity (the certificate expired in 2013-09); this report only states its existence and structural position and does not assert its trustworthiness.
