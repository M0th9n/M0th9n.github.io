> This sample is a Mirai-family DDoS botnet program targeting ARM/Linux IoT devices. The static side confirms that it contains C2 domain resolution, C2 command dispatch, several DDoS flooding modules, boot autostart writes, self-copy into writable directories and process-name masquerading; during the real-machine run we directly observed the process renaming itself to uhttpd/lighttpd/telnetd/init, reading TracerPid from /proc/self/status and then killing itself and exiting, probing and copying itself into writable directories, and a provocative banner decrypted at runtime. Multiple attack/persistence components have corresponding evidence in both the code and the runtime.

## Behavior Analysis

There are **9** behaviors in total, each backed by evidence; **5** are statically available and **4** were obtained through dynamic analysis.

### 1. Resolves C2 domain

`T1071.004` · Confidence **medium** · Static

A built-in DNS client sends an A-record query for kiraservices[.]shop to 8.8.8[.]8:53; the resolution result is filtered against private/reserved addresses and then written into a CNC sockaddr_in, with port constant 0xDD19.

> **Evidence**: FUN_00011a7c@0x11A7C calls FUN_00014b34 for strings[0] and then FUN_000143a4@0x143A4; the latter builds a DNS packet and connects to 8.8.8[.]8:53 (observed via strace on a dynamically patched copy); port 0xDD19 is written in FUN_00011a7c.
> 
> **Source**: `ref:b4837bbf27` · `ref:d647dc955b` · `ref:4c3016f9af` · `ref:cf14fd930e`

### 2. Masquerades as system process

`T1036.005` · Confidence **high** · Dynamic

After startup it calls prctl(PR_SET_NAME) to change the process name to legitimate daemon names such as uhttpd/lighttpd/telnetd/init, and writes './prog' plus a random 10-character string to /proc/self/cmdline to overwrite the command-line display.

> **Evidence**: FUN_00014a3c@0x14A3C randomly picks a value from the name table at VA 0x26714, then prctl(0xF,...) and writes /proc/<pid>/cmdline; dynamic observation of prctl(PR_SET_NAME,"uhttpd"/"lighttpd"/"telnetd"/"init") and write("nwlrbbmqbh").
> 
> **Source**: `ref:b0a4a5c7e8` · `ref:70f27ba1cf` · `ref:04530f7762`

### 3. Exits on anti-debug

`T1622` · Confidence **high** · Dynamic

It reads /proc/self/status and parses TracerPid, together with ptrace(PTRACE_TRACEME) and checks of the LD_PRELOAD/LD_AUDIT/STRACE environment variables; once it detects being traced it calls exit(1) immediately and performs no further network communication.

> **Evidence**: FUN_000148cc@0x148CC opens /proc/self/status at VA 0x265DC and matches 'TracerPid:' at VA 0x265F0; at runtime this value was non-zero, followed by exit_group(1).
> 
> **Source**: `ref:41d039d86e` · `ref:04530f7762` · `ref:70f27ba1cf`

### 4. Writes boot autostart

`T1543.002` · Confidence **high** · Static

It derives a service name from its own path, writes /etc/systemd/system/<name>.service and runs systemctl enable, and also prepares an /etc/init.d/<name> script, appends a startup line to /etc/rc.local, and injects '@reboot <path> &' via crontab.

> **Evidence**: FUN_000132b8@0x132B8 references the systemd template VA 0x262D8, the system-call string VA 0x263A8, the init.d template VA 0x2645C, the cron template VA 0x26414 and rc.local VA 0x26514.
> 
> **Source**: `ref:54ac496355` · `ref:f7145f9559`

### 5. Self-copies to writable directories

`T1570` · Confidence **high** · Dynamic

It reads /proc/mounts to enumerate tmpfs/ramfs mount points and copies itself (/proc/self/exe) into writable directories such as /usr/local/bin, /tmp, /var/tmp and /dev/shm, then performs the persistence writes.

> **Evidence**: FUN_000132b8@0x132B8 reads /proc/mounts and probes /usr/local/bin, /usr/local/lib, /opt, /var/lib, /usr/bin, /usr/sbin, /lib, /usr/lib, /tmp, /var/tmp and /dev/shm with access(F_OK/W_OK); an identical access sequence was dynamically observed (returning EACCES due to non-root privileges).
> 
> **Source**: `ref:54ac496355` · `ref:70f27ba1cf` · `ref:cf14fd930e`

### 6. Receives C2 attack commands

`T1095` · Confidence **high** · Static

The main loop establishes a TCP connection to the CNC, reads commands by 2/4-byte lengths, recognizes the fixed 4-byte magic ('J', 0x8F, ',', 0xD1) and then dispatches the specific flooding function from the attack interface table.

> **Evidence**: In FUN_00011e94@0x11E94, after socket/connect it reads 4 bytes and compares them with 0x4A/0x8F/0x2C/0xD1, and on a hit calls FUN_00010aec to dispatch; contains Mirai-style private/reserved address filter constants.
> 
> **Source**: `ref:b4837bbf27` · `ref:54ac496355` · `ref:5f899c1fc9`

### 7. Launches DDoS floods

`T1498.001` · Confidence **high** · Static

Several built-in attack modules: TCP floods with HTTP/Discord request payloads, TCP SYN floods (spoofed source addresses), two UDP floods, and a game-server query flood using 'Source Engine Query' as the payload.

> **Evidence**: FUN_0000960c@0x960C (copies a 0xFA-byte HTTP payload and sendto), FUN_0000cc84@0xCC84 (spoofed-source TCP SYN), FUN_0000c4e4@0xC4E4 and FUN_0000c9e4@0xC9E4 (UDP floods), FUN_00009b88@0x9B88 (SYN probe with random IPv4); decrypted strings include 'Source Engine Query'.
> 
> **Source**: `ref:7721a077bd` · `ref:9386ba4aac` · `ref:2bfc7612e2` · `ref:4c3016f9af`

### 8. Decrypts built-in strings

`T1140` · Confidence **high** · Static

At startup it XOR-decrypts the built-in ciphertext in place by string-table index (80-byte key table, equivalent to the single byte 0x3A), yielding the C2 domain, the provocative banner, attack payloads and /proc paths, avoiding plaintext on disk.

> **Evidence**: FUN_00014c08@0x14C08 XORs strings dword by dword from the key table at .data VA 0x2FB1C; the literal at VA 0x14C00 points to both the string table 0x32ADC and the key table 0x2FB1C.
> 
> **Source**: `ref:61dbcddb94` · `ref:4c3016f9af`

### 9. Probes host environment

`T1082` · Confidence **high** · Dynamic

It reads /proc/mounts, /proc/cpuinfo, /proc/self/exe and /proc/<pid>/cmdline etc. to obtain mount points, CPU core count and process information, used to choose copy directories and masquerade names.

> **Evidence**: Dynamic observation of openat("/proc/mounts"), readlink("/usr/local/bin") and a series of access directory probes; on the static side FUN_000132b8 references /proc/mounts (VA 0x26284) and /proc/cpuinfo (VA 0x261C0).
> 
> **Source**: `ref:70f27ba1cf` · `ref:54ac496355`

## Do Not Misjudge

:::important
The following conclusions are **easy to misjudge**; please note them when citing this report.

- Do not conclude from the gateway.discord.gg and Discord/HTTP request-header strings alone that it uses Discord as C2: these bytes are TCP/UDP flood payload templates, and the actual C2 is kiraservices[.]shop.
- Do not conclude that it has Telnet weak-password worm propagation: no account dictionary, interactive login commands or wget/tftp download chain was found in the sample.
- Do not conclude that real outbound traffic occurred or a C2 session was established: the network was isolated; only a DNS resolution attempt to 8.8.8[.]8:53 was observed, returning ENETUNREACH at connect.
- Do not classify it as ransomware or an infostealer: no file encryption, credential reading or browser-data access logic was found.
:::

**Limitations and pending verification**

1. The network was isolated (unshare -n); no real TCP session with kiraservices[.]shop or 89.190.156[.]145 was obtained, the C2 and port are statically recovered, pending_dynamic_verify.
2. The sample's anti-debugging calls exit(1) immediately when TracerPid is non-zero, so the unmodified sample exits before connecting to C2; to observe the DNS resolution path, anti-debugging was skipped on a local lab copy and connect was made to return success directly, so the resulting network behavior cannot serve as evidence of a real session.
3. 89.190.156[.]145 exists only as a plaintext string alongside the C2 domain in the decrypted string pool; no code was located that writes its numeric value directly into a sockaddr, so its callback role is inferred.
4. Port constant 0xDD19 is written to sin_port as 16-bit little-endian and interpreted as 6621 in network byte order; if the sample intended a network-order constant the port could be 56601, so a byte-order ambiguity exists.
5. The ARM32 static glibc binary was run under qemu, and Ghidra's inference of some function boundaries and types is incomplete; no vendor naming, VT or public sandbox report was obtained, so family naming confidence is medium.
