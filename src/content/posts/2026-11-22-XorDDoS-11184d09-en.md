> **Verdict: Malicious** · Family **XorDDoS** (uncertain) · Confidence **Medium**
> 
> Aliases: Xor.DDoS, Linux.Xor.DDoS, Win.XorDDoS, W64 socket loader
> 
> The sample is a mere 3.5KB x64 remote-payload loader: its entry point walks the PEB and dynamically resolves WinSock/memory-execution APIs by ROR13 mixed hashing, checks %TEMP%\log_de.log as a single-instance marker, then connects to the hardcoded C2 163.7.0[.]131:8084, sends a 40-byte w64 beacon handshake, and decodes received data with single-byte XOR 0x99 into PAGE_EXECUTE_READWRITE memory and calls it directly. In the isolated dynamic environment the process was actually observed initiating that TCP connection and sending the complete handshake payload, showing clear remote payload delivery and in-memory execution capability.

## Behavior Analysis

**7** behaviors in total, each backed by evidence; **5** are static and **2** were obtained dynamically.

### 1. PEB Walk Resolves APIs

`T1027` · Confidence **High** · Static

The entry point reads the PEB through the GS segment, walks the export tables of loaded modules and resolves APIs by ROR13 mixed hashing (uppercase-folded module-name hash plus function-name hash), so WinSock and memory-execution functions never appear in the import table.

> **Evidence**: 0x14000145c hash-resolution function; 0x140001485 mov rax, gs:[0x60]; resolves 13 APIs including kernel32!LoadLibraryA, ws2_32!WSAStartup/WSASocketA/connect/send/recv, kernel32!VirtualAlloc
> 
> **Source**: `ref:451b2a25d9` · `ref:f68c86f86e` · `ref:8195817602` · `ref:eb79ec9386`

### 2. Check Temp-Directory Marker

`T1480` · Confidence **High** · Static

Uses GetTempPathA to obtain the temp directory, builds %TEMP%\log_de.log with wsprintfA, and calls _access(path,0) to check whether the file exists; if it exists it exits immediately, otherwise it continues the callback flow, providing single-instance/repeat-run protection.

> **Evidence**: 0x140001133 call GetTempPathA; 0x14000117f call wsprintfA("%s%s%s", %TEMP%, "log_de.", "log"); 0x140001188 call _access; if present jumps to 0x140001448 and exits
> 
> **Source**: `ref:eb79ec9386` · `ref:8195817602` · `ref:451b2a25d9`

### 3. Connect Hardcoded C2

`T1095` · Confidence **High** · Dynamic

After initializing Winsock it creates a TCP socket and connects to the hardcoded 163.7.0[.]131:8084; on connect failure it calls Sleep(10000) and retries, forming a fixed 10-second polling loop.

> **Evidence**: WSASocketA(2,1,6,...) around 0x1400012C9; 0x140001321 call connect; 0x140001311 Sleep(10000) retry; dynamic network monitoring records PID 6220 requesting TCP 163.7.0[.]131:8084 at 00:23:48
> 
> **Source**: `ref:7e588b637e` · `ref:25f6be2e3d` · `ref:451b2a25d9` · `ref:ecdad4c99b`

### 4. Send w64 Beacon

`T1082` · Confidence **High** · Dynamic

After a successful connection it sends a 40-byte fixed-format beacon: "w64 ", the network-order port 0x1F94 (8084), the dotted C2 address string "163.7.0[.]131" and zero padding, identifying the architecture and target to the C2.

> **Evidence**: Dynamic network monitoring captured RawTCP payload 77 36 34 20 20 20 1F 94 31 36 33 2E 37 2E 30 2E 31 33 31 00… (40 bytes total); statically corresponds to 10 send calls at 0x140001335–0x1400013E6
> 
> **Source**: `ref:25f6be2e3d` · `ref:7e588b637e` · `ref:ecdad4c99b`

### 5. Receive Remote Payload

`T1105` · Confidence **High** · Static

Once the RWX buffer is ready it loops recv on the socket, reading at most 0x64000 bytes at a time and appending the data in order to the VirtualAlloc buffer until the connection ends.

> **Evidence**: 0x1400013F9 VirtualAlloc(NULL, 0x1C9C380, 0x1000, 0x40); mov r12d,0x64000 around 0x1400013E8 and the recv loop; the dynamic C2 did not respond this run, so no stage2 was obtained
> 
> **Source**: `ref:eb79ec9386` · `ref:8195817602` · `ref:ecdad4c99b`

### 6. Single-Byte XOR Decryption

`T1140` · Confidence **High** · Static

Decodes the receive buffer byte by byte with XOR 0x99, accumulating the offset by received length and decrypting as data arrives, preparing for later direct execution.

> **Evidence**: 0x14000141F xor byte ptr [rcx+rdi], 0x99; block loop at 0x140001418–0x14000142E
> 
> **Source**: `ref:451b2a25d9` · `ref:eb79ec9386` · `ref:ecdad4c99b`

### 7. RWX In-Memory Payload Execution

`T1620` · Confidence **High** · Static

Stores the decoded data in PAGE_EXECUTE_READWRITE memory, closes the socket and directly calls the buffer base as a function, executing the remote payload inside the loader process.

> **Evidence**: 0x1400013F9 VirtualAlloc(...,0x40 PAGE_EXECUTE_READWRITE); after closesocket at 0x140001440 call rdi (buffer base)
> 
> **Source**: `ref:eb79ec9386` · `ref:8195817602` · `ref:ecdad4c99b`

## Common Misinterpretations

:::important
The following conclusions are **easy to misinterpret**; keep them in mind when citing this report.

- Do not assert from this loader alone that the sample itself has DDoS attack, persistence or lateral-movement capability: this analysis only observed the beacon handshake and did not obtain the second-stage payload; the final capability is determined by that payload.
- Do not treat %TEMP%\log_de.log as a log or configuration written by the sample: the code only checks its existence and exits if present; this run's telemetry also recorded no creation or writing of that file.
- Do not claim a complete session with the C2 or that commands were obtained: network monitoring captured only the 40-byte request, after which the connection timed out with no response.
:::

**Limitations and pending verification**

1. The C2 returned no data in the isolated network and the connection timed out after about 10 seconds, so no second-stage payload was obtained; the C2 entry is therefore marked as static recovery and remains pending dynamic confirmation, and final DDoS/persistence capabilities cannot be confirmed.
2. Family attribution is based on code-level same-family traits (%TEMP%\log_de.log marker, "w64 " handshake, XOR 0x99, 0x1C9C380 RWX buffer, 0x64000 recv chunking) compared with known same-family sample traits; lacking vendor naming/multi-engine results, name confusion and misattribution are possible.
3. The actual creator of %TEMP%\log_de.log was not observed in this analysis; the sample only checks existence, and it is presumed to be written by another component of the delivery chain or a later payload.
4. No file writes, registry, service, scheduled-task or certificate-store changes were observed; system telemetry contains no such events related to this sample.
