> [!WARNING]
> **Verdict: malicious** · Family **XMRig** · Confidence **high**
> 
> Aliases: CoinMiner, Monero miner, XMRig dropper
> 
> The sample is a PyInstaller-packaged Python loader: after launch it base64-decodes and execs a second-stage script, drops the embedded XMRig 6.22.3 as %TEMP%\svchost.exe, generates config.json containing a Monero wallet and pool address, and starts the miner in a hidden window; it then copies itself to the Startup folder as WinUpdateX64.exe for boot autostart, and polls taskmgr.exe every 3 seconds, terminating the miner as soon as Task Manager appears. In a real dynamic sandbox, the file drops above, the creation of the miner process, and the miner repeatedly resolving and connecting to the pool xmr-us-east1[.]nanopool[.]org:10343 were observed; this is resource-hijacking malware.

## Behavior Analysis

**8** behaviors in total, each backed by evidence; **4** are available statically and **4** were obtained through dynamic analysis.

### 1. Decode and exec stage-2 script

`T1027` · Confidence **high** · Static

The program's main script contains only an 11,409,492-character base64 constant; at runtime it base64-decodes it into 8,557,118 bytes of Python source and execs it, with all malicious logic hidden in stage 2 to evade static string detection.

> **Evidence**: co_consts[4] of the protected_launcher marshalled code is a 11409492-character base64 blob; after decoding, the first line of the source imports base64/json/os/subprocess, and the main logic is executed via exec
> 
> **Source**: `ev-000019`

### 2. Drop embedded miner to temp directory

`T1027.009` · Confidence **high** · Dynamic

Writes the 6,412,288-byte XMRig 6.22.3 (PE32+) embedded as base64 to %TEMP%\svchost.exe; if the file already exists, it is reused directly.

> **Evidence**: extract_xmrig writes %TEMP%\svchost.exe; dynamically, monitoring component EID11 02:12:51.579 TargetFilename=C:\Users\analyst\AppData\Local\Temp\svchost.exe (PID 5652); monitoring component scanned image C:\Users\analyst\AppData\Local\Temp\svchost.exe
> 
> **Source**: `ev-000020` · `ref:25d0e400da`

### 3. Self-copy into Startup folder

`T1547.001` · Confidence **high** · Dynamic

Copies the current executable to %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\WinUpdateX64.exe for logon autostart; no registry Run key, service, or scheduled task is used.

> **Evidence**: in runAtStartup, shutil.copy2(current_executable, Startup\WinUpdateX64.exe); monitoring component EID11 02:12:51.344 TargetFilename=...\Startup\WinUpdateX64.exe (Image=sample, PID 5652)
> 
> **Source**: `ev-000019` · `ref:25d0e400da`

### 4. Launch miner with hidden window

`T1564.003` · Confidence **high** · Dynamic

After generating config.json, starts %TEMP%\svchost.exe --config %TEMP%\config.json via subprocess.Popen, setting STARTF_USESHOWWINDOW+SW_HIDE and CREATE_NO_WINDOW and redirecting stdout/stderr to DEVNULL, so the miner runs with no window and no console output.

> **Evidence**: stage2 lines 129-151: startupinfo.dwFlags|=STARTF_USESHOWWINDOW; wShowWindow=0; creationflags=CREATE_NO_WINDOW; monitoring component EID1 CommandLine=C:\Users\analyst\AppData\Local\Temp\svchost.exe --config C:\Users\analyst\AppData\Local\Temp\config.json
> 
> **Source**: `ev-000019` · `ref:25d0e400da`

### 5. Connect to Monero pool and mine

`T1496` · Confidence **high** · Dynamic

The miner continuously connects to pool xmr-us-east1[.]nanopool[.]org:10343 (TLS) using the rx/0 (RandomX) algorithm and wallet 41dWwJp3...; in the sandbox the process repeats DNS resolution and TCP connections roughly every 30 seconds.

> **Evidence**: pools[0].url/user/pass in config.json; monitoring component EID22 QueryName=xmr-us-east1[.]nanopool[.]org (PID 4260, Image=%TEMP%\svchost.exe); network monitoring log: svchost.exe (4260) requested TCP 192.0.2[.]123:10343 (17 times from 02:12:55 to 02:16:59)
> 
> **Source**: `ev-000019` · `ref:914f881750`

### 6. Watch Task Manager and kill the miner

`T1562.001` · Confidence **high** · Static

A background daemon thread enumerates processes with psutil every 3 seconds; once taskmgr.exe is found running, it terminates and waits on the miner process, so the user does not see the mining load in Task Manager.

> **Evidence**: monitor_task_manager lines 165-187: process_iter(['name']) compared against 'taskmgr.exe', then miner_holder['proc'].terminate
> 
> **Source**: `ev-000019`

### 7. Delete dropped config file

`T1070.004` · Confidence **medium** · Static

Two seconds after the miner starts, it deletes %TEMP%\config.json, keeping the pool and wallet configuration only briefly in memory/on the command line, reducing forensic traces.

> **Evidence**: start_hidden_miner lines 153-156: os.remove(config_path) after time.sleep(2)
> 
> **Source**: `ev-000019`

### 8. Restart the miner process in a loop

`T1496` · Confidence **high** · Static

The main loop is while True: rebuild the config, start the miner, wait for it to exit, then sleep 10 seconds and relaunch, forming a self-healing mining watchdog.

> **Evidence**: stage2 lines 206-215: while True: create_config; start_hidden_miner; poll; time.sleep(10)
> 
> **Source**: `ev-000019`

## Do Not Misjudge

:::important
The following conclusions **are easy to misjudge**; note this when citing this report.

- Do not report it as an information stealer: the code only enumerates process names with psutil and does not read browser data, wallet files, the clipboard, or credentials.
- Do not report it as ransomware/wiper: there is no file encryption or user-data deletion anywhere in the flow; only its own temporary config file is deleted.
- Do not claim persistence via registry Run keys, services, or scheduled tasks: dynamic telemetry shows no new entries under HKCU\...\Run and no new services; persistence is achieved only through a file in the Startup folder.
- Do not claim a pool session was successfully established: only DNS resolution and TCP connection attempts to port 10343 were observed; no stratum/TLS login or share submission was obtained.
- Do not report it as a downloader that fetches payloads from the network: the miner binary is embedded in the sample itself as base64, and no download occurs during the drop.
:::

## Analysis Method and Limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | Yes (stage2 `55b25d5092bdd7b4d96518e2eacbae77d8381154ecd8c6cddb4aa8ae73851624`) |

**Limitations and pending verification**

1. On the pool side, only DNS resolution and TCP connection attempts to port 10343 were observed (no responder session), so C2's recoverability is recorded as static and pending_dynamic_verify=true.
2. The taskmgr.exe monitoring and the 10-second restart loop are on pending-trigger paths; no interactive Task Manager launch occurred within the observation window, so these judgments come from source code rather than runtime behavior.
3. No deletion event for config.json was captured (no corresponding file-deletion telemetry); this behavior is based on source-code logic.
4. For the embedded XMRig, only version resources and characteristic strings were compared; no same-origin comparison against the upstream official portable build's hash was performed, so it may be a recompiled or secondarily modified build.
5. The outer loader's UI imports (USER32/GDI32/GDI font drawing) come from PyInstaller bootstrap code, so the presence of a windowed interface cannot be inferred from them.
