Complete HTTP requests and responses were dynamically observed and the behavior chain is complete, so it is judged malicious.

## Behavior Analysis

There are **7** behaviors in total, each backed by evidence; **3** are static and **4** were obtained through dynamic analysis.

### 1. Disguised NSIS Installer

`T1027.009` · confidence **high** · static

The sample is a 32-bit NSIS installer shell; its version information uses random words (OriginalFilename: gersemis useful.exe, CompanyName: pianoernes beglor overpricing), and it extracts 17 files from its own container, about 24 MB in total after decompression.

> **Evidence**: static unpacking: 17 files/24 MB; version resources are random words; installer sections contain .ndata and $PLUGINSDIR
> 
> **Sources**: `ref:78bcc77f58` · `ref:85dc06669c` · `ref:4c59c3d78b`

### 2. Self-Replication into Multiple Processes

`T1036` · confidence **high** · dynamic

During real execution the first process (3240) spawns two same-hash child processes (1192, 2148), and 2148 further spawns same-hash process 980; the child processes' working directory is set to the random-word directory %USERPROFILE%\trinitrotoluene.

> **Evidence**: dynamic process telemetry: 3240→1192/2148→980, all four processes share the same SHA256 and the same image path, CurrentDirectory=C:\Users\analyst\trinitrotoluene
> 
> **Sources**: `ref:6c7f2844ab` · `ref:47a37752bb`

### 3. In-Memory Image Replacement Execution

`T1620` · confidence **medium** · dynamic

Memory forensics show that the DOS/NT/entry/section headers of the worker process's 0x400000 module were all rewritten (is_pe_replaced=1), the mapping source is marked as mshtml.dll, and a replacement module dump of about 18 MB was generated, consistent with module stomping/reflective loading execution.

> **Evidence**: memory forensics: headers_scan is_pe_replaced=1, dos/file/nt/ep/sec_hdr_modified=1; mapping_scan mapped_file=C:\Windows\SysWOW64\mshtml.dll
> 
> **Sources**: `ref:50bf7ca49b` · `ref:47a37752bb`

### 4. WinHTTP Callback Download

`T1071.001` · confidence **high** · dynamic

After resolving the domain braggoonbus[.]store, process 2148 uses a WinHTTP session to send GET /frakas/LPKNGH180.bin to port 443 with the UA spoofed as Firefox/157.0, and keeps the full request headers in memory.

> **Evidence**: dynamic network monitoring: GET /frakas/LPKNGH180.bin HTTP/1.1, Host: braggoonbus[.]store; a WinHTTP global session and the same request string appear in memory
> 
> **Sources**: `ref:559bfeb576` · `ref:ef050e31a3` · `ref:b1f0bdc305`

### 5. Ten-Second Timed Retry

`T1105` · confidence **high** · dynamic

After receiving a 32,768-byte application/octet-stream response, the sample repeatedly requests the same URL at about 10-second intervals until the observation window ends, indicating it keeps retrying after failing to validate the downloaded content.

> **Evidence**: dynamic network monitoring: GET about every 10 seconds from 00:10:40 to 00:12:33; in-memory response headers HTTP/1.0 200 OK / Content-Length: 32768
> 
> **Sources**: `ref:559bfeb576` · `ref:90b69ae9e1`

### 6. Self-Signed Certificate Disguise

`T1553.002` · confidence **high** · static

The PE security directory embeds a PKCS#7 signature; both the certificate subject and issuer are C=DE, O=Ryger, OU=pergamenian Nedbrydningerne Unspirit, CN=Ryger, i.e., a self-signed certificate used to masquerade as a trusted publisher.

> **Evidence**: PE Security directory RVA 0xF62A8; parsed certificate subject=issuer=CN=Ryger
> 
> **Sources**: `ref:07c4d75810` · `ref:aa09a0b820`

### 7. Decoy File Padding

`T1027` · confidence **high** · static

The installation package contains 3 normally parseable JPEG decoys, several text files of random dictionary words, and 6–8 MB large files filled with a single byte (0x05/0x95/0xb6/0x99), used to inflate volume, mimic normal installer content, and hinder analysis.

> **Evidence**: static unpacking: humoristiske.thu 8.5 MB, stathenrys.fal 8.3 MB, Kline107.rus 6.4 MB, Caprice.reh 240 KB are mostly single-byte padding; plus 3 JPEGs
> 
> **Sources**: `ref:78bcc77f58` · `ref:85dc06669c` · `ref:6c1f6fb148`

## Do Not Misjudge

:::important
The following conclusions **are easily misjudged**; please note them when citing this report.

- Do not claim the sample created services, scheduled tasks, or Run keys for persistence: HKCU/HKLM Run keys did not change after execution, and the service/task events in telemetry were all produced by the analysis facility.
- Do not claim the sample successfully downloaded or executed a stage-2 payload: the sandbox network only returned 32,768 bytes of placeholder data, the sample kept retrying, and the real .bin content was not obtained.
- Do not claim any data theft, ransomware, lateral movement, or DDoS capability: no credential access, file-walking encryption, SMB/WMI, or exfiltration behavior was observed.
- Do not assert anti-debugging or a specific API call chain based solely on strings such as GetProcAddress/IsDebuggerPresent/WinHTTP in memory; rely on actual calls and dynamic events instead.
:::

**Limitations and Pending Verification**

1. The sandbox network returned a fixed 32 KB fake response and no real server content was obtained, so the stage-2 payload's family, encryption method, and final capabilities cannot be determined.
2. No persistence, privilege escalation, lateral movement, or data exfiltration was observed; only downloader behavior is confirmed.
3. The family is a candidate (GuLoader/CloudEyE) and lacks corroboration from family hardcoded strings, YARA, or multi-engine naming; confidence is medium.
4. The NSIS headers use custom compression/obfuscation and the installation script could not be recovered, so the script layer's specific use of each decoy file cannot be confirmed.
5. Memory forensics show the 0x400000 module was replaced and its mapping source is anomalous, but most of the 18 MB replacement dump is zero-filled; the module-stomping conclusion should be interpreted cautiously together with more memory pages.
