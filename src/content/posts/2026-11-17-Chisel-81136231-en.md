## Behavior Analysis

There are **6** behaviors in total, each backed by evidence; **4** are available statically and **2** were obtained through dynamic analysis.

### 1. Listens on Port 8080

`T1090` · Confidence **high** · Dynamic

When started in server mode, it creates an AF_INET6 socket and listens on 0.0.0[.]0:8080, printing "server: Listening on hxxp://0.0.0[.]0:8080" to stderr and waiting for tunnel clients to connect.

> **Evidence**: server.(*Server).listener; strace listen(5,4096) + write(2,"server: Listening on hxxp://0.0.0[.]0:8080")
> 
> **Source**: `ev-000041` · `ev-000030`

### 2. Client Connects Out to Server

`T1071.001` · Confidence **high** · Dynamic

When running in client mode, it proactively initiates a TCP connection to the URL specified by the operator; after a failed connection it retries indefinitely with 2s/4s exponential backoff, giving the controlled endpoint outbound callback capability.

> **Evidence**: client.(*Client).connectionLoop; strace dial tcp 127.0.0[.]1:1 + "Retrying in 2s" / "Retrying in 4s"
> 
> **Source**: `ev-000042` · `ev-000058` · `ev-000059`

### 3. Built-in SOCKS5 Proxy

`T1090.001` · Confidence **high** · Static

In client mode it listens locally on 127.0.0[.]1:1080 as a SOCKS5 proxy (depending on github[.]com/armon/go-socks5), forwarding proxy traffic through the tunnel to the server-side network, forming an internal-network lateral entry point.

> **Evidence**: listening on 127.0.0[.]1:1080 (getsockname); socks remote description in --help; dependency github[.]com/armon/go-socks5
> 
> **Source**: `ev-000028` · `call:call_97566b21276b44b5a03457f0`

### 4. Supports Reverse Port Forwarding

`T1090` · Confidence **high** · Static

After the server enables --reverse, it can map a server-local port back to a host on the client side, achieving port forwarding from outside into the internal network; when not enabled, reverse requests are explicitly denied.

> **Evidence**: settings.Remotes.Reversed / tunnel.(*Tunnel).BindRemotes; string "Denied reverse port forwarding request, please enable --reverse"
> 
> **Source**: `ev-000028` · `call:call_97566b21276b44b5a03457f0`

### 5. TLS-Encrypted Tunnel

`T1573.002` · Confidence **high** · Static

Supports HTTPS/WSS transport and can use --tls-key/--tls-cert or automatic Let's Encrypt certificate issuance; tunnel payloads sit inside a TLS-encrypted channel, evading plaintext-based detection.

> **Evidence**: server.(*Server).tlsKeyCert / tlsLetsEncrypt; crypto/tls, crypto/acme and LetsEncrypt strings
> 
> **Source**: `call:call_97566b21276b44b5a03457f0` · `ev-000028`

### 6. TCP/UDP Multiplexing

`T1090` · Confidence **high** · Static

Multiplexes multiple TCP/UDP sessions over a single WebSocket tunnel and periodically probes with keep-alive, carrying multiple forwarding and proxy connections simultaneously.

> **Evidence**: tunnel.(*Tunnel).handleTCP / handleUDP / keepAliveLoop / (*udpChannel).encode
> 
> **Source**: `call:call_97566b21276b44b5a03457f0` · `ev-000028`

## Do Not Misjudge

:::important
The following conclusions **are easy to misjudge**; please note them when citing this report.

- It cannot be called a malicious sample with an implanted backdoor: no hardcoded C2, persistence mechanism, credential theft, or additional payload was found, and the code matches the upstream open-source project.
- It cannot be concluded that real outbound communication or a C2 session exists: the isolated environment has no network, all client-mode connection attempts failed, and no successful tunnel or data return was observed.
- It cannot be classified into specific malicious families such as ransomware, stealer, or miner: its behavior is a generic network tunnel and proxy, and the risk comes from how it is abused rather than built-in malicious logic.
:::

**Limitations and Pending Verification**

1. The execution environment has no network (separate network namespace); only local loopback connect attempts and network unreachable were seen, and no real C2 session or tunnel data transfer could be observed.
2. No built-in C2, key, or operator configuration was found; C2 parameters are supplied entirely via the runtime command line, so no specific C2-address-type IOC can be given.
3. Dynamic verification was completed only in a hardened Linux instance and does not cover behavioral differences in the tool's Windows build.
4. The Go binary is stripped, and function names come from gopclntab reconstruction; not every implementation path was verified by per-function decompilation.
5. Server mode was run only briefly to verify listening; no handshake or port-forwarding test with a real client was completed.
