> 
> Aliases: XorDDoS, XOR.DDoS, Linux.XorDdos, ELF/XorDdos
> 
> Full decompilation of the only business function, main, shows: it first checks /tmp/log_de.log for a single-instance decision, then connects to the hard-coded address 39[.]107[.]238[.]247:8726, sends an "l32 " handshake, creates an anonymous in-memory file (memfd_create) to receive and single-byte XOR 0x99 decrypt a second-stage payload, and finally executes it in memory via fexecve with argv[0]="[kworker/0:2]". This chain is a typical downloader/loader with no legitimate business functionality.

## Behavior analysis

**8** behaviors in total, each backed by evidence, and all are statically available.

### 1. Check single-instance marker

`T1480` · Confidence **high** · static

It calls access("/tmp/log_de.log") and, if the file already exists, exits directly with exit(0) to avoid running repeatedly on the same host.

> **Evidence**: 0x80486d2 push 0x8048a60 ("/tmp/log_de.log"); 0x80486d7 call access; 0x80486e1 jne 0x80486ed then exit(0)
> 
> **Source**: `ref:0928a185bd` · `ref:5b769f8d64`

### 2. Hard-coded C2 address and port

`T1095` · Confidence **high** · static

It copies the constant "39.107.238[.]247" into a stack buffer and builds a sockaddr_in: AF_INET, port 0x2216 (network order, i.e. 8726), preferring gethostbyname and falling back to inet_addr on failure.

> **Evidence**: 0x80486fa mov esi,0x8048a8c ("39.107.238[.]247"); 0x8048720 mov word [ebp-0x144a],0x2216
> 
> **Source**: `ref:0928a185bd` · `ref:5b769f8d64` · `ref:51533c95c9`

### 3. Reconnect to C2 in a loop

`T1095` · Confidence **high** · static

After socket(AF_INET,SOCK_STREAM,0) it sets TCP options; if connect fails it sleeps 10 seconds and retries indefinitely until the connection succeeds.

> **Evidence**: 0x804879d call connect; 0x80487ab push 0xa; 0x80487ad call sleep; 0x80487b5 jmp back to connect
> 
> **Source**: `ref:0928a185bd` · `ref:5b769f8d64`

### 4. Send l32 handshake

`T1095` · Confidence **high** · static

After connecting it sends, in order, the 6-byte magic "l32 ", the 2-byte network-order port, and a 0x20-byte host-name string, identifying itself to the C2 as a 32-bit Linux client.

> **Evidence**: 0x80487bb push 0x8048a70 ("l32 "); send(...,6); 0x80487e9 send(port,2); 0x80487f7 send(host,0x20)
> 
> **Source**: `ref:0928a185bd` · `ref:5b769f8d64` · `ref:02c1a889cc`

### 5. Create anonymous in-memory file

`T1620` · Confidence **high** · static

It uses syscall 356 (memfd_create) with the name "a" to create an anonymous in-memory file as the landing carrier for the second-stage payload, without touching disk.

> **Evidence**: 0x8048801 push 0x8048a77 ("a"); 0x8048806 push 0x164; 0x804880b call syscall
> 
> **Source**: `ref:0928a185bd` · `ref:5b769f8d64`

### 6. XOR-decrypts delivered payload

`T1140` · Confidence **high** · static

It loops on recv for up to 0x1000 bytes, XORs each byte with 0x99 and writes it to the memfd, until the peer closes.

> **Evidence**: 0x8048832 call recv; 0x8048846 xor byte ptr [edx+ecx],0x99; 0x8048859 call write
> 
> **Source**: `ref:0928a185bd` · `ref:5b769f8d64`

### 7. Executes masquerading as kworker

`T1036.005` · Confidence **high** · static

After closing the socket, it writes realpath(argv[0]) into the environment variable CWD, builds argv=["[kworker/0:2]",NULL], and calls fexecve to execute the decrypted second-stage payload from the memfd, with the process name masquerading as a kernel worker thread.

> **Evidence**: 0x804887e call realpath; 0x8048899 push 0x8048a79 ("CWD"); 0x80488b4 mov [ebp-0x1454],0x8048a7d ("[kworker/0:2]"); 0x80488c8 call fexecve
> 
> **Source**: `ref:0928a185bd` · `ref:7fb4fca440` · `ref:02c1a889cc`

### 8. Streams in the second-stage payload

`T1105` · Confidence **high** · static

Within a single TCP session it continuously receives data chunks delivered by the C2 and writes them to the memfd immediately, forming a receive-as-you-decrypt payload delivery channel.

> **Evidence**: 0x8048832 recv(...,0x1000) → 0x8048846 XOR → 0x8048859 write(memfd) loop
> 
> **Source**: `ref:0928a185bd` · `ref:5b769f8d64`

## Must not be misjudged

:::important
The following conclusions are **easy to misjudge**; keep them in mind when citing this report.

- Do not claim that a real C2 session was observed or that the second-stage payload content was obtained: the isolated environment has no external network, and the sample could not actually start, so the payload content is unknown.
- Do not classify it as ransomware or a credential stealer: the code contains no file-encryption, credential-collection or browser-data-reading logic.
- Do not claim persistence: the sample only checks /tmp/log_de.log, does not create that file, and does not write to cron, systemd, rc or shell configuration.
- Do not claim that it executed successfully on this host: this 32-bit i386 program failed to reach main in the isolated instance because /lib/ld-linux.so.2 was missing.
:::

## Analysis method and limitations

**Limitations and pending verification**

1. The isolated instance had no 32-bit runtime (/lib/ld-linux.so.2 missing), and both dyn_exec and qemu-user returned ENOENT at the exec stage, so runtime behaviors such as connect/handshake/XOR/second-stage execution could not be observed.
2. The C2 and configuration were recovered statically and are marked recoverability=static and pending_dynamic_verify=true per the rules; no request/response session was obtained.
3. The second-stage payload was not obtained (no C2 session), so its exact capabilities (DDoS command set, persistence, privilege escalation) cannot be confirmed.
4. Family attribution is based on code and protocol fingerprints (l32 magic, XOR 0x99, memfd_create+fexecve, [kworker/0:2] masquerade, linux_i386_tcp.c compilation unit), without vendor-engine or YARA cross-validation.
5. /tmp/log_de.log is only checked, never created, by this file; it is presumed to be written by another component of the delivery chain or an install script, which could not be confirmed.
