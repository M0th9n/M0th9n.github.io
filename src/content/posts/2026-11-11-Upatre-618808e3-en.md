> [!WARNING]
> **Verdict: malicious** · Family **Upatre** (uncertain) · Confidence **medium**
> 
> Aliases: Win32/Upatre, Upatre downloader, BFLH, Cryptodef
> 
> The PE32 GUI program statically imports only GUI/CRT functions, but after running it decrypts a loader of about 2.4KB at 0x4011F0 in the .text section: it dynamically resolves more than 30 APIs including WinINet, file and ShellExecuteW through LoadLibraryA/GetProcAddress, embeds 3 C2 IPs and tar download paths, and decompresses with RtlDecompressBuffer before dropping to disk and executing; in the dynamic sandbox the sample was also observed writing a copy of itself to %TEMP%\eilgx.exe and creating a child process to run it (the child's imphash is identical to the parent's, while sha256 differs). Static decryption and dynamic behavior together identify a malicious downloader/dropper.

## Behavior analysis

**9** behaviors in total, each with attached evidence; **7** of them are available statically and **2** were obtained through dynamic analysis.

### 1. Decrypt embedded payload at runtime

`T1027.013` · Confidence **high** · Dynamic

The 2496 bytes of high-entropy data starting at .text RVA 0x11F0 (entropy 7.87) are decrypted in place after running: at that location in memory, E8 00 00 00 00 5B 83 C3 09 E9 5F 02 00 00 and plaintext such as LoadLibraryA/GetProcAddress appear; memory forensics shows 42 code patches from 0x11F0–0x1B6C, indicating runtime self-decryption and code execution.

> **Evidence**: memory image vs disk file differ at 0x4011F0; memory bytes E8 00 00 00 00 5B 83 C3 09; 42 patch records (from 0x11F0, stride 0x3D)
> 
> **Source**: `ref:14797fbce1` · `ref:9528ce7b24` · `ref:7f440916cb`

### 2. Self-copy to temp directory and execute

`T1036.005` · Confidence **high** · Dynamic

In the sandbox the sample process (pid 7336) created and executed C:\Users\analyst\AppData\Local\Temp\eilgx.exe about 26 seconds after startup (pid 3516, parent 7336); the child's sha256=F686B251…9AA, md5=1CA92A02…4ABE differ from the parent, but the imphash is the same 9ca48999135432f56a673e3735586d87, indicating that what was dropped is a rewritten/repacked program of the same origin.

> **Evidence**: process-creation telemetry: image=C:\Users\analyst\AppData\Local\Temp\eilgx.exe, parent_pid=7336, hashes=MD5 1CA92A02…/SHA256 F686B251…/IMPHASH 9ca48999…
> 
> **Source**: `ref:0418b4d6ff` · `ref:2ca6d0917a`

### 3. Dynamically resolve system APIs

`T1027.007` · Confidence **high** · Static

The import table has only 46 GUI/CRT symbols (no network, no file, no process creation); the real capability depends on the string table in the decrypted loader, resolving more than 30 APIs such as LoadLibrary/file I/O/WinINet/ShellExecute through LoadLibraryA/GetProcAddress.

> **Evidence**: decrypted string table 0x4011FE LoadLibraryA, 0x40120B GetProcAddress, 0x40131B wininet.dll, 0x40138E shell32.dll; import table only 6 DLLs/46 symbols
> 
> **Source**: `ref:29a34b0ec6` · `ref:0d878e5797`

### 4. Download payload via WinINet

`T1071.001` · Confidence **high** · Static

The decrypted loader contains InternetOpenW/InternetConnectW/HttpOpenRequestW/HttpSendRequestW/InternetReadFile and the request method "GET"; the connection code pushes port 0x50(80) at 0x40191F and retries 3 times per target, and on success opens the HTTP request and reads the response body.

> **Evidence**: strings 0x401327–0x40138C WinINet family + 0x4013D0 "GET"; 0x40191F push 0x50 followed by call [ebp+4] (InternetConnectW)
> 
> **Source**: `ref:29a34b0ec6` · `ref:9e442fc4b0` · `ref:6f01b489ca`

### 5. Decompress downloaded payload

`T1140` · Confidence **high** · Static

The loader resolves RtlDecompressBuffer from ntdll and calls it, first allocating about 0xA7D8C0 bytes with VirtualAlloc, then dividing the compressed/decompressed buffers by offset to decompress the HTTP response body into executable second-stage data.

> **Evidence**: string 0x40122E RtlDecompressBuffer; 0x4014CB VirtualAlloc(0, 0xA7D8C0, 0x1000, 4); 0x3D0900/0x5B8D80 buffer offsets
> 
> **Source**: `ref:29a34b0ec6` · `ref:406fefc25f`

### 6. Drop and execute the downloaded file

`T1105` · Confidence **high** · Static

The decrypted loader uses CreateFileW (0x80000000 read / 0x40000000 write, CREATE_ALWAYS, 0x80 attributes), ReadFile/WriteFile/GetFileSize/DeleteFileW, joins the temp directory and a fixed filename with "%s\%s" (eilgx.exe, gtlbf.exe), and finally executes the dropped file via ShellExecuteW("open").

> **Evidence**: strings 0x401298 CreateFileW/0x4012A4 ReadFile/0x4012AD WriteFile/0x4012B7 DeleteFileW/0x40139A ShellExecuteW/0x4013B0 "%s\%s"/0x4013DA eilgx.exe; 0x40168C CreateFileW(GENERIC_WRITE, CREATE_ALWAYS)
> 
> **Source**: `ref:29a34b0ec6` · `ref:9e442fc4b0` · `ref:406fefc25f`

### 7. Disguise as a simple GUI

`T1036` · Confidence **high** · Static

The program uses the WINDOWS_GUI subsystem, and its entry point only initializes common controls before showing a dialog; the dialog title in the resource is the misspelled "Simle dialog", containing SysTabControl32, SysListView32 and two buttons both titled "IDC_BTN", serving as cover rather than a real business interface.

> **Evidence**: resource DIALOG(101): "Simle dialog", SysTabControl32, SysListView32, IDC_BTN; DialogBoxParamA call at 0x401D50
> 
> **Source**: `ref:67425b28a9` · `ref:05777af5df`

### 8. Collect host system information

`T1082` · Confidence **medium** · Static

The decrypted loader resolves and calls GetComputerNameW, GetVersionExW, GetModuleFileNameW, GetTempPathW and GetCurrentDirectoryW to obtain the hostname, OS version, own path and temp directory, serving the subsequent naming and drop-path construction.

> **Evidence**: strings 0x401259 GetComputerNameW, 0x40126A GetVersionExW, 0x401278 GetModuleFileNameW, 0x40128B GetTempPathW
> 
> **Source**: `ref:29a34b0ec6`

### 9. Hardcoded C2 and campaign identifiers

`T1071.001` · Confidence **high** · Static

The decrypted loader contains three hardcoded targets: 188.165.204[.]210→gtlbf.exe, 216.47.169[.]47→/data/Pdf/1709test.tar, 213.198.118[.]94→/apps/1709test.tar, along with the campaign identifiers "Treck" and "17cc"; these strings sit in the same decrypted block as the download/drop code.

> **Evidence**: string table 0x4013D4 Treck, 0x4013E4 188.165.204[.]210, 0x4013F4 gtlbf.exe, 0x4013FE 216.47.169[.]47, 0x40140C /data/Pdf/1709test.tar, 0x401423 213.198.118[.]94, 0x401432 /apps/1709test.tar, 0x401445 17cc
> 
> **Source**: `ref:29a34b0ec6` · `ref:14797fbce1`

## Do not misjudge

:::important
The following conclusions **are easy to misjudge**; please note this when citing this report.

- Do not judge it as ransomware merely from multi-engine Cryptodef labels: this time no file traversal, encryption APIs, encrypted files or ransom notes were observed (ransom_notes=0); the behavior surface is download/drop rather than encryption.
- Do not treat the three hardcoded IPs as confirmed online C2: no request or response to them was captured during the dynamic phase; they were recovered only from strings in runtime-decrypted memory, all static evidence.
- Do not claim the sample established persistence: the telemetry comparison shows no new Run key, and no service, scheduled task or related API call was found.
- Do not treat the roughly 31.7KB UTF-16 path list at the end of the file as sample behavior: that data lies outside the last mapped section (overlay) and is not referenced by the decrypted loader.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | Yes (stage2 `869e0d666963752026df24ab4c8e5cadd5d292dce8045409cb9b0a822e95cc10`) |

**Limitations and to be verified**

1. No HTTP request/response was captured for the 3 hardcoded C2s; network monitoring showed only background traffic such as system updates; therefore the C2s and configuration are statically recovered (pending_dynamic_verify=true), and it cannot be excluded that the sample did not initiate connections or failed to connect in the restricted network.
2. The disk file of the child process eilgx.exe was not retrieved; only hashes and a memory image exist, and the exact byte differences from the parent could not be confirmed byte by byte.
3. Run keys were identical before and after telemetry, but the service list shows environment-level differences (query timing/system noise) that cannot be attributed to the sample; no service, scheduled task, certificate store or security software operations were observed.
4. The 31,698-byte (231 entries) UTF-16LE path list at the end of the file is not inside any mapped section and is not referenced by the decrypted loader; its origin and purpose are undetermined, and it is suspected to be data appended during sample packing/distribution.
5. The second-stage payload (tar/PE) after a successful download was not obtained; family attribution relies mainly on decrypted loader behavior characteristics and external multi-engine labels.
6. Multi-engine labels conflict (Cryptodef/Upatre/BFLH) and include the ransomware category, which does not match this observation; family remains uncertain=true.
