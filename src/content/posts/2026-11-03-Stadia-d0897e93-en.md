## Behavior analysis

**11** behaviors in total, each backed by evidence; **8** statically recoverable, **3** obtained through dynamic analysis.

### 1. Decrypt embedded payload

`T1140` · Confidence **high** · static

The loader assembles 2,007,040 bytes according to a 445-entry chunk table (sizes and source pointers stored in record structures in .data), then decrypts it with RC4 using a fixed 32-byte key to obtain the next-stage plaintext.

> **Evidence**: FUN_0040e0a8 @0x40E0A8 (assembly + RC4 call), FUN_0040e3c4 @0x40E3C4 (KSA), FUN_0040deb0 @0x40DEB0 (PRGA); key at .rdata RVA 0x5FB32D, chunk table at .data RVA 0x5FC060 (stride 0x147)
> 
> **Source**: `ref:5a8bc6882a` · `ref:4ab6f4418a` · `ref:8283662bcb`

### 2. Reflectively load memory image

`T1620` · Confidence **high** · static

It allocates private memory (0xA2000) with PAGE_EXECUTE_READWRITE, rebuilds the MZ/PE header and section table in memory, then jumps to the entry point for execution, with the payload never touching disk.

> **Evidence**: FUN_004011b1 @0x4011B1 calls VirtualAlloc(0,0xA2000,0x1000,0x40); FUN_00401225 @0x401225 writes 'MZ', e_lfanew=0xC0 and 'PE\0\0'; FUN_0040d933 @0x40D933 validates the PE header
> 
> **Source**: `ref:b485fc055d` · `ref:a5c949d550` · `ref:506a4f96d8`

### 3. Drop as fake system process

`T1036.005` · Confidence **high** · dynamic

The payload copies itself into a random directory %ProgramData%\anMZRqlXKe19\RuntimeBroker.exe and launches it with an executable named after a system process.

> **Evidence**: dynamic: child process pid 7608's main module path is C:\ProgramData\anMZRqlXKe19\RuntimeBroker.exe; memory forensics: C:\ProgramData\ and '.txt' template (payload .data 0x8CDB0/0x8CDC0); imports CopyFileA/CreateProcessA
> 
> **Source**: `ref:d24d80bfe6` · `ref:a58a037fba` · `ref:df11566856`

### 4. Inject and replace process image

`T1055.002` · Confidence **high** · dynamic

## Must not claim

:::important
The following conclusions are **prone to misjudgment**; take care when citing this report.

- It is not ransomware/wiper: no file encryption, shadow copy deletion, or ransom note appeared within the dynamic window (the sandbox recorded no ransom note), and AES/DPAPI-related imports alone do not make it ransomware.
- No provable persistence yet: no service, scheduled task, or registry writes were observed, so it should not be claimed to establish boot autostart; only dropping to %ProgramData% and launching is confirmed.
- It is not merely a downloader/dropper: the payload includes browser theft, screen capture, and remote command modules, and labeling it only downloader/dropper would understate its capabilities.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | yes (stage2 `1dbd3bfab1f716064579d7a3bc14973230ed708f984a872c0349512b92c5c0ff`) |

**Limitations and pending verification**

1. The payload was recovered as a memory image (dump reconstruction), not unpacked directly from a disk file; the dumped image's import table was rebuilt from memory, so some section offsets may differ from the original file.
2. About 640KB of high-entropy second-layer data starting at 0x12AC97 in the decrypted plaintext was not recovered and may correspond to later modules or encrypted config.
3. C2 responses were returned by the emulated network; commands and secondary payloads actually delivered by the real server were not observed, and remote command/file upload capabilities come from static code and strings, not live triggering in the sandbox.
4. The family name is based only on the sample's internal module/window-class string ('StadiaVnc'), lacking vendor engine or YARA cross-verification, so confidence is low.
5. Config items such as mutex and campaign ID were not obtained; no persistence action appeared in the observation window, and autostart behavior after longer runtime cannot be ruled out.
