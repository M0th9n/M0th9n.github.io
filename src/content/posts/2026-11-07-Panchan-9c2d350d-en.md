### 1. Verify the P2P handshake magic

`T1095` · Confidence **high** · static

After a P2P connection is established it compares the 28-byte constant "pan-chan's mining island hi!" and only proceeds to peer-command handling if the comparison passes.

> **Evidence**: 0x6b8560 cmp r10,0x1c; 0x6b856e lea rbx,[rip+0x9599f] → 0x74df14; 0x6b8578 call 0x404e60 (memequal)

> **Source**: `ref:c1a315c692` · `ref:59b39860e8` · `ref:3d73c32fbf`

## What not to claim

:::important
The following conclusions are **easy to misinterpret**; please note them when citing this report.

- Do not report it as ransomware/wiper: no file encryption, deletion, ransom message, or destructive logic was seen.
- Do not treat the Discord webhook as the only/main C2: the main body is a P2P peer network, and the webhook only handles infection notification/liveness reporting.
- Do not call it a PAM module or claim /etc/pam.d was modified: only libpam bindings and PAM calls were seen, with no pam.d configuration writes or .so module drops.
- Do not report browser/wallet stealer behavior: credential acquisition is limited to SSH private keys/known_hosts and the SSH authentication queue.
- Do not assert hardcoded C2 IPs or mining pool addresses exist: statically only the Discord webhook, P2P protocol, and public IP query services were seen; pool/peer addresses are delivered at runtime.
- Do not directly identify the second embedded ELF as NBMiner or any specific family: the blob is truncated in the file (missing 0x301DCC bytes), so it can only be confirmed as an incomplete ELF.
:::

**Limitations and open questions**

1. This environment used the static-only tier and did not execute the sample; Discord reporting, P2P communication, miner startup, and PAM call paths are all code-level evidence pending dynamic verification (pending_dynamic_verify=true).
2. The section header table is out of bounds/stripped, with no symbol table or DT_NEEDED records; function boundaries are inferred from disassembly and string references, and some indirect call sites were not fully recovered.
3. The read-only segment's declared file length exceeds the actual file: the second base64 payload expects length 0xE64CD2, but only 0xB62F06 bytes remain, missing 0x301DCC bytes; the decoded ELF is incomplete, so its specific family and functionality cannot be confirmed.
4. The P2P peer list, XMRig/NBMiner pool addresses, and actual Discord response are not in the static configuration and require runtime delivery via sharepeer/shareupdateinfo or configuration pushed at runtime.
5. The specific purpose of the libpam calls (authentication verification, password-change backdoor, or local privilege escalation) is not fully confirmed; only the complete PAM session lifecycle binding is confirmed.
6. No dynamic sandbox or real execution was used; this format currently has no isolated dynamic channel.
