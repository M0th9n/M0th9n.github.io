> [!WARNING]
> **Verdict: malicious** · Family **PowerShell Add-Type shellcode loader (scaffold)** (unconfirmed) · Confidence **low**
> 
> Aliases: Add-Type P/Invoke loader stub, mssesafq.dll
> 
> This file is an ILONLY managed DLL whose only native import is mscoree.dll!_CorDllMain; the only method with IL is an empty constructor that just calls the Object constructor. Type nnnd6v3 declares kernel32's VirtualAlloc, CreateThread, WaitForSingleObject, LoadLibraryA, GetProcAddress, and GetProcAddressO via DllImport, with parameter names compressed to a/s/t/p/f/g/id/h/ms/n/m. This API set is exactly the standard injection primitive set of "allocate executable memory → write shellcode → create a thread to execute → dynamically resolve APIs", and the assembly namespace is Microsoft.PowerShell.Commands.AddType.AutoGeneratedTypes with randomized assembly and type names, matching the loader scaffold that PowerShell Add-Type compiles at runtime. The file itself contains no shellcode, configuration, or invocation logic; it is an auxiliary component in a loading chain rather than a standalone malicious program, so it is classified as a malicious loader artifact (confidence: medium).

## Behavior Analysis

There are **8** behaviors in total, each backed by evidence; **6** are statically available and **2** were obtained through dynamic analysis.

### 1. Declare injection primitive set

`T1055` · Confidence **high** · Static

Type nnnd6v3 declares six kernel32 exports — VirtualAlloc, CreateThread, WaitForSingleObject, LoadLibraryA, GetProcAddress, GetProcAddressO — via DllImport, forming the standard shellcode-injection primitive set of "allocate executable memory → write payload → create and wait on a thread → dynamically resolve APIs"; parameter names are compressed to a/s/t/p/f/g/id/h/ms/n/m to reduce readability.

> **Evidence**: all 6 ImplMap entries point to ModuleRef kernel32.dll; the Rva of MethodDefs VirtualAlloc/CreateThread/WaitForSingleObject/LoadLibraryA/GetProcAddress is 0 (pure declarations)
> 
> **Source**: `ref:ac33ff791c` · `ref:c7186166ba`

### 2. Dynamic API resolution declarations

`T1027.007` · Confidence **high** · Static

Declares LoadLibraryA plus two same-named overloads, GetProcAddress/GetProcAddressO, indicating a design that resolves arbitrary exported functions by name at runtime rather than statically binding the called APIs in the import table.

> **Evidence**: MethodDef 3=LoadLibraryA, 4=GetProcAddress, 5=GetProcAddressO, ImportedModule=kernel32.dll
> 
> **Source**: `ref:c7186166ba`

### 3. Add-Type compilation traces

`T1027` · Confidence **high** · Static

The type namespace is fixed to Microsoft.PowerShell.Commands.AddType.AutoGeneratedTypes, while the assembly name mssesafq and type name nnnd6v3 are random short strings — a signature left by PowerShell Add-Type compiling C# source on the fly in memory/a temporary directory, with the random naming also used to evade name-matching detection rules.

> **Evidence**: TypeDef 1 = Microsoft.PowerShell.Commands.AddType.AutoGeneratedTypes / nnnd6v3; Assembly name mssesafq; #Strings contains Microsoft.PowerShell.Commands.AddType.AutoGeneratedTypes
> 
> **Source**: `ref:c7186166ba` · `ref:7d4554074c`

### 4. Empty constructor with no call sites

`T1055` · Confidence **high** · Static

The only method with IL is .ctor (RVA 0x2050, bytes 1e 02 28 05 00 00 0a 2a), whose semantics are only ldarg.0 + call Object::.ctor + ret; no code path in the file calls the six P/Invokes above, indicating that the execution logic is held by an external script and this DLL only provides static methods that can be invoked via reflection.

> **Evidence**: .ctor RVA 0x2050 / file offset 0x250, IL bytes 1e02280500000a2a; Rva=0 for the remaining MethodDefs
> 
> **Source**: `ref:c7186166ba`

### 5. No embedded payload or configuration

`T1027` · Confidence **high** · Static

In the CLI metadata, the Field, FieldRva, ManifestResource, File, and ExportedType tables all have 0 rows; .rsrc contains only VS_VERSION_INFO (file name mssesafq.dll, version 0.0.0[.]0); strings contain no base64/hex blobs or URLs, so it can be concluded that the shellcode and configuration are both supplied at runtime by an external loading script.

> **Evidence**: metadata table row counts Field=0 / FieldRva=0 / ManifestResource=0; .rsrc RVA 0x4000 contains only the version resource; no flag/URL/hash string hits
> 
> **Source**: `ref:c7186166ba` · `ref:7d4554074c`

### 6. Purely managed, cannot self-start

`T1204.002` · Confidence **high** · Static

The PE has only the native import mscoree.dll!_CorDllMain, no export table, no exception directory, and no TLS directory; the CLI header flags are ILONLY and the entry is the _CorDllMain thunk; the file can only be loaded as a managed library by a CLR host and cannot start as a process on its own.

> **Evidence**: import table has 1 entry mscoree!_CorDllMain; data directories EXPORT=0/EXCEPTION=0/TLS=0; COM descriptor RVA 0x2008 flags=1(ILONLY)
> 
> **Source**: `ref:af08f25b7a` · `ref:ac33ff791c`

### 7. Standalone submission did not execute

`T1204.002` · Confidence **high** · Dynamic

> **Evidence**: dynamic timeline candidate_count=0, dumped_pids=[], events=[]; monitoring-component targets are only baseline processes such as svchost/monitoring component

> **Source**: `ref:3a6ac9a773`

### 8. No network egress at runtime

**Limitations and pending verification**

1. The sample is only a P/Invoke scaffold in a loading chain and contains no shellcode, configuration, or invocation logic; the actual loading script and payload are not in this file, so the family and C2 cannot be confirmed from this file.
2. After the dynamic sandbox submitted this DLL as an executable, no process creation occurred within the observation window and network monitoring showed no sample traffic; this is because the DLL has no standalone entry point, so no runtime behavior was obtained and reproduced is recorded as false.
3. The generic emulation engine does not support .NET assemblies, so its API call sequence could not be observed through emulation; the conclusions all come from static CLI metadata and IL parsing.
4. No cross-confirmation from vendor engines or YARA naming was obtained; the family is a behavioral inference marked uncertain=true.
