> [!WARNING]
> **Verdict: malicious** · Family **Remcos** · Confidence **high**
> 
> Aliases: Remcos RAT, Remote Control System, RemcosPro
> 
> This sample is an AutoIt3 compiled loader packed with PECompact. Statically, PECompact entry characteristics are visible, .text/.rsrc are both writable and executable, the import table retains only 4 kernel32 functions and all strings are unreadable; in a real dynamic sandbox it self-copies to %APPDATA%\UIMgrBroker\AboutSettingsHandlers.exe and is repeatedly relaunched by the task scheduler service host svchost.exe, its process main module is replaced by a 128KB Remcos 2.2.2 Pro image whose imports and strings cover keylogging, clipboard, screenshots, microphone recording, browser credential theft, service/registry operations and process injection; the same process initiates a TCP connection to the configured remcoss[.]onmypc[.]org:3765 and sends 728 bytes of encrypted data. Static analysis, memory forensics and real dynamic evidence corroborate one another, forming a complete observation of the malicious remote-control loader chain.

## Behavior analysis

**11** behaviors in total, each backed by evidence; **7** are available statically and **4** were obtained through dynamic analysis.

### 1. PECompact self-decryption

`T1027.002` · Confidence **high** · Static

The entry point is PECompact stub code; .text and .rsrc are both writable and executable (W^X); the decoded memory image restores the 'AU3!EA06' AutoIt script container at 0x107448, indicating that at runtime the AutoIt loader is first self-decrypted and then executed.

> **Evidence**: unpack.detect: packer=pecompact confidence 0.85; scan.triage: .text/.rsrc W^X; memory image 0x107448 = 'AU3!EA06'
> 
> **Source**: `ref:87645a9a2a` · `ref:9f540d09e8` · `ev-000016`

### 2. Memory replaced by Remcos

`T1055` · Confidence **high** · Dynamic

After execution its own main module is replaced: memory scanning determines that the module image was replaced (is_pe_replaced=1); at base address 0xC0000 there is a 0x20000-byte 32-bit PE that imports VirtualAllocEx/WriteProcessMemory/ReadProcessMemory/SetThreadContext/CreateProcessW, and its strings contain 'REMCOS v' and '2.2.2 Pro'.

> **Evidence**: Memory forensics: module=c0000 size=0x20000 is_pe_replaced=1; memory PE sha256=d9eb5077863a1419744d5a148464d5218028c3f5d3c88fcdb09e02211a887bc4; strings 'REMCOS v' / '2.2.2 Pro'
> 
> **Source**: `ref:2baa9590f5` · `ev-000016`

### 3. Self-copy to user profile

`T1036.005` · Confidence **high** · Dynamic

Creates %APPDATA%\UIMgrBroker\AboutSettingsHandlers.exe, with the file name impersonating a Windows settings handler component; this path is then actually executed, file sha256=AEDFFEA022E91FC0F195C64EA51A04615F502FD2FC606BC1F96426E2EFBAB882.

> **Evidence**: Dynamic process creation event: image=C:\Users\analyst\AppData\Roaming\UIMgrBroker\AboutSettingsHandlers.exe, hashes SHA256=AEDFFEA0...B882, imphash=1FC39DC9D4AA234C524DFA2F97E8B7E0
> 
> **Source**: `ev-000017` · `ref:2baa9590f5`

### 4. Kept alive by scheduled task

`T1053.005` · Confidence **medium** · Dynamic

The parent process of the above copy process is svchost.exe (the task scheduler service host), and it was relaunched 5 times within about 2 minutes (including rebirth after failure), consistent with a "registered scheduled task + watchdog restart" keep-alive scheme.

> **Evidence**: Dynamic events: parent_image=C:\Windows\System32\svchost.exe; pid 6876/5320/3096/4880 repeatedly appear within 18:32:03–18:33:14
> 
> **Source**: `ev-000017`

### 5. Callback to Remcos C2

`T1095` · Confidence **high** · Dynamic

The sample process initiates a TCP connection to the configured remcoss[.]onmypc[.]org:3765 and sends 728 bytes of high-entropy encrypted data; network monitoring recorded no response at all and no session was established.

> **Evidence**: Network monitoring: TCP connect 192.0.2[.]123:3765 (sandbox redirect address), uplink 0x2D8=728 bytes, followed by connection timeout; memory config 'remcoss[.]onmypc[.]org:3765:pass'

## Do not misjudge

:::important
The following conclusions are **easy to misjudge**; keep this in mind when citing this report.

- Do not judge this as ransomware because of the ransomware entry in the VT threat category or strings such as 'logs.dat' and 'Screenshots' inside the sample — no file encryption, deletion or ransom-note behavior was observed this time; these strings are Remcos's log and collection directories.
- Do not claim that a C2 session was successfully established or that remote commands were received — network monitoring saw only one TCP connection and a 728-byte encrypted uplink, with no response data and no complete request/response session.
- Do not claim that the sample actually downloaded a follow-up payload — no HTTP/HTTPS download request was observed; URLDownloadToFileW/InternetOpenUrlA appear only in the import table.
- Do not infer the existence of multiple independent unanalyzed payloads solely from the 4 high-entropy resource blocks — these resources were not decrypted and verified block by block.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | Yes (stage2 `d9eb5077863a1419744d5a148464d5218028c3f5d3c88fcdb09e02211a887bc4`) |

**Limitations and pending verification**

1. Network monitoring hid DNS query logs from the sample process; the C2 domain comes from the Remcos configuration in memory rather than from resolution records; the connection target appears in the logs as a sandbox redirect address, so the real IP cannot be inferred from the logs.
2. The sandbox timed out during the artifact collection stage, so some large memory dumps were not fully retrieved; the dumps, events and network logs used for these conclusions are all parts that were successfully retrieved.
3. The specific name and creation command line of the scheduled task were not covered by telemetry; the keep-alive method is inferred from the task scheduler service host as parent process and the repeated relaunch behavior, and is of medium confidence.
4. The HKCU\Software\r-8ET8H0 and Uninstall keys come from the Remcos configuration/strings; no direct evidence of registry write events was obtained.
5. The loaded Remcos module exists only in memory (it never landed as a standalone file), so its file-level hash cannot be compared with public sample repositories; the hash given in this report is the memory image hash.
6. Only a connection and an encrypted uplink were observed for the C2, with no reply and no complete session, so the C2 entry is marked as statically recovered and pending dynamic verification is retained.
