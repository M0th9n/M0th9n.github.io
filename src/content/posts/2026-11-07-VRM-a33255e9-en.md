> [!WARNING]
> **Verdict: Malicious** · Family **VRM** (uncertain) · Confidence **medium**
> 
> Aliases: VRM Stealer, vrm new, Phantom/Steam wallet stealer
> 
> The sample really executed in an isolated dynamic sandbox: process pid 4380 actively connected out to hxxps://nintifiv[.]net/sync (later switching to hxxps://nintifivopkackup[.]net/sync), periodically sending 133-byte ECDH(P-256) key-exchange requests; a ~2.87MB second-stage image was mapped in its memory, containing browser/Steam/Telegram/wallet (Phantom, Keplr) data-theft, clipboard monitoring, and hashed API-resolution code; after the sample stopped sending, the same beacon protocol continued from an already-running msedge.exe. The static side is a custom encrypted-container loader + hashed API resolution, masquerading as HyperX NGENUITY version information with no digital signature.

## Behavior analysis

**12** behaviors in total, each backed by evidence; **8** are statically available and **4** were obtained through dynamic analysis.

### 1. Load the encrypted container

`T1027.002` · Confidence **high** · static

It walks the PE section table, locates the .extjmp container by the magic 0x832F01EDEB2BAAC4 in the first 8 bytes of the section's raw data, then de-interleaves from section+0x50 by "copy 240 bytes / skip 240 bytes" to extract 2,595,904 bytes of high-entropy ciphertext.

> **Evidence**: at 0x1400024E0 it compares qword -0x7CD0FE1214D4553C; .extjmp raw offset 175616 starts with c4 aa 2b eb ed 01 2f 83
> 
> **Source**: `ref:dd36133b8c` · `ref:6f3ac43749`

### 2. Decrypt the payload in memory

`T1140` · Confidence **high** · static

It calls an internal decryption routine with material at container header 0x08/0x28, validates the plaintext's first 8 bytes 0x3E8F4A71C62B9D05, the 0x54-byte header and the 0x1C-word record table, then rebuilds the module to be executed.

> **Evidence**: 0x140003E90 calls 0x140003CD0/0x140003BD0/0x140003830, then validates 0x3E8F4A71C62B9D05
> 
> **Source**: `ref:7aac64be7a` · `ref:6f3ac43749`

### 3. Resolve APIs by hash

`T1027.007` · Confidence **high** · static

The static import table has only 7 DLLs / 113 symbols and does not include winhttp, ws2_32, or ncrypt; at runtime it first gets the module by 0x32BBCED2, then resolves function pointers by 32-bit hashes such as 0x1A953874 / 0x93E6AF36 before calling them (context identifier 0x50CA35D).

> **Evidence**: inside 0x140003E90, FUN_140001000(0x32BBCED2) and FUN_140001280(obj,0x1A953874/0x93E6AF36)
> 
> **Source**: `ref:7aac64be7a` · `ref:cf04506e6f`

### 4. Map and execute the payload

`T1620` · Confidence **high** · dynamic

It forms a ~2.87MB second-stage image at 0x140000000 (the sample's own image is at 0x7FF762860000), with the image header page zeroed; the payload retains resolution strings for NtCreateSection / NtMapViewOfSection / NtQueryInformationProcess.

> **Evidence**: process memory region 0x140000000..0x1402BE000, image sha256 deb7a1f773b1328bad6c5aeb84dfafa140e45b473d535f90585c9b8937f1f7bc
> 
> **Source**: `ref:f9bcbb4118` · `ref:7868c42621`

### 5. Inject into a browser process

`T1055` · Confidence **medium** · dynamic

The sample itself sent 13 C2 requests and then stopped; about 12 seconds later the exact same C2 protocol (same token, same campaign, same body structure) was sent 15 times by an already-running msedge.exe (pid 196), after which the sample process exited, consistent with the beacon migrating into the browser process.

> **Evidence**: network-side process ownership switched pid 4380 → pid 196 (msedge.exe) from 05:49:27; the sample had exited before the final scan
> 
> **Source**: `ref:1a40fbbdab` · `ref:7868c42621`

### 6. ECDH handshake callback

`T1071.001` · Confidence **high** · dynamic

Every 4–8 seconds it sends a POST to hxxps://nintifiv[.]net/sync (later switching to hxxps://nintifivopkackup[.]net/sync), with Content-Length always 133 and the body ' EK:04'+64 bytes (an uncompressed P-256 public key), used for ECDH session key exchange.

> **Evidence**: network log: POST /sync, X-Auth-Token: VRM-x9k4p2Q8rTmL5Ws1, X-Campaign-ID: main, X-Ts: 1794001720
> 
> **Source**: `ref:1a40fbbdab` · `ref:7868c42621`

### 7. Rotate browser user agents

`T1036` · Confidence **high** · dynamic

The same beacon rotates through 8 User-Agent strings (Chrome 134/135/136, Edge 135/136, Opera 120, Firefox 136/137) while the request headers and body structure stay fixed, blending into normal browser traffic.

> **Evidence**: in-memory UA list + a different User-Agent on every POST (including OPR/120.0.0[.]0, Firefox/137.0)
> 
> **Source**: `ref:1a40fbbdab` · `ref:f9bcbb4118`

### 8. Steal browser credentials

`T1555.003` · Confidence **high** · static

It reads Chrome/Edge 'Local State' and the cookie/login databases, decrypting with DPAPI + AES-GCM (error strings [DPAPI failed], [no AES key], [AES-GCM failed], [unknown prefix]), and counts entries via the ' -> cookies=' diagnostic.

> **Evidence**: payload .rdata: U:'\Local State', [DPAPI failed], [AES-GCM failed], ReadCookie/SetCookie, PRAGMA wal_checkpoint
> 
> **Source**: `ref:f9bcbb4118`

### 9. Extract wallet seed phrases

`T1555` · Confidence **high** · static

For Phantom (salt '.phantom-labs.vault.seed.') and Keplr/Cosmos extension data ('vaultV2', 'keyRingType', 'keyRingName', __uint8array__) it extracts seeds/private keys, outputting markers SEED_PHRASE|0x / PRIVATE_KEY|0x, and queries on-chain balances via /balances//delegations//accounts/.

> **Evidence**: payload .rdata at about 0x27411E and 0x27492E: '.phantom-labs.vault.seed.', 'SEED_PHRASE|0x', 'PRIVATE_KEY|0x'
> 
> **Source**: `ref:f9bcbb4118`

### 10. Harvest Steam tokens

`T1555` · Confidence **high** · static

It parses Steam loginusers.vdf and the registry ConnectCache, exporting steamid / web_secure / token, and reads the CEF cookie database, with Russian diagnostic output ('# diag: loginusers / cef / connectcache').

> **Evidence**: payload strings 'steamid: ', 'account: ', 'web_secure: ', 'ConnectCache', '# diag: cef'
> 
> **Source**: `ref:f9bcbb4118`

### 11. Monitor the clipboard

`T1115` · Confidence **medium** · static

It registers AddClipboardFormatListener / RemoveClipboardFormatListener and continuously receives clipboard content-change events.

> **Evidence**: payload import strings AddClipboardFormatListener (about 0x29EA56) and RemoveClipboardFormatListener
> 
> **Source**: `ref:f9bcbb4118`

### 12. Masquerade as a vendor version

`T1036.005` · Confidence **high** · static

The resource version information says 'HyperX NGENUITY 4.3.11[.]0 / Copyright (C) 2025 HyperX / NGENUITY.exe', but the PE timestamp is 2020-02, there is no Rich header, the security directory is empty (unsigned), and the main code is unrelated to HyperX products.

> **Evidence**: version resource starting at offset 0x51EA50; data directory SECURITY rva=0 size=0
> 
> **Source**: `ref:4c7229a38d` · `ref:2ce5422fbf`

## What not to claim

:::important
The following conclusions are **easy to misinterpret**; please note them when citing this report.

- Do not report it as ransomware/destructive: the sample did not encrypt user files, leave ransom notes, or delete/overwrite disks.
- Do not report it as a downloader/dropper: no later payload download or dropped file was seen in the observation window, and all C2 request bodies were 133-byte key exchanges.
- Do not judge it as legitimate software because the version information says HyperX NGENUITY: the file is unsigned, the PE timestamp does not match the version, and the main body is a custom encrypted-container loader.
- Do not take the presence of the comsvcs name in the memory dump as evidence of LSASS credential dumping: comsvcs.dll is not in that process's module list, and no lsass access behavior was observed.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | Yes (stage2 `deb7a1f773b1328bad6c5aeb84dfafa140e45b473d535f90585c9b8937f1f7bc`) |

**Limitations and open questions**

1. The container ciphertext uses the program's internal custom decryption flow and was not recovered offline; the second stage was taken from the running process memory with its header page zeroed, so its complete PE structure (section/import tables, etc.) cannot be given.
2. msedge.exe (pid 196) had exited before the final memory scan, so no dump of it was obtained; "the beacon migrated into a browser process" is based on network-side process ownership switching and is a medium-confidence inference.
3. All C2 request bodies in the observation window were 133-byte ECDH public keys; no data upload was seen, so the actual stolen-data format, volume, and encrypted payload were not verified.
4. The second C2 domain appeared only on the network side and was not found in the captured memory snapshot; its source (backup list/DGA/delivery) is undetermined.
5. Complete file-system and registry monitoring records were not obtained, so persistence cannot be strictly ruled out; currently only the absence of observed related behavior can be confirmed.
6. The family name VRM comes from the cross-corroboration of the self-built path with the build number/token prefix; there is no public vendor naming or YARA rule to compare against, so it is marked uncertain.
