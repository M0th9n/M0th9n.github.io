## Behavior Analysis

**12** behaviors in total, each backed by evidence, and all obtainable statically.

### 1. Delivers a PowerShell Script

`T1059.005` · Confidence **High** · Static

The sample body is unencrypted VBScript (only the .vbe extension is used); after running, it decodes the embedded base64 into a PowerShell script, writes it to C:\Temp\<random tag>.ps1, and executes it hidden with powershell.exe -nop -ep bypass -file.

> **Evidence**: VBE constants TEMP_DIR=C:\Temp\, PS_LAUNCH_CMD=powershell.exe -nop -ep bypass -file; DecodeAndWrite/Invoke use fso.CreateTextFile and shell.Run(launchCmd,0,True)
> 
> **Source**: `ev-000012`

### 2. GZip+AES Double Decryption

`T1140` · Confidence **High** · Static

The first-layer PowerShell first performs a SHA-256 integrity check on the packed data, then GZip-decompresses it and decrypts with AES-256-CBC/PKCS7, yielding a second-layer PowerShell script that runs in memory.

> **Evidence**: stage1_loader.ps1's Test-HashMatches/Expand-GZipBytes/Invoke-AesDecrypt; SHA-256 check passed, 1,877,568 B of ciphertext decrypted to 1,877,565 B of plaintext
> 
> **Source**: `ev-000012`

### 3. Polls the Host Process

`T1546` · Confidence **High** · Static

The second-layer script checks every ~5 seconds whether the aspnet_compiler process exists; when it is not running, the next injection is triggered, forming watchdog-style guarding and re-injection.

> **Evidence**: stage2.ps1's Start-WatchLoop / Test-ProcessAbsent -Name 'aspnet_compiler' / Start-Sleep 5; XOR key WWaDazKR6@@^^
> 
> **Source**: `ev-000012` · `ev-000014`

### 4. Hollows and Injects Remcos

`T1055.012` · Confidence **High** · Static

MACHINEE.dll's LAUNCHER(targetPath, shellcode) uses aspnet_compiler.exe as the host: CreateProcessA creates the process suspended, ZwUnmapViewOfSection unmaps the original image, VirtualAllocEx+WriteProcessMemory writes the embedded PE, and after fixing the PEB it resumes execution with SetThreadContext/ResumeThread.

> **Evidence**: stage3 user strings include VirtualAllocEx/WriteProcessMemory/ZwUnmapViewOfSection/CreateProcessA/GetThreadContext/SetThreadContext/ResumeThread and 'Failed to update PEB'; stage2 calls MACHINEE.WHORE.LAUNCHER, hostExe=C:\Windows\Microsoft.NET\Framework\v4.0.30319\aspnet_compiler.exe
> 
> **Source**: `ev-000014` · `ref:65a6f42c27` · `ref:d1c29dd133` · `ref:ece968bb12`

### 5. Decrypts the Built-in Configuration

`T1140` · Confidence **High** · Static

The embedded PE's SETTINGS resource (RT_RCDATA, 1,298 B) is stored in a "first byte = key length" format: the first byte is 0x88, followed by a 136 B key, and the remaining 1,161 B are RC4-decrypted to yield the C2, mutex and operational parameters.

> **Evidence**: FUN_00414e65 @0x414e65 obtains the resource via FindResourceA('SETTINGS' @0x476754)/LoadResource/LockResource; FUN_00407b8c/FUN_00407cad construct the key and decrypt; RC4 yields readable configuration
> 
> **Source**: `ev-000013` · `ev-000006` · `ev-000008` · `ev-000009` · `ref:9051237d0a`

### 6. TLS Callback to C2

`T1071.001` · Confidence **High** · Static

Remcos connects to 203.202.232[.]138 ports 50606/50607 over TLS, with a built-in TLS 1.3/AES-128-GCM suite; it also queries pro[.]ip-api[.]com for the victim's public IP geolocation.

> **Evidence**: stage4 string TLS13-AES128-GCM-SHA256; SETTINGS decrypts to 203.202.232[.]138:50606:1 and :50607:1 (trailing 1 indicates TLS); string hxxps://pro[.]ip-api[.]com/line/?key=...; imports WS2_32/WININET
> 
> **Source**: `ev-000013` · `ev-000014` · `ref:1a59d6449f`

### 7. Registry Persistence

`T1547.001` · Confidence **High** · Static

Writes autostart entries via HKCU\Software\Microsoft\Windows\CurrentVersion\Run and Policies\Explorer\Run, and can generate update.vbs to be executed by WScript.Shell invoking cmd, deleting the script itself afterwards.

> **Evidence**: stage4 strings Run key paths, \update.vbs, CreateObject(\"WScript.Shell\").Run \"cmd /c \"\"; configured install filename is remcos.exe
> 
> **Source**: `ev-000014` · `ev-000013`

### 8. Keylogging and Clipboard Capture

## Do Not Misjudge

:::important
The following conclusions are **easy to misjudge**; please take note when citing this report.

- The sample was not executed, so it cannot be claimed that C2 callbacks, session establishment or data exfiltration were observed on the current network; C2 was obtained only by static decryption and still requires dynamic verification.
- Although screenshot, camera, keylogging and clipboard API call paths exist, it cannot be asserted that these actions actually occurred on a victim machine.
- Do not misreport MACHINEE.dll as an independent malware family; it is the .NET process-hollowing loader of the first stage of this attack chain.
- No ransomware encryption, worm self-propagation or mining code was found; it should not be classified as ransomware/wiper/miner.
:::

## Analysis Method and Limitations

| Item | Content |
|:--|:--|
| Analysis method | Pure static analysis |
| Unpacking | Yes (stage2 `a903aec480623fdb790aeb356402d9d13a70b4479bfac84822968d42928d418e`) |

**Limitations and Pending Verification**

1. Pure static tier; the sample was not run. C2 sessions, actual persistence writes, collection actions and exfiltration were not dynamically observed, and relevant fields are marked pending_dynamic_verify.
2. C2 and mutex come from static RC4 decryption of the SETTINGS resource (the key sits after the resource's first byte) and have not been validated by real network callbacks.
3. The install filename and log/screenshot/recording directories come from configuration and strings; the full parent directory under %APPDATA% is inferred, and the actual drop paths were not observed.
4. The stage3 .NET injector has string obfuscation and was not decompiled method by method; the injection target is determined by call arguments and API strings.
5. No public sandbox or multi-engine reports were available; the family determination is based on the sample's own plaintext identifiers, configuration fields and code structure.
