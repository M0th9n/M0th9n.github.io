> [!WARNING]
> **Verdict: malicious** · Family **Unattributed Java-launcher masquerading loader** (uncertain) · Confidence **low**
> 
> Decompilation and emulation directly observed: the PE header is marked as a DLL yet the file is delivered as an .exe; the export table forges the Java launcher interface (JLI_Launch etc.) and every export has been reduced to a jump stub, while the real control flow is dispatched through a runtime-indexed relative-offset jump table; a TLS callback decrypts a set of pointers with a 64-bit rolling constant before DllMain; .rdata and .data each hide a Base64URL text of roughly 200 KB that decodes to full-entropy random data and can be judged an embedded encrypted payload. The sample itself has no legitimate Java launcher characteristics (no jvm/java-related strings), so the masquerading intent is clear. Payload execution was not observed.

## Behaviour analysis

**8** behaviours were recovered, each with supporting evidence; **7** of them are static and **1** was obtained through dynamic analysis.

### 1. DLL masquerading as EXE

`T1036.005` · confidence **high** · static

The PE characteristics field contains both EXECUTABLE_IMAGE and DLL, and the image is delivered as an .exe file; Windows cannot run it directly as an EXE, so it can only be loaded by a host process.

> **Evidence**: pe_parse: characteristics=0x2022(EXECUTABLE_IMAGE|LARGE_ADDRESS_AWARE|DLL), subsystem=WINDOWS_GUI, entry RVA 0xBB70
> 
> **Source**: `ref:4641691147`

### 2. Forged Java launcher exports

`T1036.005` · confidence **high** · static

The export table's DLL name is loader.dll and all 14 exports are OpenJDK launcher interface names (JLI_Launch/JLI_CmdToArgs/JLI_GetStdArgs…), intended to make the party loading it and security products mistake it for a legitimate Java launcher component.

> **Evidence**: pe_exports: dll_name=loader.dll, 14 JLI_* exports, JLI_Launch @RVA 0x308F
> 
> **Source**: `ref:74b7bf1ebd`

### 3. Exports degraded into jump stubs

`T1027` · confidence **high** · static

JLI_Launch is only 6 instructions (sub rsp,0x28 / xor ecx,ecx / call 0x18000336d / xor eax,eax / ret); all real logic has been moved into an internal obfuscated function, and the argument parsing and JVM loading code a legitimate launcher should contain is absent.

> **Evidence**: 0x1800030BF call 0x18000336d; 0x1800033D0 is the dispatcher
> 
> **Source**: `ref:b9d40e9498` · `ref:ffe819b1cd`

### 4. Jump-table dispatch hides control flow

`T1027` · confidence **high** · static

The dispatcher takes a 32-bit relative offset from a .rdata table (bases 0x18005F548 / 0x18005F1A4), adds it to code address 0x1800069D5 and calls indirectly; it switches between the two tables according to a one-time initialisation flag, so the static CFG cannot be recovered linearly.

> **Evidence**: *(code*)(0x1800069D5 + *piVar2) indirect call; table entries include negative offsets such as 0xFFFFD69A
> 
> **Source**: `ref:ffe819b1cd`

### 5. TLS callback pre-decrypts the pointer table

`T1027` · confidence **high** · static

The TLS callback tls_callback_0 calls FUN_18000a610, which decrypts 5 qwords with a 64-bit additive key (initial value -0x56F5C16FAC3B17A4, step 0x3794650508AE8BA1) and writes them into the TLS slot, together with status words such as 0x87B3/0xF3DF, so that the sensitive pointers are ready before DllMain.

> **Evidence**: tls_callback_0 @0x1800033D0 -> FUN_18000a610 @0x18000A610; 5 qwords starting at DAT_18005EE58
> 
> **Source**: `ref:ffe819b1cd` · `ref:6702866be5`

### 6. Two embedded encrypted payloads

`T1027.009` · confidence **high** · static

Two Base64URL texts (275,400 characters starting at .rdata 0x19200, and 276,224 characters starting at .data 0x68E00) decode to full-entropy data with a perfectly uniform byte distribution, distinct from one another and not compressed plaintext; the outer encoding pushes the section entropy down to 6.27/6.05 to evade high-entropy packer detection.

> **Evidence**: off 0x19200 / 0x68E00 long-string leading byte sequences 'zX3TE_dmv6h_' / '5-pjn3gf-kKM4'; decodes to 206,550 / 207,168 bytes, entropy≈8.0
> 
> **Source**: `ev-000014` · `ref:0250ea0365`

### 7. Deliberately minimal import surface

`T1106` · confidence **medium** · static

Only 80 imports, with no WinSock/WinINet/registry/service/process-creation/thread-injection APIs; all of them are basic CRT and kernel32 capabilities. Network and registry operations can only happen at runtime through dynamic resolution via LoadLibrary/GetProcAddress.

> **Evidence**: 75 kernel32 + 3 USER32 + 2 api-ms-win-core-synch; the only APIs that can be resolved dynamically are GetProcAddress/LoadLibraryA/LoadLibraryExW
> 
> **Source**: `ref:9495853994`

### 8. Likely executed through host sideloading

`T1574.002` · confidence **medium** · dynamic

The sample is a DLL delivered in .exe form; in the real sandbox it produced no new process after delivery (no child process, no network, no file dropped), which is consistent with a sideloading loader that must be loaded by a legitimate host process.

> **Evidence**: Dynamic sandbox: after detonation candidate_count=0, hollows count=0, no network requests; no new process appeared in the process table
> 
> **Source**: `ref:378364d4ae`

## Don't misread this

:::important
The following conclusions are **easy to get wrong**; keep them in mind when citing this report.

- It must not be concluded from this that C2 or outbound capability exists: the import surface contains no network APIs, and no network request appeared in the dynamic sandbox.
- The sample must not be treated as a Java program itself or as requiring a JVM to run: the JLI exports are only masquerading, and no jvm.dll / java.dll / JAVA_HOME or any other launcher string exists inside the sample.
- It must not be claimed that the payload plaintext, C2 address or configuration decryption key has been recovered: neither embedded blob decrypted into a recognisable structure, and recomputing the additive decryption still yields random values.
- It must not be classified as a stealer / ransomware / miner: there is no credential or browser-data access, no encrypted-file traversal and no compute-related code evidence.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | dynamic sandbox analysis + static decompilation |

**Limitations and open questions**

1. The sample is a DLL delivered under an EXE name; the dynamic sandbox produced no new process after delivery and no payload-layer behaviour (network/file/registry/injection) was observed, so all behavioural conclusions come from static analysis and emulation.
2. The two embedded encrypted blobs were not successfully decrypted: our own script's base64url decoding yields full-entropy random bytes, and neither zlib nor single-byte XOR produced a file-header hit; recomputing the additive decryption of FUN_18000a610 from the pseudocode did not yield valid pointers, so the algorithm details (or an XOR/rotation mix) still require dynamic memory forensics to confirm.
3. Because no plaintext payload was obtained, fields such as C2, mutex, install path and persistence method cannot be given; the related config items are marked dynamic and pending verification.
4. No vendor engine or family-rule cross-validation was available, so the family attribution remains unattributed, with low confidence.
5. The sample is relatively resistant to analysis (control-flow dispatch, TLS pre-decryption, section-entropy masquerading), so some branches may not be fully covered in a static environment.
