## Behavior Analysis

There are **7** behaviors in total, each backed by evidence; **1** is statically available and **6** were obtained through dynamic analysis.

### 1. Reflectively load embedded PE implant

`T1620, T1055` · Confidence **high** · Dynamic

The Go loader maps a standalone 260KB PE implant inside its own process (base 0x140000000, memory attribute MEM_PRIVATE, not in the loaded-module list); the host process was not observed writing this component to disk.

> **Evidence**: dynamic memory inspection: implanted_pe=1, module=140000000, size=0x3f000, mapping_type=MEM_PRIVATE; 4 standard PE sections (.text/.rdata/.data/.reloc) can be parsed from this memory region
> 
> **Source**: `ref:f7833ebd12` · `ref:ca60722598` · `ref:48b6fe5aa9`

### 2. Collect host and account information

`T1082, T1033` · Confidence **high** · Dynamic

The implant imports GetComputerNameA/GetComputerNameExA/GetUserNameA/GetKeyboardLayout/EnumDisplaySettingsW and queries system information via COM/WMI (CoCreateInstance, loading wbemprox.dll), giving it the ability to build a host fingerprint.

> **Evidence**: implant import table: kernel32.GetComputerNameA/GetComputerNameExA, advapi32.GetUserNameA, user32.EnumDisplaySettingsW/GetKeyboardLayout, combase.CoCreateInstance; the process module list includes wbemprox.dll
> 
> **Source**: `ref:14657dce92` · `ref:ca60722598`

### 3. Desktop screenshot capability

`T1113` · Confidence **high** · Dynamic

The implant imports GDI screen-capture and desktop-manipulation APIs (GetDC/GetWindowDC/BitBlt/CreateCompatibleBitmap/GetDIBits, OpenDesktopW/CreateDesktopW), giving it the ability to capture the current desktop image; no decrypted image content was obtained this time.

> **Evidence**: implant import table: gdi32.BitBlt/CreateCompatibleBitmap/CreateCompatibleDC/GetDIBits/GetCurrentObject, user32.GetDC/GetWindowDC/GetWindowRect/OpenDesktopW/CreateDesktopW
> 
> **Source**: `ref:14657dce92`

### 4. Beacon C2 and register host

`T1071.001, T1071.004` · Confidence **high** · Dynamic

After resolving 3skfin[.]tattoo, the process sends an application/x-www-form-urlencoded registration request to hxxps://3skfin[.]tattoo/:443 carrying tag, exp, and hwid.

> **Evidence**: network monitoring: DNS A query for 3skfin[.]tattoo; same process POST / HTTP/1.1, Host: 3skfin[.]tattoo; request body tag=6212ce203028b93bd449dc6e2524d44f&exp=1795454208&hwid=0137dfff850f0689d389fd2b7a15aa35
> 
> **Source**: `ref:007f642b77` · `ref:ca60722598`

### 5. Upload encrypted data in chunks

`T1041` · Confidence **high** · Dynamic

The same session continues with a multipart/form-data request (access_token, type=0, file="data", about 1.1KB of high-entropy binary), then sends a further 6-byte application/octet-stream request, performing data exfiltration.

> **Evidence**: network monitoring: Content-Type: multipart/form-data; boundary=msg1uR4R7i; Content-Length: 1226; fields name="access_token", name="type" value 0, name="file"; filename="data"; subsequent POST Content-Length: 6
> 
> **Source**: `ref:007f642b77` · `ref:ca60722598`

### 6. Disguise traffic as Chrome browser

`T1036` · Confidence **high** · Dynamic

All C2 requests uniformly use a Chrome/117 User-Agent and carry common browser headers such as Cache-Control/Pragma: no-cache, imitating ordinary browser access.

> **Evidence**: User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/117.0.0[.]0 Safari/537.36; Cache-Control: no-cache; Pragma: no-cache
> 
> **Source**: `ref:007f642b77`

### 7. Built-in glacier route simulation engine

`T1027` · Confidence **high** · Static

The Go body contains a complete glacier-crevasse route-planning DSL with A* search, invariant checks, and drill scenario data (GRID/START/GOAL/CELL, SLED_KG, KHUMBU/DENALI, etc.), forming a runnable functional shell that coexists with the malicious component.

> **Evidence**: strings include 'glacier DSL', 'CREVASSE', 'A*', 'missing mandatory GRID, START, or GOAL directive in glacier DSL', 'SLED_KG 140', 'CELL 0 0 PIN-A0 BLUE 340 95 2 6100', and multiple expedition fixtures
> 
> **Source**: `ref:5dce546f37` · `ref:0314f376ad`

## Do Not Misjudge

:::important
The following conclusions are **easy to misjudge**; please note them when citing this report.

- Do not assert that a desktop image was successfully captured and uploaded just because the implant imports BitBlt/GetDIBits: the sandbox has no interactive desktop, the uploaded content remains high-entropy data, and it was not decrypted for verification.
- Do not assert persistence: no registry Run key, service, scheduled task, or startup-directory write was observed within the analysis window.
- Do not assert that it downloaded or executed a second stage: no subsequent download requests or child-process creation were observed.
- Do not classify it as ransomware/wiper: no file encryption, ransom note, or data destruction behavior was observed.
:::

## Analysis Method and Limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | No |

**Limitations and pending verification**

1. The uploaded ~1.1KB multipart data is high-entropy binary, and no key or plaintext was obtained, so its specific content (host information, screenshots, or other data) cannot be confirmed.
2. The implant is a memory dump, and some code/strings are packed or obfuscated, so its internal logic could not be fully recovered statically.
3. Family attribution is based on C2 protocol fields (tag/exp/hwid, access_token/type/file) and component structure, without independent corroboration from vendor engines or YARA rules, so attribution uncertainty remains.
4. Dynamic interaction was completed in the isolated sandbox's fake network environment; domain resolution and HTTP sessions were handled by the sandbox, and no real C2 server was contacted.
5. No follow-on behavior such as persistence, downloading, or lateral movement was observed within the analysis window, so longer dwell time or other capabilities in different environments cannot be ruled out.
