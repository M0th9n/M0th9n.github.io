## Behavior analysis

**10** behaviors in total, each backed by evidence, all statically recoverable.

### 1. Drop embedded XMRig payload

`T1140` · Confidence **high** · static

It decodes a base64 string from its own read-only data section and drops a 7,051,456-byte ELF64 miner program; the payload contains XMRig features such as XMRIG_VERSION, stratum+ssl://randomx[.]xmrig[.]com:443, and --tls-fingerprint.

> **Evidence**: file off 0x375aa1 holds a 9,401,944-byte base64 string that decodes to a 7,051,456-byte ELF64 (sha256 6f445252...c063); the payload contains the string XMRIG_VERSION.
> 
> **Source**: `ref:317d66943f` · `ref:3d506b4337` · `ref:e48ba22c2c`

### 2. Configure pool and mine

`T1496` · Confidence **high** · static

It embeds XMRig run parameters (pool address, wallet/username, password, algorithm, NiceHash switch) and launches the miner process with remotely delivered pool parameters after running.

> **Evidence**: globals current_preset_xmrig_poolAddr / poolUser / poolPass / algo / enabled / nicehash and json tags xmrig_poolAddr etc. @ off 0x2d2d8c-0x2d587a.
> 
> **Source**: `ref:4881ee20d4` · `ref:60908d171e`

### 3. Preset NBMiner mining

`T1496` · Confidence **medium** · static

It likewise embeds NBMiner run parameters and switches and carries a second base64-encoded ELF payload, providing CPU/GPU dual-miner deployment capability.

> **Evidence**: current_preset_nbminer_enabled / algo / poolAddr / poolUser / poolPass and json:"nbminer_poolAddr" etc. @ off 0x2d39c6-0x2d60f6; the second base64 payload starts at off 0xc6d0fb and decodes to a high-entropy ELF64.

> **Source**: `ref:4881ee20d4` · `ref:a4beb0ea62` · `ref:42832d7fed`

### 4. Register systemd service

## Must not claim

:::important
The following conclusions are **prone to misjudgment**; take care when citing this report.

- Do not classify it as ransomware or a file encryptor merely because the sample contains chacha20-poly1305/AES cryptographic constants: these come from Go's standard TLS/SSH libraries, and no evidence of walking files and encrypting them was found.
- Do not treat the string-scan hits 'shusvz{}|0|1}' and 'uint64unuseduptimevmwarewaitid{hash}' as flags/keys: they are false hits caused by concatenation of adjacent short strings in Go's string table and have no real meaning.
- Do not assert a fixed C2 domain or IP: the main program contains no hardcoded C2/pool address; pool and update addresses are believed to be supplied by server-delivered config.
- Do not assume it is a legitimate system PAM module because it uses libpam: the sample is a standalone ELF executable that only dynamically calls libpam through cgo.
:::

**Limitations and pending verification**

1. The sample was not executed: this format has no isolated dynamic channel in this environment, and actual mining, SSH scanning, credential exfiltration, or egress were not observed; the related conclusions are all static inferences.
2. The main program contains no hardcoded C2/pool address; pool accounts and self-update addresses are believed to be supplied by server-delivered config and require dynamic observation or a config sample for confirmation.
3. The second embedded base64 payload is truncated at the end of the file (base64 length is not a multiple of 4); only about 9.5MB can be recovered, with content entropy near 8.0, so its exact program and purpose cannot be confirmed.
4. The ELF section header table has been removed and a LOAD segment's p_filesz exceeds the actual file size; static tools may miss some code/data, and some function boundaries and cross-references cannot be precisely recovered.
5. The family name is inferred from the combination of persistence naming, PAM-based fake sshd, XMRig/NBMiner config, and SSH propagation, without vendor YARA/multi-engine corroboration, so confusion with related variants is possible.
