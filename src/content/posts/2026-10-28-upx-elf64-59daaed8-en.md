> [!WARNING]
> **Verdict: malicious** · Family **Unattributed UPX-packed ELF64** (uncertain) · Confidence **low**
> 
> The file is an x86-64 static ELF64 that stores a UPX packing header directly after its three program headers (magic, checksum, stub size, version 14 and format 22 are all self-consistent). The body has been entropy-flattened (overall entropy 7.91, with no readable function names, imports, config or URLs), and the entry point sits at an unpacking stub at the end of the code segment — the classic "packed self-extracting payload" shape. All of the above was observed directly by this environment's tooling (program-header parsing, entropy/string scanning, isolated execution). The *malicious* verdict carries only medium confidence: the sample retains just its first 720,896 bytes from the delivery/collection chain (the declared code segment is 18,099,827 bytes long), so it crashes on entry with an out-of-bounds entry page and yields no real behavioural evidence.

## Behaviour analysis

**6** behaviours were recovered, each with supporting evidence; **5** are static and **1** comes from dynamic analysis.

### 1. Detect the UPX self-extracting stub header

`T1027.002` · confidence **high** · static

A UPX packing header sits directly after the three program headers (file offset 0xEC): magic 'UPX!', l_checksum 0x3CD9F8AC, l_lsize 0xAE4 (2788) bytes, l_version 14 and l_format 22 — evidence that this ELF was processed by a UPX-style self-extracting packer.

> **Evidence**: bytes '55 50 58 21' at offset 0xEC; string scan hits '<UPX!' at offset 0xEB; l_lsize=0xAE4, l_format=0x16
> 
> **Source**: `ev-000002` · `ev-000004`

### 2. Strip section and symbol tables

`T1027` · confidence **high** · static

The ELF header has e_shoff=0 and e_shnum=0, so the section table is removed entirely; the symbol count is 0 with no main, no exports and no readable function names, eliminating the usual reverse-engineering entry points.

> **Evidence**: structure parse: sections=[], symbol_count=0, symbols=[]; e_shoff=0/e_shnum=0
> 
> **Source**: `ref:97b98749fa` · `ev-000004`

### 3. Statically linked with no external dependencies

`T1027` · confidence **high** · static

The file has no PT_INTERP, no DT_NEEDED and zero dynamic imports, so it can be loaded without the dynamic linker. Consequently there is no libc/syscall import surface to infer functionality from.

> **Evidence**: structure parse: interp=null, needed=[], import_count=0
> 
> **Source**: `ref:97b98749fa`

### 4. Declares an 18 MB code segment

`T1027.002` · confidence **high** · static

The program headers declare a 24,326,946-byte RW segment at 0x400000 (only 4,096 bytes exist in the file, the rest is BSS) and an 18,099,827-byte RX segment at 0x1B34000. The entry point 0x2C76398 lies 0xADB bytes before the end of the RX segment, landing exactly inside the 2,788-byte stub region declared by the packer header — the runtime unpacks first, then jumps into the unpacked image.

> **Evidence**: LOAD#1 vaddr=0x1b34000, filesz=memsz=0x1142e73; e_entry=0x2c76398; segment end − entry = 0xADB, l_lsize=0xAE4
> 
> **Source**: `ev-000004`

### 5. Payload is fully entropy-flattened

`T1140` · confidence **high** · static

The file body (after 0x110) has a Shannon entropy of 7.91; 512-byte blocks average 7.43 with a maximum of 7.62, and there is no low-entropy plaintext region. Re-deflating the same data gives a ratio of only 0.99. Decoding attempts with LZMA, deflate, bzip2, zstd, LZ4, LZF and Snappy all produced no valid output, and no plaintext code, configuration or C2 strings were recovered.

> **Evidence**: overall entropy 7.91; mean block entropy 7.43; recompression ratio 0.99; multi-algorithm decode produced no output; scan_crypto 0 hits
> 
> **Source**: `ref:e7f71ac155` · `ev-000005` · `ref:fa8deef8e2`

### 6. SIGBUS on startup

`N/A` · confidence **high** · dynamic

In an isolated Linux execution environment, execve succeeds but the kernel immediately terminates the process with SIGBUS(BUS_ADRERR) at fault address 0x2C76398 — exactly the ELF entry point. That entry maps to file offset 18,097,048 while the file is only 720,896 bytes, so the entry page lies beyond the end of the file and the stub never executes. No file, network or child-process behaviour occurred at any point.

> **Evidence**: dynamic execution: exit=135, trace records 'SIGBUS si_code=BUS_ADRERR si_addr=0x2c76398'; address translation: 0x2c76398 → off 18,097,048 > 720,896
> 
> **Source**: `ev-000003` · `ref:94b20566bf`

## Don't misread this

:::important
The following conclusions are **easy to get wrong**; keep them in mind when citing this report.

- Do not classify the sample as ransomware, a stealer, a miner or a botnet. No file writes, network connections, process creation or memory injection were observed at any point.
- Do not claim a C2, domain, IP, URL or embedded configuration exists. String scanning, cryptographic-constant scanning and multiple decoding attempts all recovered nothing usable.
- Do not treat the 'QO{{}' at offset 630447 as a flag or signature: it is merely a five-byte printable run that occurs by chance in high-entropy data.
- Do not attribute the "file won't run" behaviour to deliberate anti-analysis design. An out-of-bounds entry page with only ~4% of the code segment present fits a truncated delivery/collection chain better than an intentional construction.
:::

**Limitations and open questions**

1. The sample is incomplete: only the first 720,896 bytes of the declared 18,099,827-byte RX segment exist in the file. Both the tail of the compressed data and the unpacking stub are missing, so it cannot be unpacked.
2. Family and behaviour class cannot be confirmed: there are no strings, imports, configuration or dynamic behaviour, so any specific capability (stealer, miner, RAT, etc.) lacks evidence.
3. Static recovery was attempted via program-header parsing, address translation, entropy and block-entropy analysis, and decoding with several common compression formats, all without success. A private compression or encryption format for the payload cannot be ruled out.
4. The packing header may be forged or altered (l_checksum cannot be verified offline), so "UPX-packed" is a shape-based judgement only — it does not confirm a specific packer or version.
5. The sample crashes at its entry point, so it cannot be ruled out that the complete form has arbitrary capabilities. This report does not speculate about behaviour that was not observed.
