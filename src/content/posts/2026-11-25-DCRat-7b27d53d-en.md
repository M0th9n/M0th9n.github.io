> **Verdict: malicious** · Family **DCRat** (unconfirmed) · Confidence **medium**
> 
> Aliases: DarkCrystal RAT, DCRAT
> 
> Static decompilation fully recovered an in-memory loading chain: DllMain creates a thread, downloads data from hxxp://47[.]98[.]135[.]22/diretxx[.]bin over WinHTTP, writes it into PAGE_EXECUTE_READWRITE memory and decrypts it in place with a custom RC4, then calls the decrypted entry directly; at runtime it also uses vectored exception handling and a timed thread to decrypt payload pages on demand and hide them a second time. The public sample repository labels this hash as DCRat, and the code structure is consistent with a native stager. Because the sample is a DLL without exports, the dynamic sandbox could not actually execute this chain, so no malicious behavior was obtained on the dynamic side; the assessment is based mainly on static code and public signature.

## Behavior Analysis

There are **7** behaviors in total, each backed by evidence, and all are statically available.

### 1. Starts loader worker thread

`T1106` · Confidence **high** · Static

When DllMain handles DLL_PROCESS_ATTACH it calls FUN_10001f20, which first calls DisableThreadLibraryCalls and then CreateThread to start the FUN_10001470 loader thread, so the malicious logic executes asynchronously outside the host's load flow.

> **Evidence**: FUN_10001f20 @0x10001F20 calls CreateThread(..., FUN_10001470, ...); FUN_1000217B @0x1000217B is the DllMain dispatcher.
> 
> **Source**: `ev-000013` · `ev-000012`

### 2. Downloads encrypted payload

`T1105` · Confidence **high** · Static

The loader thread calls FUN_10001c30, which uses WinHttpCrackUrl/WinHttpOpen/WinHttpConnect/WinHttpOpenRequest/WinHttpSendRequest/WinHttpReceiveResponse/WinHttpQueryDataAvailable/WinHttpReadData in sequence to download data from hxxp://47[.]98[.]135[.]22/diretxx[.]bin, with a receive buffer capped at 0x400000 bytes.

> **Evidence**: the WinHTTP call chain in FUN_10001C30 @0x10001C30; the URL plaintext is at VA 0x10016000 (file offset 0x14000).
> 
> **Source**: `ev-000015` · `ev-000014` · `ev-000024`

### 3. Allocates RWX memory

`T1620` · Confidence **high** · Static

It rounds the download length up to 4KB and calls VirtualAlloc(0, size, MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE), then copies the downloaded content into that writable and executable region.

> **Evidence**: FUN_10001470 @0x10001470: push 4 / push 0x3000 then call [0x1000F034] (VirtualAlloc), followed by FUN_10002E40 for the memory copy.
> 
> **Source**: `ev-000014` · `ref:c40e1a1d1f`

### 4. RC4-decrypts payload

`T1140` · Confidence **high** · Static

It runs a custom RC4 in place in the RWX memory: the S box is initialized with the four byte sequences (i+0), (i+1), (i+2), (i+3), the KSA mixes in a 16-byte key table, and the PRGA decrypts the downloaded content byte by byte; the decrypted result stays in the same memory region.

> **Evidence**: vectorized key generation starting at 0x100015B0, KSA starting at 0x10001650 and PRGA starting at 0x100016A0 inside FUN_10001470; key table VA 0x10016200 = 7f33c2211994c8701c437d9ebab29783.
> 
> **Source**: `ev-000014` · `ev-000024` · `ref:c40e1a1d1f`

### 5. Calls payload entry directly

`T1620` · Confidence **high** · Static

After decryption it first uses VirtualProtect to set the payload region to PAGE_NOACCESS, registers a vectored exception handler, and takes kernel32!BaseThreadInitThunk+0x14 as a fake return address, then calls FUN_10001000 to execute the payload's first byte through a function pointer.

> **Evidence**: FUN_10001470 calls VirtualProtect(...,1,...), AddVectoredExceptionHandler(1,0x100010A0), GetProcAddress(kernel32,"BaseThreadInitThunk")+0x14, then call FUN_10001000; FUN_10001000 @0x10001000 directly calls param_1.
> 
> **Source**: `ev-000016` · `ev-000014` · `ref:c40e1a1d1f`

### 6. VEH decrypts pages on demand

`T1027` · Confidence **high** · Static

The exception handler 0x100010A0 only intervenes when the exception code is 0xC0000005; it locates the 4KB page containing the faulting address, VirtualProtects it to PAGE_EXECUTE_READWRITE and records the access time, then returns to continue execution, thereby decrypting code pages on demand.

> **Evidence**: 0x100010A0: cmp dword ptr [esi], 0xC0000005; after computing the page index, call [0x1000F038] (VirtualProtect set to 4).
> 
> **Source**: `ref:4116fde5d3` · `ev-000017`

### 7. Second hiding of idle pages

`T1027` · Confidence **high** · Static

The guard thread FUN_10001230 polls every 20ms; for payload pages not accessed for more than 99ms it XORs them again with the plaintext copy and resets the page protection to PAGE_NOACCESS, so decrypted code does not remain in memory as plaintext for long.

> **Evidence**: FUN_10001230 @0x10001230: Sleep(0x14), GetTickCount, 99<delta check, per-page XOR with DAT_10016B54 then VirtualProtect(...,1,...).
> 
> **Source**: `ev-000017` · `ev-000014`

## Do Not Misjudge

:::important
The following conclusions are **easy to misjudge**; please note them when citing this report.

- Do not assert that the sample has persistence capability: neither static nor dynamic analysis found service, scheduled-task or registry-autostart writes.
- Do not claim the final payload has been confirmed as DCRat or that a C2 panel address was obtained: only the download URL was extracted; diretxx.bin was not retrieved or decrypted.
- Do not describe it as a standalone stealer or ransomware: the existing code only performs download, decryption and in-memory execution, and subsequent capabilities depend on the unretrieved payload.
- Do not treat the presence of the IsDebuggerPresent import or CPUID instructions as evidence of active anti-debugging: the symbols and instructions come from CRT initialization, and no independent anti-debug call chain was found.
:::

## Analysis Method and Limitations

| Item | Content |

**Limitations and pending verification**

1. The sample is a DLL without exports and needs an external host such as LoadLibrary/rundll32; the dynamic sandbox dropped it as a .exe and no new process appeared, so no runtime network, memory or file behavior was obtained.
2. hxxp://47[.]98[.]135[.]22/diretxx[.]bin was not retrieved, so the content of the payload after RC4 decryption, the final C2 and family attribution cannot be verified.
3. The C2 and configuration items are all statically extracted and marked pending_dynamic_verify; no HTTP request/response session was observed within the analysis window.
4. Dynamic emulation covered only CRT initialization and the DLL entry; the download, decrypt and execute chain inside the worker thread was never triggered.
5. No persistence, privilege-escalation, lateral-movement or credential-access code was found, so the final payload's capabilities cannot be inferred from it.
