## Behavior analysis

**8** behaviors in total, each backed by evidence, and all are statically recoverable.

### 1. Double fork and daemonize

`T1564` · Confidence **high** · static

After startup it forks twice and the parent exits; the child calls setsid, chdir('/') and ignores SIGPIPE, detaching from the terminal and working directory to stay resident.

> **Evidence**: main @0x40cdfc: fork→fork→setsid→chdir('/'); chdir target string '/' @0x4149ec
> 
> **Source**: `ev-000005` · `ref:e58636e966`

### 2. Plaintext direct connection to embedded C2

`T1095` · Confidence **high** · static

It reads the only entry in the built-in server table, '181.214.147[.]11:999', parses the port after the colon, creates a TCP socket and connects with a 30-second timeout, retrying every 5 seconds on failure.

> **Evidence**: initConnection @0x40cca8: strchr(':')→atoi→socket(2,1,0)→connectTimeout(...,30); commServer[0]=0x414244='181.214.147[.]11:999'
> 
> **Source**: `ev-000006` · `ref:5466e49e50` · `ref:78c82d33c0`

### 3. Report host fingerprint

`T1082` · Confidence **high** · static

After connecting it sends the C2 a banner carrying the local IP, a service-port tag and an architecture tag; the architecture is fixed to 'Sh4', and the port tag is '22' when python/python3/perl/telnetd is found, otherwise 'Unknown Port'.

> **Evidence**: main @0x40cdfc calls sockprintf(banner, inet_ntoa(ourIP), getPortz, getArch); getArch @0x407140 returns 'Sh4'; getPortz @0x407154 access('/usr/bin/python'…'/usr/sbin/telnetd')
> 
> **Source**: `ev-000005` · `ev-000007` · `ev-000008`

### 4. Probe local IP and MAC

`T1016` · Confidence **high** · static

It creates a UDP socket towards 8.8.8[.]8:53 and uses getsockname to obtain the local egress IP; it reads /proc/net/route and gets the MAC via SIOCGIFHWADDR, for reporting and network positioning.

> **Evidence**: getOurIP @0x4004bc: socket(2,2,0)→inet_addr('8.8.8[.]8')→connect→getsockname; open('/proc/net/route'); ioctl(SIOCGIFHWADDR)
> 
> **Source**: `ev-000010`

### 5. Dispatch remote commands to multiple processes

`T1059` · Confidence **high** · static

The main loop reads C2 commands with recvLine, trims them, splits command and arguments on '!' and upper-cases the command; for each attack type it calls listFork to spawn a worker process while the parent reaps children and maintains a pids table.

> **Evidence**: main @0x40cdfc recvLine loop + waitpid/pids table; processCmd @0x4071ec: strcmp command dispatch, strtok arguments, listFork
> 
> **Source**: `ev-000005` · `ev-000009`

### 6. Multi-protocol flood attacks

`T1498.001` · Confidence **high** · static

Built-in TCP/UDP flood implementations: SendSTDHEX repeatedly sends fixed payloads and connects to the target; sendMTCP/sendJUNK/sendHOLD/SendUDPCher/SendUDPByp/SendSTDv2-v4 and others select payload and rate according to the command.

> **Evidence**: SendSTDHEX @0x401d14: socket(2,2,0)→gethostbyname→loop send/connect until timeout; processCmd dispatches STDHEX/CNC/UDPHIT/UDPFULL/UDPKILL/UDPBYPASS/UDPCUSTOM
> 
> **Source**: `ev-000012` · `ev-000009`

### 7. HTTP layer-7 flood

`T1498.001` · Confidence **high** · static

It builds HTTP requests with random User-Agents and random paths, with the target path fixed to /cdn-cgi/l/chk_captcha; each attack runs until a specified expiry, repeatedly doing socket_connect→write→read(1)→close.

> **Evidence**: sendHTTPtwo @0x406f18: sprintf('%s /cdn-cgi/l/chk_captcha HTTP/1.1…'), useragents[] rotation, fork, while(time<deadline)
> 
> **Source**: `ev-000011` · `ev-000003`

### 8. Targeted game/voice protocol attacks

`T1498.001` · Confidence **high** · static

It provides dedicated payloads and query packets for SAMP/SA-MP, TeamSpeak3, Source/Valve, Minecraft, Fortnite and FiveM (e.g. 'TSource Engine Query', getstatus/getinfo) to take down game and voice services.

> **Evidence**: function table sendPrivSAMP/sendPrivTS3/sendValve/sendMC/sendFortnite/sendTS3; strings 'TSource Engine Query', 'getstatus', 'getinfo', 'SAMP'
> 
> **Source**: `ref:78c82d33c0` · `ev-000003` · `ev-000009`

## What not to claim

:::important
The following conclusions are **easy to misjudge**; keep them in mind when citing this report.

- Do not classify it as ransomware or an infostealer: there is no file encryption, credential reading or data exfiltration logic in the code; its actual capability is remote-command-driven DDoS.
- Do not treat the '22' returned by getPortz as evidence of SSH brute forcing or lateral movement: it is only a reporting field, and the program implements no SSH client or credential attempts.
- Do not claim the configuration is encrypted: the C2 and commands are embedded in plaintext; the TEA delta constant appears only in a custom PRNG and does not indicate an encrypted config.
- Do not claim a real C2 callback was dynamically observed: the sample could not be executed successfully in this run, and both the callback and command interaction are static inferences.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | Static decompilation (SH4 dynamic execution did not run) |
| Unpacking | no |

**Limitations and pending verification**

1. Dynamic execution could not start: the execution orchestration failed at the environment proxy configuration stage and produced no in-process behavior or network events.
2. The sample is SuperH4 architecture, which a normal x86 execution environment cannot run directly, and the emulation channel also returned no parseable output; therefore no socket/connect or C2 interaction was observed.
3. The availability of the C2, the actual command sequence issued and the attack targets are unverified; the C2 may be offline, and the related fields are marked pending dynamic confirmation.
4. Decompilation recovery of SH4 stack variables is incomplete and the command dispatch contains a jump table, so the parameter bounds of every attack branch could not be checked one by one.
5. The family naming is based on the program's built-in banner and self-identifying strings, without external engine/YARA cross-validation.
