> [!WARNING]
> **Verdict: malicious** · Family **VRM Stealer** (uncertain) · Confidence **medium**
> 
> Aliases: VRM, Phantom-labs Stealer
> 
> Detonated for real in the dynamic sandbox: the program decrypts the compressed payload in its own .extjmp section, then reflectively loads a 2.88 MB second-stage module into private memory; this module uses WinHTTP to POST every few seconds to hxxps://flybeebox[.]fun/sync and hxxps://heysunlab[.]fun/sync with a fixed token and ECDH public key, rotating forged browser User-Agents. The second stage contains extraction logic for browser credentials/Cookies, Telegram tdata, Steam login state, and wallet vaults/mnemonics/private keys for OKX/Bitget and others, plus clipboard monitoring and AES-GCM/DPAPI local encrypted storage logic, and it injects its own image into msedge.exe, replacing that module's headers. The outer version information is disguised as Shure MOTIV App.

## Behavior analysis

**11** behaviors in total, each backed by evidence; **7** are available statically and **4** were obtained through dynamic analysis.

### 1. Locate and decompress the embedded payload

`T1140` · Confidence **high** · Static

Walks its own PE section table, locates the .extjmp payload section via the 8-byte marker 0x7c521f83b30cd930, then obtains ntdll's RtlGetCompressionWorkSpaceSize / RtlDecompressBufferEx through PEB hash resolution, decompresses with format=4 (XPRESS-Huffman), and validates the structure magic 0x3e8f4a71c62b9d05 of the decompressed result.

> **Evidence**: FUN_1400024e0 validates the first 8 bytes of the section; FUN_140003e90 calls the hash-resolved decompression function and validates magic 0x3e8f4a71c62b9d05
> 
> **Source**: `ev-000021` · `ev-000022`

### 2. Hash-resolve ntdll exports

`T1027` · Confidence **high** · Static

Walks the PEB module list to locate ntdll.dll by name hash 0x4cacedce (a self-implemented djb2 variant XOR 0xa5b6409f), then resolves the needed exports via export-name hashes 0x64821b68/0xedf18c2a, avoiding static imports.

> **Evidence**: FUN_140001000(0x4cacedce)->ntdll.dll; FUN_1400014c0 is the hash function; FUN_140001280 parses the export table and handles api-ms-* forwards
> 
> **Source**: `ev-000023` · `ev-000024` · `ev-000019`

### 3. Reflectively load the second-stage PE in private memory

`T1620` · Confidence **high** · Dynamic

A few seconds into execution, a 2.88 MB implanted PE with 7 sections appears in the process's private memory at 0x140000000 (is_listed_module=0, MEM_PRIVATE), meaning the payload is reflectively loaded and executed; the image imports WinHTTP, BCrypt (ECDH/AES-GCM), COM, clipboard and SQLite.

> **Evidence**: memory scan workingset records module=140000000, module_size=2bd000, implanted_pe=1, and it was successfully dumped as 140000000.exe
> 
> **Source**: `ref:269905d703` · `ref:51a0b1ed63`

### 4. Inject and replace the msedge module

`T1055` · Confidence **high** · Dynamic

After about 90 seconds, a loader image with 8 sections and SizeOfImage 0x525000 (including an .extjmp section) appears at 0x27085f20000 inside msedge.exe (pid 5540); its PE header/section headers/entry point are marked as replaced (is_pe_replaced=1), and the process then continues outbound communication in place of the original process.

> **Evidence**: memory scan headers_scan: is_pe_replaced=1, dos/file/nt/sec hdr modified; workingset PE base 0x27085f20000; dump 27085f20000.msedge.exe
> 
> **Source**: `ref:df384f3b96` · `ref:269905d703`

### 5. ECDH heartbeat to C2

`T1071.001` · Confidence **high** · Dynamic

Uses WinHTTP to POST every 3-5 seconds to hxxps://flybeebox[.]fun/sync (original process) and hxxps://heysunlab[.]fun/sync (injected msedge process), with Content-Type: text/plain and a body of EK:04<64 hex bytes> (an uncompressed P-256 public key), used for key agreement and the beacon heartbeat.

> **Evidence**: network monitoring captured POST /sync, Host: flybeebox[.]fun / heysunlab[.]fun, and a 133-byte body beginning with EK:04; telemetry DNS events show pid 4908 querying flybeebox[.]fun and pid 5540 querying heysunlab[.]fun
> 
> **Source**: `ref:1c070b358c` · `ref:ebb5a6daf4` · `ref:5f8d98e169`

### 6. Rotate forged browser UAs

`T1036.005` · Confidence **high** · Dynamic

Each C2 request switches among User-Agents of multiple Chrome/Edge/Firefox versions, blending the HTTPS traffic into normal browser traffic.

> **Evidence**: within the same /sync request sequence the User-Agents were Chrome/135, Chrome/136, Firefox/136, Chrome/136 Edg, etc. in order
> 
> **Source**: `ref:1c070b358c`

### 7. Steal browser accounts and cookies

`T1555.003` · Confidence **medium** · Static

The second stage contains CEF/Chromium cookie and accounts parsing code (# diag: cef -> cookies=/accounts=) and reads login credentials and sessions from browser profile directories.

> **Evidence**: strings '# diag: cef ', ' -> cookies=', ' -> accounts=', '# diag: root=' and a SQLite engine

> **Source**: `ref:5f8d98e169` · `ref:0decdcb3d5`

### 8. Extract wallet mnemonics and private keys

`T1555` · Confidence **high** · Static

Embeds wallet extension IDs such as OKX/Bitget, markers such as vault/vaultV2/keyRing, SEED_PHRASE|0x, PRIVATE_KEY|0x and .phantom-labs.vault.seed., and parses mnemonics, private keys and keyrings from wallet extension storage.

> **Evidence**: strings mcohilncbfahbmgdjkbpemcciiolgcge, pbpjkcldjiffchgbbndmhojiacbgflha, "vaultV2":{, SEED_PHRASE|0x, PRIVATE_KEY|0x

> **Source**: `ref:0decdcb3d5` · `ref:5f8d98e169`

### 9. Collect Telegram and Steam sessions

`T1539` · Confidence **medium** · Static

Contains fields such as the tdata directory, steamid/account/web_secure/token, loginusers and ConnectCache, locating the Telegram desktop data directory and Steam login-state files and extracting session tokens.

### 10. Monitor clipboard content

`T1115` · Confidence **medium** · Static

Imports AddClipboardFormatListener/RemoveClipboardFormatListener and creates a message window to continuously monitor clipboard changes (usable for hijacking wallet addresses or collecting copied content).

> **Evidence**: import table user32.AddClipboardFormatListener / RemoveClipboardFormatListener; strings with the same names

> **Source**: `ref:5f8d98e169`

### 11. AES-GCM/DPAPI encrypted storage

`T1560.001` · Confidence **medium** · Static

Encrypts collected results with DPAPI and AES-GCM, saving them as JSON and SQLite databases (journal_mode=OFF) carrying nonce/salt/iterations/digest, and prints [AES-GCM failed]/[DPAPI failed] on failure.

> **Evidence**: strings [AES-GCM failed], [DPAPI failed], nonce/salt/iters/digest fields, PRAGMA journal_mode=OFF;
> 
> **Source**: `ref:0decdcb3d5`

## Do not misjudge

:::important
The following conclusions are **easy to misjudge**; take care when citing this report.

- Do not judge it as ransomware or a wiper: no file encryption, shadow copy deletion or destructive behavior was observed in this run; the sample's capabilities center on information theft.
- Do not conclude it is an official Shure component because its version information mentions Shure Incorporated / MOTIV App: that resource is a disguise; the internal build markings and PDB are both vrm/phantom-labs.
- Do not claim persistence (registry Run/services/scheduled tasks) was observed: the autostart entries in telemetry match the baseline, and no writes to persistence locations were observed from the sample itself.
- Do not claim remote download of follow-up payloads: only the ECDH beacon heartbeat was observed in this run; no server-side commands or secondary downloads were captured.
:::

## Analysis method and limitations

| Item | Content |

| Unpacked | Yes (stage2 `379c964b372fd5b5ed60d006ae96dc46a50a414c8f6125413e2e43e7861e28b2`) |

**Limitations and pending verification**

1. Network monitoring recorded only requests (full HTTP POST headers and bodies), not server responses, so the delivered commands or follow-up payloads cannot be confirmed; the protocol details of both C2s are reconstructed from the request side.
2. The actual read paths for wallet/Telegram/Steam/browser data were not dynamically verified one by one; the related capabilities are inferred from strings, imports and parsing code in the second stage.
3. No persistence behavior such as file drops, registry writes, services or scheduled tasks was observed within this analysis window; persistence capability is unknown.
4. The second stage is a memory dump with a rebuilt import table, so some function boundaries may differ from the original file; the outer loader's XPRESS-Huffman container was reconstructed only from structure and call chains, not rebuilt byte by byte from the original archive.
