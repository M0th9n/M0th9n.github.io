## Behaviour analysis

**10** behaviours in total, each tied to evidence; **8** are statically recoverable and **2** were obtained dynamically.

### 1. UPX self-extract image recovery

`T1027.002` · Confidence **high** · static

Entry RVA 0xE82A0 is the UPX unpacking stub (pushad; mov esi,0x413000; lea edi,[esi-0x12000]); it decompresses about 917KB of data from UPX1 to 0x401000, restores the full image and then jumps into it.

> **Evidence**: 0x4E82A0 pushad / mov esi,0x413000 / lea edi,[esi-0x12000]; CPU emulation executed 8.67M instructions, ending with edi=0x4E4008 and 0xE3008 bytes written.
> 
> **Source**: `ref:2eec4a0815` · `ref:4774a337fc`

### 2. Implant stage-2 PE in memory

`T1620` · Confidence **high** · dynamic

The main process holds MEM_PRIVATE executable images not registered as modules at 0xF00000 and 0x960000 (PE, 5 sections); the one at 0xF00000 is the ransomware body, with its import table rebuilt in memory.

> **Evidence**: memory scan implanted_pe=2; 0xF00000 has_pe=1 sections_count=5 mapping_type=MEM_PRIVATE protection=0x20; 0x960000 has_shellcode=1 pe_base_offset=0x53f.
> 
> **Source**: `ref:3fd73702f3`

### 3. Write ransom notes

`T1486` · Confidence **high** · dynamic

Writes one Recovery_Instructions.html into each of the user's Desktop, Documents and Downloads, replacing the template placeholders {{IDENTIFIER}}/{{URL}} with the victim ID and Tor portal address.

> **Evidence**: 01/02/04_Recovery_Instructions.html share sha256 50b2037314a20b1042847ce32f39907959ec896de79c8be0a75329171db5d689, written 01:29:55–01:29:56; the body contains 'Your personal ID:' and hxxp://gvlay6u4g53rxdi5[.]onion/18-Ki2t…
> 
> **Source**: `ref:3fd73702f3`

### 4. Encrypt files with .RS extension

`T1486` · Confidence **high** · static

Encrypts file content with the embedded RSA public key and CryptGenKey/CryptEncrypt, appends the .RS extension, and skips already-encrypted extensions such as .RS and .hivteam to avoid double encryption.

> **Evidence**: 0x85058 is an RSA PUBLICKEYBLOB (blob type 0x06 after base64 decoding); 0x84f10 '.RS_EXTENSION'; the extension whitelist includes .RS; readme.txt.RS appeared in the user's Downloads.
> 
> **Source**: `ref:8f38e4dc66` · `ref:80ead0cb98`

### 5. Delete shadow copies and backups

`T1490` · Confidence **high** · static

CreateProcessW launches vssadmin.exe Delete Shadows /All /Quiet, wmic.exe SHADOWCOPY /nointeractive and wbadmin DELETE SYSTEMSTATEBACKUP to remove shadow copies and system-state backups, and uses bcdedit to disable recovery and boot-failure policy.

> **Evidence**: 0x84d70 'vssadmin.exe Delete Shadows /All /Quiet'; 0x84dc0 / 0x84e48 bcdedit recoveryenabled / bootstatuspolicy; 0x84ec8 / 0x84f30 wbadmin; 0x84f90 wmic SHADOWCOPY.
> 
> **Source**: `ref:8f38e4dc66`

### 6. Terminate processes holding files

> **Evidence**: imports CreateToolhelp32Snapshot / Process32FirstW / TerminateProcess; process lists 'wxServer.exe,…,ZhuDongFangYu.exe' and 'wrapper,DefWatch,…,RTVscan'.

## Do not misjudge

:::important
The following conclusions are **easy to misjudge**; keep them in mind when citing this report.

- Do not report it as a stealer: no browser-credential, keylogging or mail-client data collection APIs/strings were found; the confidential-data wording appears only in the ransom note.
- Do not report it as a worm or claim confirmed lateral movement: the sample only enumerates network shares and volumes; no SMB brute force, PsExec or other propagation was observed.
- Do not report it as a backdoor/RAT (C2 heartbeat): there was no egress in the sandbox; the .onion address is a negotiation portal, not a command server, and should not be described as a persistent C2 channel.
- Do not report it as a wiper: files are encrypted and kept, with a ransom note attached; no logic overwriting or deleting disk data was seen.
- Do not assert the sample contains a private key or can decrypt by itself: only the RSA public key is present; the private key is not in the sample.
:::

## Analysis method and limitations

| Item | Content |
|:--|:--|
| Analysis method | Dynamic sandbox analysis + static decompilation |
| Unpacking | yes (stage2 `61e32079b1ba718025bbdcabe3e0a8677da7b31e05d20b0b2bab2be6ef2caef0`) |

**Limitations and pending verification**

1. The UPX wrapper's section headers were modified (UPX0 virtual size 0x12000 does not match the UPX header's u_len=0xE3881), and automated emulate-to-OEP unpacking did not locate the OEP, so the unpacked image was taken from the running process's memory.
2. No outbound network behaviour was observed in the sandbox; the .onion portal and email addresses come only from sample strings and the on-disk note, so portal liveness and the victim registration flow cannot be confirmed.
3. Ransomware encryption ran for only about 3 minutes before being stopped, so coverage is limited; the collected .RS files are fixed 8728-byte high-entropy data, which is insufficient to assess encryption algorithm details.
4. Family attribution is based on the high similarity of the ransom-note template, Tor portal URL structure and RSA+AES scheme, with no vendor engine or YARA result for cross-validation offline.
5. The autostart path %APPDATA%\svhost.exe and registry key HKCU\Software\MDSLK are inferred from string combinations; this run did not directly capture the corresponding registry/file drop.
6. The memory dump at 0x96053F was encrypted and renamed by the sample right after collection, leaving only the hash record in the timeline.
